製品選択シートを作る

用途と必須条件を先に決め、候補を絞り、公式情報で確認した日付を残す。感覚で選ばず、後から理由を説明できる形にするための一枚のシートを作ります。

3行の要点

  • 選ぶ前に「用途を1文」と「必須条件を3〜5個」を書き、足切りと加点を分けておくと、候補が自然に絞れる。
  • 候補は図鑑の検索・絞り込み・比較で出し、決定の根拠は公式ページと確認日で裏づける。
  • 未確認の欄を0点や「不可」で埋めず、確認待ちとして残すことが、後から説明できるシートの条件になる。

製品を選ぶときに困るのは、候補が少ないことではなく、多すぎることです。そして困るのが、選んだあとに「なぜこれを選んだのか」を説明できなくなることです。半年前の自分にも、隣の席の人にも説明できない選択は、条件が変わったときに見直せません。

この記事では、選択の理由を残すための一枚のシートを作ります。特別な道具は要りません。表計算ソフトか、紙とペンで足ります。候補を出す段階では、このサイトのAI製品の五つの層の分け方と、AI図鑑の検索・比較を使います。

用途を一文で書く

最初に書くのは、製品名ではなく用途です。「AIを使いたい」では、まだ何も決まっていません。一文で、次の三つが入るように書きます。

  • 何をしたいのか（作業）
  • どこで使うのか（端末・場所）
  • どんな制約があるのか（予算・機密性・期限）

たとえば「会議の録音から議事録の下書きを作りたい。手元の Windows で、外部に音声を出せない。月の予算は 3,000 円まで」となります。この一文があると、そのあとの判断がすべてこの文に照らして決まります。

用途が二つ以上あるときは、シートを分けてください。「議事録」と「コードの補助」は、必要なモデルも入り口も違います。一枚にまとめると、どちらにも中途半端な選択になります。

必須条件と加点条件を分ける

次に、条件を二種類に分けます。必須条件は、満たさなければ候補から外す条件です。加点条件は、満たせば嬉しいが、なくても諦められる条件です。

必須条件は 3〜5 個に絞ります。よく使うのは次の四つです。

条件何を書くか例
使う場所・OSどの端末の、どの入り口から使うかWindows のデスクトップと CLI
データの扱い外に出せるか、出せないか音声は社内のみ。文字起こしも外部不可
予算上限と支払い方月 3,000 円まで。年払いは不可
必要な機能これが無いと仕事にならない機能長い音声の分割入力、用語集の参照

加点条件には、料金の安さ、応答の速さ、拡張のしやすさ、復旧のしやすさ、日本語の自然さなどを置きます。加点条件は点数化しても構いませんが、必須条件は点数にしません。0.5 点の不足で「まあいいか」となる余地を作らないためです。

ここで一つ注意があります。必須条件に「最新の最上位モデルが使えること」を入れると、ほぼすべての候補が落ちます。モデルの世代は数か月で変わるので、必須条件には「今月必要か」を書いてください。「最上位」は加点条件に移します。

候補を図鑑で出す

条件が決まったら、候補を出します。AI図鑑では、名前・別名・提供元・モデルIDから検索でき、分類（モデル・ハーネス・アプリ・プラン）と、用途・使う場所・料金の区分で絞り込めます。

絞り込みで気をつけるのは、料金の区分の意味です。図鑑の「料金未確認」は「無料」でも「使えない」でもありません。価格表がまだ確認できていない、という意味です。ですから「無料」で絞って候補が1件しか出なくても、それ以外が有料とは限りません。料金で絞るのは、無料枠があることを確認済みの候補を探すときだけにしてください。

候補は 2〜4 件に絞ります。5 件以上残ったら、必須条件が足りていません。逆に 0 件になったら、必須条件が厳しすぎます。0 件のときに予算を上げる前に、どの必須条件が本当に必要かを読み返してください。「外部に音声を出せない」を外せば候補は増えますが、その条件を外してよいかは予算とは別の判断です。

公式ページで確かめ、確認日を書く

候補が決まったら、各候補について、必須条件に関わる事実を公式ページで確認します。確認するのは、料金、利用枠、対応する入り口、使えるモデル、データの扱いの5点です。まとめ記事や比較サイトは、公式で確認できるまでの手がかりとしてだけ使い、シートの確定欄には書きません。

確認したら、その日付を欄に入れます。料金と枠は数か月で変わるので、日付のないシートは半年後に使えません。確認できなかった項目は「未確認」と書き、空欄にしません。空欄は「0」や「なし」と読めてしまうからです。

同じ理由で、比較表に金額を並べるときは、単位を揃えてから並べます。月額のプランと、100万トークンあたりの単価は、そのままでは比べられません。使う量を仮定しないと換算できないので、仮定を書いた上で別々の列に置きます。この計算はコスト比較シートを作るで扱います。

シートの形

出来上がるシートは、次の列を持ちます。1候補につき1行です。

列書くこと
候補名製品名と、動くモデル名（分かれば）
層モデル・ハーネス・アプリ・プランのどれか
必須条件の判定条件ごとに「満たす」「満たさない」「未確認」
月額・単価額・通貨・税の扱い・確認日
使う場所実際に使う入り口
未確認のこと決定までに確かめること
判定採用・保留・不採用と、その理由1行

「判定」の列が、このシートの目的です。理由は1行で構いません。「必須条件のうち音声の外部送信だけが未確認。確認できれば採用」のように書けば、次に何をするかが決まります。

記入例を一つ挙げます。用途は「会議の録音から議事録の下書き。Windows、音声は外部に出せない、月3,000円まで」とします。

候補名層必須条件の判定月額・単価使う場所未確認のこと判定
デスクトップアプリ AアプリOS 満たす／予算 満たす／音声の扱い 未確認月 $20（税別、2026-10-28）デスクトップ音声がローカル処理か保留
ローカル実行のモデル BモデルOS 満たす／予算 満たす／音声 満たす無料（機材費は別）ローカル日本語の精度保留
クラウドの API Cモデル音声の扱い 満たさない100万トークン $2／$10（2026-10-28）API—不採用

この表は、正解を出すためのものではありません。保留の理由が「音声の扱いが未確認」と「日本語の精度が未確認」で違うことが見えることが成果です。次に確かめる順番も、ここから決まります。

小さく試してから決める

シートが埋まったら、採用候補に対して一度だけ試します。試すのは、実際の仕事そのものではなく、その縮小版です。議事録なら、3分の録音を1本、実際の会議と同じ条件で流します。

試した結果もシートに書き足します。うまくいったかどうかだけでなく、どこで止まったか、何回やり直したか、待ち時間はどれくらいかを書きます。ここで測った値は、自分の環境での実測です。公式ページに載っている数値や、他の人の記事の数値とは別物として扱ってください。

試せなかった操作は「未実機確認」と書きます。手元に該当の端末がない、契約していない、権限がない。どれも珍しい話ではありません。試していないことを「たぶんできる」で埋めると、シート全体の信頼が落ちます。

うまくいかないとき

シート作りでよく詰まるのは、次の四つです。

候補が 0 件になる場合は、必須条件を一つずつ外して、何件増えるかを確かめます。増えない条件は、実は候補を絞っていません。増えすぎる条件は、本当に必須かを見直します。

比較表が空欄だらけになる場合は、図鑑の記録が薄い項目を引いています。各項目のページには確認日と出典があるので、確認日が古いものは公式ページで取り直します。

金額が比べられない場合は、単位が違います。月額とトークン単価を同じ列に入れていないか確かめてください。同じ列に入れると、桁の大小で誤った判断をします。

判定が全部「保留」になる場合は、試す課題が大きすぎます。1回15分で終わる課題に縮めてください。15分で終わらない課題は、まだ製品の評価ではなく、業務の設計の話になっています。

評価

できたシートは、次の三つで点検します。第一に、第三者が読んで判定の理由を説明できるか。第二に、未確認の欄が残っているか。全部埋まっているシートは、たいてい推測で埋まっています。第三に、確認日が候補ごとに入っているかです。

シートは一度作って終わりではありません。料金と枠は変わり、モデルは入れ替わります。判定を変える必要が出たときのために、確認日を入れておくのです。

次は、このシートの「候補名」の欄を埋める作業に進みます。モデルの階層と用途から候補を選ぶ手順を、モデルの階層とタスク別の候補で扱います。
