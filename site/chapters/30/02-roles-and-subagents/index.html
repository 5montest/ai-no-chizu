第30章 分担と並列

調査・実装・レビューを、別の役に分ける

一つのエージェントに全部を任せず、役割を分けて渡します。コンテキストの分離が何をもたらし、何を失うのかを確かめてから、分担の可否を決めます。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • サブエージェントは会話履歴を引き継がない独立したコンテキストで始まる。分離は汚染を防ぐが、前提も伝わらない。
  • 役割は調査・実装・レビューで分け、道具と権限を役割ごとに変える。レビュー役には書き込みを与えない。
  • 分担は無条件に速くならない。起動と受け渡しのコストを測ってから決める。

前の記事で、計画を読んでから実行させる手順を作りました。この記事では、その計画を一人で全部やらずに、役割を分けて渡します。分ける相手は、同じハーネスの中のサブエージェントです。

先に結論を書きます。役割を分けると、作業の質は上がることがありますが、速くなるとは限りません。分けたぶんだけ、前提を書き直す手間と、結果を受け取って統合する手間が増えます。この記事の目的は、その増えた手間を測って、次に分けるかどうかを決められるようにすることです。

分けると、前提が消える

サブエージェントの性質で、最初に押さえるべき点はコンテキストウィンドウの分離です。Claude Code の公式の説明では、サブエージェントは新しい独立したコンテキストで始まり、会話履歴、すでに呼び出した Skill、すでに読んだファイルを見ません。例外は fork で、親の会話を引き継ぐとされています。

この性質は、両刃です。良い面は、親の会話に溜まった余計な情報や、途中で出た誤った前提を持ち込まないことです。悪い面は、あなたが当然だと思っている前提も伝わらないことです。リポジトリの構成、テストの走らせ方、触ってはいけないファイル、前回のレビューで指摘した点。どれも、渡さなければ存在しません。

だから、役割を分ける仕事では、指示の書き方が変わります。一人に頼むときの「いつもの調子で」は通じません。渡す情報を、依頼文とは別に項目として書き出します。

三つの役割と、渡すもの

役割は、調査・実装・レビューの三つで足ります。それぞれ、渡すもの、使わせる道具、返させるものが違います。

役割渡すもの使わせる道具返させるもの
調査質問、見てよい範囲、判断の基準読み取り、検索候補と根拠、確かめられなかった点
実装作業計画、触るファイル、検証コマンド読み書き、テスト実行差分、実行したコマンドと出力
レビュー差分、[[acceptance-criteria受け入れ条件]]、検査の観点読み取り、テスト実行

レビュー役には、書き込みを渡しません。レビュー役が自分で直し始めると、検査の対象と修正が同じ手に集まります。指摘を受けて直すのは実装役か自分です。第29章で作った検査用の Skill は、このレビュー役に渡す指示としてそのまま使えます。

調査役も、書き込みは要りません。読んだ結果を返すだけの役です。Claude Code には Explore と Plan という組み込みの役があり、どちらも一度きりで、会話履歴を持たずに走ると説明されています。この二つは、CLAUDE.md と git status を読み飛ばす点も公式に書かれています。前提を読ませたい調査なら、この組み込みではなく、自分で定義した役に渡します。

定義はファイルに置く

役割は、毎回プロンプトで説明するより、ファイルに置いたほうが安定します。Claude Code では .claude/agents/ か ~/.claude/agents/ に Markdown を置きます。YAML の frontmatter で名前と説明を書き、本文に指示を書きます。必須は name と description の二つだけで、ほかに tools、disallowedTools、model、permissionMode、maxTurns、isolation、background などが指定できます。

description は、呼び出すかどうかの判断に使われます。だから「調査する」ではなく「どの依頼のときに、何を返すか」を書きます。たとえば「差分と受け入れ条件を渡されたときに、指摘を場所・観点・直し方の三つで返す」のように書きます。

OpenCode では .opencode/agents/ に置くか、opencode.json の agent に書きます。mode で primary、subagent、all を選び、指定が無ければ all になります。権限は ask、allow、deny の三段階で、permission.task を使うと呼べるサブエージェントを制限できます。deny にした役は、呼び出しの候補から外れて説明にも出ません。ただし利用者が @ で直接呼ぶことはできる、と公式に書かれています。

Codexも、独立した調査をサブエージェントへ委任し、結果を主担当へ集約できます。CLIでは /subagents でスレッドを確認できます。ローカルクライアントでは独自のエージェント定義も作れます。親のサンドボックスと承認設定を引き継ぐため、役を分けることと、権限を分離することは別です。並列に書き込ませると競合が起こるので、まず独立した読み取り作業から分担します。

モデルは役割ごとに変えてよいが、記録する

役割ごとにモデルを変えるのは、理にかなった使い方です。調査やレビューは読み取りが中心で、実装は書き換えの正確さが要ります。安いモデルで足りる役割と、そうでない役割があります。

Claude Code では、使われるモデルが決まる順番が公式に示されています。呼び出し時の指定、frontmatter の model、環境変数 CLAUDE_CODE_SUBAGENT_MODEL、メインのモデルの順です。OpenCode では、上書きが無ければサブエージェントは呼び出した側のモデルを継ぎます。

どちらの場合も、役割分担表にモデルの列を残してください。記録が無いと、結果の差が役割の設計の差なのか、モデルの差なのかを切り分けられません。第28章の実験ログと同じ理由です。

同時に走らせるときの上限

役割を分けると、同時に走らせたくなります。走らせる前に、上限と費用を知っておきます。

Claude Code のサブエージェントは、同時に走らせられる数に上限があり、超えると Concurrent subagent limit reached と表示されると説明されています。入れ子の深さにも既定の上限があります。バックグラウンドで走らせたサブエージェントは、こちらの作業と並行して進みます。

費用の面では、サブエージェント自身の要求も、メインの会話と同じ利用上限に数えられます。加えて、多くのサブエージェントが詳しい結果を返すと、その受け取りでコンテキストを使います。詳しく返させるほど、次に使える余白が減ります。

さらに、役割同士が直接やり取りする形もあります。Claude Code の Agent teams は実験的な機能で、既定では無効です。有効にするには環境変数を設定します。公式の説明では、調整の費用がかかり、単独のセッションよりトークンを大幅に使うと書かれています。向くのは、各自が独立して進められる仕事です。逐次の作業、同じファイルの編集、依存の多い作業では、単独かサブエージェントのほうが効果的だと明記されています。人数の目安は 3〜5 人、1 人あたり 5〜6 個のタスクとされています。二人が同じファイルを編集すると上書きが起きる、という注意も書かれています。

Agent teams は対話セッションでのみ動き、-p のような非対話の実行では使えません。セッションに一つまで、入れ子のチームは作れない、といった制限もあります。使う前に、公式の制限の一覧を読んでください。

分担が向く仕事、向かない仕事

分けるかどうかは、仕事の形で決まります。

向くのは、境界がはっきりした仕事です。調査と実装が別のファイルを触る。実装とレビューが別の観点を持つ。二つの独立した機能を、別のディレクトリで作る。こうした仕事は、役割の間で受け渡す情報が小さく済みます。

向かないのは、同じ場所を触る仕事です。一つの関数を書き換えながら、そのテストも直す。二つの役割が同じファイルを編集すれば、後から書いたほうが前の変更を消します。順番に回したほうが速く終わります。

判断に迷ったときは、次の順で考えます。まず一人でやってみる。時間と手戻りを記録する。次に同じ依頼を役割に分けて、統合までの時間を測る。分けたほうが良かったかどうかは、この二つの記録で決めます。印象では決めません。

試す人向け演習・記入例と確認の観点

演習：同じIssueを、一人と三人で解く

練習用リポジトリの Issue を一つ選び、二通りで解きます。三人は、調査・実装・レビューの三役です。製品の機能が足りない場合は、役割をプロンプトの指示だけで分けてもかまいません。ファイルに定義する形は、うまくいったやり方を残す段階で作ります。

  1. リポジトリを clean にします。Issue を一つ選び、受け入れ条件を三行で書きます。
  2. 一人目（単独）の回として、計画を出させてから実行させ、検収まで通します。開始と終了の時刻、差分の行数、テストの結果、指摘の数を記録します。
  3. 変更を戻し、clean にします。
  4. 三人目の回として、まず調査役に、触るべきファイルと根拠を返させます。返ってきた内容を読み、実装役に渡す前提を三行で書きます。
  5. 実装役に、作業計画と一緒に渡します。実行させ、差分とテストの出力を受け取ります。
  6. レビュー役に、差分と受け入れ条件と検査の観点を渡します。指摘を、場所・観点・直し方の三つで返させます。
  7. 指摘を受けて直すかどうかを、自分で決めます。全部直す必要はありません。直さないと決めた指摘は、理由を一行で残します。
  8. 二回の記録を並べます。開始から検収までの時間、差分の行数、指摘の数、統合にかかった時間、使ったトークンの目安。

比較するのは、指摘の妥当さ、見落とし、重複、所要時間と利用量です。役を増やせば改善するとは限りません。受け渡しの分だけ手間がかかるからです。時間だけが増えて指摘も増えないなら、その分担は今の依頼には合っていません。

うまくいかないときの見方は、次のとおりです。調査役の返す内容が的外れなら、渡した質問が広すぎます。「どのファイルを、なぜ触るか」まで絞ります。実装役が調査の結果を無視するなら、渡す前提が長すぎて埋もれています。三行に削ります。レビュー役が実装を始めるなら、権限の設定が漏れています。書き込みを外します。三役の結果がかみ合わないなら、統合の担当を決めていません。統合は自分がやると決め、役割分担表に書きます。

役割分担表の雛形

分担するときは、先に表を書いてから始めます。書けない項目があれば、その分担はまだ設計できていません。

# 役割分担表

依頼：（四行の依頼文）
土台：（コミット）
受け入れ条件：
- 

| 役割 | 担当する作業 | 触るファイル | 渡す前提 | 使う道具 | モデル | 返す形式 |
| --- | --- | --- | --- | --- | --- | --- |
| 調査 |  |  |  | 読み取り |  |  |
| 実装 |  |  |  | 読み書き |  |  |
| レビュー |  |  |  | 読み取り＋テスト |  |  |

## 統合
- 統合する人：
- 統合の順番：
- 競合したときの判断：

## 結果
- 単独の回：時間 / 差分 / 指摘
- 分担の回：時間 / 差分 / 指摘 / 統合の時間

モデルの列は、実際に使った値を書きます。分からなければ未確認と書きます。空欄にすると、あとで「同じ条件で比べた」と読めてしまいます。

評価

五つの観点で点検します。役割ごとに触るファイルが重なっていないか。渡す前提が三行程度に収まっているか。レビュー役に書き込みを渡していないか。指摘を採るかどうかを自分で決めたか。そして、単独の回と分担の回の記録が、同じ依頼文で残っているか。

書き直しが要るのは、次の状態です。分担した回だけ依頼文を変えた。指摘をすべて自動で反映した。統合の時間を記録しなかった。どれも、分担が効いたかどうかを後から判断できない記録です。

できあがるもの

手元に残るのは、役割分担表と、二つの回の記録です。分担が効く依頼と効かない依頼の見分けが、一件ぶん具体的になります。

ここまでの分担は、一つの作業ディレクトリの中で行う前提でした。次の記事では、作業ディレクトリそのものを分けて、二つの仕事を同時に進めます。Git の worktree を使い、統合の費用まで記録します。並列にすれば速くなるとは限らない理由も、そこで数字として出てきます。

製品ごとのサブエージェントの対応はAI図鑑の比較ページで並べられます。図鑑の値は確認日つきなので、手元の版と食い違ったら、新しいほうを採ってください。
