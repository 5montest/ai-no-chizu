計画を先に出させ、実行と分ける

書き換える前に、何をどこまで変えるかの計画を出させます。計画に書かせる項目と、承認・差し戻しの判断を、製品ごとの実装の違いを確かめながら練習します。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 計画と実行を分けると、書き換えの前に「何を触るか」を読んで決められる。
  • Plan mode は製品ごとに置き場所が違い、権限モードの一つである場合と、役割の一つである場合がある。
  • 計画には、触るファイル・触らない範囲・検証のコマンド・完了の条件を書かせる。

書き換えが始まってから「これは頼んでいない」と気づくのは遅い。差分を読んで戻す手間がかかり、戻したあとに同じ依頼をやり直すことになります。手間を減らす方法は、書き換えの前に、何をどこまで変えるかを文章で出させることです。この記事の目的は、その計画を読んで、承認するか差し戻すかを自分で決められるようになることです。

前提は二つあります。第27章で作った練習用リポジトリと、第28章で決めた依頼文の型です。どちらも手元にない場合は、先にそちらを済ませてください。製品名からの確認はAI図鑑でできます。

計画を挟むと、読む量が減る

差分は、出来上がった結果です。結果から意図を推測するのは、思っているより難しい。計画は、結果より先に意図を見せてくれます。触るファイルが三つ書いてあれば、差分が出る前に「四つ目が出てきたらおかしい」と分かります。

計画を挟む利点は、速さではありません。書かせる手間が増える分、一度の依頼は遅くなります。代わりに、読む量が減ります。差分は数十行でも、計画は十行程度です。十行を読んで止める判断ができれば、数十行の差分を戻す作業が消えます。

計画と実行を分ける単位は、依頼一つです。依頼を出し、計画を読み、承認し、実行させ、差分で確かめる。この並びを崩すと、計画は飾りになります。

同じ「Plan mode」でも、置き場所が違う

計画を先に出させる仕組みは、製品ごとに名前と実装が異なります。ここを混同すると、別の製品の説明をそのまま当てはめて、動かない手順を書くことになります。

Claude Code では、plan mode は権限モードの一つです。公式の説明では、調査と提案を行い、変更は加えないモードで、計画を承認するまで編集はブロックされます。「Plan mode tells Claude to research and propose changes without making them.」とあり、例外として、対話端末でバイパス権限が使える場合を挙げています。入り方は四つあり、Shift+Tab での切り替え、/plan の入力、起動時の claude --permission-mode plan、設定の defaultMode です。有効な間は、状態表示に ⏸ plan mode on が出ます。

OpenCode では、Plan は役割（エージェント）の一つです。Build と Plan が primary agent として並び、Tab キーで切り替えます。Plan は「A restricted agent designed for planning and analysis.」と説明されています。権限モードではなく、道具と権限の組を変えたエージェントを切り替える形です。

Codex CLI には /plan があり、実装前に計画を提案するモードへ切り替えられます。これは現在の公式CLIコマンド一覧で確認できます。ファイルへの書き込みや通信の許可は、別途 /permissions とサンドボックス設定で確認します。計画モードにしたことだけで、実行権限まで設定できたとは考えません。

製品呼び名実装切り替え
Claude Codeplan mode権限モードの一つShift+Tab、/plan、--permission-mode plan、defaultMode
OpenCodePlanprimary agent の一つTab キー

計画に書かせる四つの項目

計画の形式は、依頼文（プロンプト）に書いて指定します。長い様式は要りません。四項目で足ります。

計画に含めること：
1. 変更するファイル（パスを列挙）
2. 変更しないもの（範囲と、触ってはいけない既存の記述）
3. 手順（順番に、何をどこへ足すか）
4. 検証（実行するコマンドと、完了と判断する条件）

まだファイルを書き換えないこと。計画だけを返すこと。

四つ目の「検証」が抜けた計画が、いちばん多い失敗です。検証が無いと、承認したあとに何をもって完了とするかを、実行のあとで決めることになります。それは検収ではなく、感想です。

「まだ書き換えないこと」の一行も必要です。plan mode に入っていれば編集は止まりますが、モードの外から同じ依頼を出すこともあるからです。モードに頼らず、依頼文でも止めます。

計画を読む三つの見方

届いた計画は、三つの見方で読みます。

範囲：変更するファイルが、依頼で名指ししたものの中に収まっているか。関係のないファイルが混ざっていたら、その理由を尋ねます。

手順：依頼の内容が、手順のどこに入っているか。抜けている項目があれば、承認の前に足させます。手順が「適切に修正する」のような一文だけなら、計画になっていません。

検証：実行するコマンドが、依頼の確認方法と対応しているか。テストを走らせる計画なのに、テストが存在しないディレクトリを指していたら、その時点で止めます。

読む時間は、長くても数分です。ここで止めれば、差分を戻す作業が消えます。読めない長さの計画は、承認しないでください。読めない計画を承認することは、計画を挟まなかったのと同じです。

承認・差し戻し・計画の続行

Claude Code では、計画を読み終えたあとに三つの選択肢が出ます。計画どおりに進めて以後の許可を省くか、編集のたびに承認するか、計画を続けさせるかです。公式の説明では、この三つが承認時の選択肢として示されています。

迷ったときは、真ん中を選びます。編集のたびに承認する形なら、計画と実行のずれをその場で見つけられます。慣れてきた仕事だけ、まとめて進めてよいと判断します。

計画そのものを直したいときは、計画を編集してから承認します。Claude Code では Ctrl+G で計画を編集できます。差し戻す場合は、理由を一行で返します。「3番目の手順は今回の依頼に含まれていないので外してください」のように、計画の項目番号を指して書くと、次の計画が変わります。

OpenCode では、Plan と Build を Tab キーで切り替えます。Plan で方針を出させ、Build に切り替えて実行させます。切り替えの時点で、方針が会話に残っているかを確かめてください。

承認した計画は、差分の代わりにはなりません。実行のあとに必ず差分を読みます。計画が正しくても、実装が計画どおりとは限らないからです。ここは第27章の検収と同じ手順です。

試す人向け演習・記入例と確認の観点

演習：同じ依頼を、計画あり・なしで一回ずつ

練習用リポジトリで、小さな依頼を二通りに試します。二つのハーネスを用意する必要はありません。一つのハーネスで、計画を挟む回と挟まない回を作ります。

  1. リポジトリを clean にします。git status で確認し、変更があればコミットするか退避します。
  2. 依頼文を一枚のテキストに書きます。第28章の四行に、上の「計画に含めること」を足した形にします。
  3. 一回目は、計画を求めずに実行させます。変更後の差分の行数と、依頼から外れた箇所の数を数えます。
  4. git restore で戻し、clean にします。
  5. 二回目は plan mode に入り、同じ依頼を出します。返ってきた計画を、範囲・手順・検証の三つで読みます。
  6. 計画に不足があれば、差し戻して書き直させます。書き直しの回数も数えます。
  7. 承認して実行させ、差分を読みます。依頼から外れた箇所の数を数えます。
  8. 二回の記録を並べます。差分の行数、外れた箇所の数、依頼から検収までの時間、計画の読み直しの回数。

期待する結果は、二回目のほうが「外れた箇所」が少なく、かかった時間は同じか少し長い、という形です。計画を挟んだ回が必ず速くなるとは限りません。速くならなくても、戻す作業が減っていれば、その依頼では計画を挟む価値があります。

この記事の数値は挙げません。手元の結果が唯一の根拠です。書き留める表の項目だけを、この記事で決めています。

うまくいかないときの見方

計画が出てこないときは、モードに入っていないか、依頼文に「計画だけを返すこと」が抜けています。状態表示を確かめ、依頼文の最後の一行を見直します。

計画が依頼とずれるときは、依頼文の「変更しないもの」が弱い可能性があります。範囲を一文で足すより、触ってはいけないファイル名を挙げたほうが効きます。

計画が長すぎて読めないときは、依頼が大きすぎます。節を一つに絞って、計画の長さが十数行に収まる大きさに分けます。

計画どおりに実行されないときは、計画を会話の最後に置き直します。「承認した計画に従って実行してください」と一行添えるだけで戻ることがあります。それでもずれるなら、計画の手順が抽象的すぎます。ファイルと関数の名前まで書かせます。

作業計画の雛形

一回の依頼につき、次の形で計画を残します。Markdown でも表計算でも構いません。列を変えないことが大事です。

# 作業計画

依頼：（四行の依頼文をそのまま）
土台：（依頼前のコミット）

## 変更するファイル
- 

## 変更しないもの
- 

## 手順
1. 

## 検証
- 実行するコマンド：
- 完了の条件：

## 判断
- 承認 / 差し戻し（回数）
- 差し戻しの理由：

計画は、実行のあとに捨てません。差分と並べて残すと、次の依頼で「どの書き方が計画を短くするか」が分かります。

評価

四つの観点で点検します。計画に四項目が入っていたか。承認の前に、範囲・手順・検証を読んだか。差し戻したときに、理由を計画の項目で指したか。そして、承認したあとにも差分を読んだか。

書き直しが要るのは、次の状態です。計画を読まずに承認した。計画を挟んだ回のほうが速いことを、成果として書いた。計画と差分のずれを、実行のあとで初めて見つけた。どれも、計画を挟んだ意味が残っていない進め方です。

できあがるもの

手元に残るのは、作業計画と、二回の実験の記録です。計画の型が一つ決まれば、次の依頼からは同じ四項目を貼るだけで済みます。

ここまでで、計画と実行を分けるところまで来ました。次の記事では、その計画を一人で全部やらずに、調査・実装・レビューへ役割を分けます。分けると何が良くなり、何が失われるかを、次の記事で確かめます。製品ごとの対応はAI図鑑の比較ページにまとめてあるので、自分の環境で確かめた値と突き合わせてください。
