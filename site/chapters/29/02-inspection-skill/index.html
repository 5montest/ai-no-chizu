第29章 拡張機構

記事を検査するSkillを作る

文体とHTMLの意味づけを、同じ観点・同じ形式で指摘させるSkillを作ります。読み取り専用の道具だけを許し、入れる前と後で指摘を比べます。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • Skill は SKILL.md 一枚で作れ、本文は呼び出したときだけ読み込まれる。
  • 検査する Skill は読み取り専用の道具だけを許し、対象を一つに絞る。
  • 入れる前と後で、指摘の数・行番号・形式を同じファイルで比べる。

前の記事で、拡張の層を分けました。この記事では Skill を一つ作ります。題材は、この連載自身の原稿です。記事の文体と HTML の意味づけを、毎回同じ観点で指摘させる Skill を作り、入れる前と後で結果を比べます。

作るものは、SKILL.md 一枚と README.md 一枚です。外部への通信も、API キーも使いません。

何を作るか

作るのは「記事検査」という名前の Skill です。Markdown か MDX のファイルを一つ受け取り、三つの観点で指摘を返します。

  • 文体：一文の長さ、ぼかし語、断定と推量の混在。
  • 見出し：階層の飛び、見出しだけを読んで内容が分かるか。
  • HTML：表のヘッダー、リンクの文言、画像の代替テキスト。

指摘は、行番号・観点・直し方の三つで返させます。ファイルは書き換えません。

なぜ検査から始めるのか。修正までさせる Skill を作ると、何を直したのかを追うのが難しくなります。検査と判断を分けておけば、指摘を読んで、採るか採らないかを自分で決められます。レビューの代わりに使うものではなく、レビューの前に見落としを減らすものです。

前提条件と、使うもの

必要なのは、テキストエディタと、Skill を置けるディレクトリだけです。Claude Code が入っている環境なら、.claude/skills/ に置けば読み込まれます。入っていない環境でも、この記事の内容は読めます。SKILL.md は Markdown なので、他のハーネスの指示ファイルに移植するときの下書きにもなります。

検査対象は、手元の Markdown か MDX を一つ用意してください。自分のブログの記事でも、業務の手順書でも構いません。うまく書けていないと分かっている古い原稿のほうが、検査の効果が見えます。

この記事の手順は、Claude Code の公式ページにある記述に沿っています。ただし、実際の検査結果は環境とモデルで変わります。この記事に出てくる出力例は、すべて例示です。実測値ではありません。

SKILL.md を書く

まず、プロジェクトの .claude/skills/article-check/SKILL.md を作ります。中身は次のとおりです。

---
name: article-check
description: 記事の Markdown/MDX を、文体・見出し・HTML の観点で検査する。記事を書き終えた直後と、公開前の点検で使う。
argument-hint: <検査するファイルのパス>
allowed-tools: Read, Grep, Glob
disable-model-invocation: true
---

# 記事検査

`$ARGUMENTS` に指定されたファイルだけを読む。書き換えない。

## 観点

### 文体
- 一文が 80 字を超えていないか。
- 同じ語が同じ段落で 3 回以上くり返されていないか。
- 「とても」「非常に」「さまざまな」のように、程度をぼかす語が残っていないか。
- 同じ段落で「〜です」と「〜かもしれません」が混ざっていないか。

### 見出し
- 見出しの階層が飛んでいないか。
- 見出しだけを順に読んで、記事の流れが追えるか。
- 見出しが「まとめ」「その他」のような、内容の分からない語だけになっていないか。

### HTML
- 表の先頭行が `<th>` になっているか。
- リンクの文言が「こちら」「ここ」だけになっていないか。
- 画像に代替テキストがあるか。

## 返す形式

指摘を、行番号・観点・直し方の三つで返す。
該当が無い観点は「該当なし」と書く。
推測で直さない。判断が分かれる箇所は「要確認」とし、理由を一行添える。

allowed-tools に、読み取り系の三つだけを書いています。Read はファイルを読む、Grep は語を探す、Glob はファイル名を探す。書き込みも、シェルの実行も入っていません。Sandbox の内側で動かすのと同じ効果を、道具の一覧で得る形です。

disable-model-invocation: true は、モデルの判断で勝手に呼ばれるのを止める欄です。検査は、自分が「やる」と決めたときに走らせたいので、これで人が呼ぶだけの Skill になります。

argument-hint は、呼び出し方の案内です。$ARGUMENTS が、渡した引数に置き換わります。

行番号を必ず付けさせているのは、指摘を確かめるためです。行番号の無い指摘は、原稿を探すところから始まります。

README を書く

SKILL.md と同じディレクトリに、README.md を置きます。 Skill を配る予定がなくても、半年後の自分が読む相手です。

# article-check

記事の Markdown/MDX を、文体・見出し・HTML の観点で検査する Skill。

## 使い方

/article-check src/content/posts/example.md

## 何をするか

- 指定したファイル一つを読み、指摘を返す。書き換えない。
- 指摘は「行番号・観点・直し方」の形で返る。

## 何をしないか

- ファイルの変更、コミット、外部への送信。
- 記事の内容そのものの事実確認。引用や数値が正しいかは見ない。

## 検査項目

SKILL.md の「観点」を参照。項目を変えたら、この README の更新日も変える。

## 限界

- 文体の判断は、この Skill の持ち主の基準である。他人の文章に当てるときは、基準を合わせる。
- 表の HTML は、Markdown の表記から生成される形を見ている。MDX の中で直接書いた HTML は、範囲外になることがある。

更新日：2026-10-28

「何をしないか」の節を省かないでください。Skill は、書かなかったことを勝手にやらないとは限りません。範囲を書いておくと、呼び出したあとに「これは想定外だった」と言いやすくなります。

試す人向け演習・記入例と確認の観点

演習：入れる前と後で、指摘を比べる

比べる条件を先に固定します。対象のファイル、依頼文、モデルの三つです。どれかが変わると、差が Skill の効果なのか条件の差なのか分かりません。

  1. 検査するファイルを一つ決めます。長すぎるものは避け、200 行以内に収まる記事を選びます。
  2. Skill を置く前に、同じハーネスで検査を頼みます。依頼文は、あとで使うものと同じ文面にします。
次のファイルを、文体・見出し・HTML の観点で検査してください。
指摘は「行番号・観点・直し方」の形で返してください。
ファイルは書き換えないでください。
  1. 返ってきた指摘を、そのままテキストに保存します。件数、行番号の有無、観点の網羅、直し方の具体性を、あとで数えられる形にしておきます。
  2. .claude/skills/article-check/SKILL.md と README.md を置きます。プロジェクトのルートからの相対パスです。
  3. ハーネスを起動し直すか、Skill を読み込み直します。/article-check <ファイル> で呼べることを確かめます。呼べない場合は、置き場所とファイル名を先に確認します。
  4. 同じ依頼を /article-check で出します。引数は 3 と同じファイルです。
  5. 二つの出力を並べます。比べるのは四つです。指摘の件数。行番号が付いている割合。三つの観点がすべて触れられているか。直し方が、書き換え可能な具体性を持っているか。
  6. 二つの出力から、実際に直す箇所を選びます。直すかどうかは自分で決めます。両方に無い問題を見つけたら、それは Skill の検査項目の不足です。

期待する結果を、例示で書きます。Skill を入れる前は、観点の一部にしか触れず、行番号が付かない指摘が混ざる傾向があります。入れた後は、三つの観点が並び、それぞれに行番号が付く、という形になります。ただし、これは例示です。件数が増えること自体は成果ではありません。同じ指摘を短く返すようになることもあります。

差分を、記録として残す

比べた結果は、二つのファイルと一枚の表で残します。

before.txt   Skill を入れる前の出力
after.txt    Skill を入れた後の出力
compare.md   比較の表

| 観点 | before | after |
| --- | --- | --- |
| 指摘の件数 |  |  |
| 行番号付きの割合 |  |  |
| 触れた観点（3つ中） |  |  |
| 直し方の具体性（3段階） |  |  |

対象：<ファイル>
依頼文：<固定した文面>
モデル：<名前。未確認なら未確認>
実施日：<日付>

モデルの欄は、起動時に表示された値を写します。分からなければ「未確認」と書きます。空欄にすると、あとで見たときに条件が分からなくなります。

コンテキストウィンドウ の使い方も、ついでに観察できます。Skill の説明は毎ターン読まれますが、本文は呼び出したときだけです。/article-check を呼ばずに長い会話を続けたときと、呼んだときで、応答の速さや安定が変わるかを見ておくと、Skill を増やすときの判断材料になります。ただし、体感で分かる差ではありません。数値として測るなら、同じ依頼を複数回出して平均を取る必要があります。この記事では、そこまでは求めません。

失敗した場合

呼んでも動かないときは、置き場所から見ます。プロジェクトの Skill は .claude/skills/<skill-name>/SKILL.md です。ディレクトリ名と frontmatter の name が食い違っていると、呼び出し名が分かりにくくなります。

/article-check が候補に出ないときは、disable-model-invocation: true が効いているかを確認します。この欄があると、モデルからは呼べず、人が呼ぶだけになります。補完の候補に出ない場合は、それ自体が原因のことがあります。

指摘が毎回違う形で返るなら、SKILL.md の「返す形式」が曖昧です。三つの要素を箇条書きで列挙し、該当なしの場合の書き方まで指定します。出力の形は、観点の数より効きます。

観点が多すぎて、重要な指摘が埋もれる場合は、項目を減らします。10 項目の検査は、たいてい 3 項目より使われません。最初は三つに絞り、使ってみて足りないものを足します。

ファイルを書き換えてしまう場合は、allowed-tools を確認します。書き込み系の道具が入っていないか、シェルの実行が入っていないか。Hook で PreToolUse を止める方法もありますが、この演習ではそこまで進みません。

評価

五つの観点で点検します。SKILL.md が 500 行未満に収まっているか。許可した道具が読み取りだけか。返す形式が、行番号・観点・直し方の三つに決まっているか。README に「何をしないか」と限界が書かれているか。そして、比べた条件（対象・依頼文・モデル）が記録に残っているか。

書き直しが要るのは、次の状態です。修正まで一つの Skill に任せた。検査項目を思いつくままに 20 個並べた。出力の形式を指定せず、件数だけを比べた。どれも、結果を読めない検査になります。

できあがるもの

手元に残るのは、SKILL.md と README.md、そして比較の表一枚です。この三つがあれば、検査項目を増やすときも、別のプロジェクトへ移すときも、同じ手順で確かめられます。

Skill は、作るより手入れのほうが長く続きます。使わなくなった項目を消し、見落としが続く観点を足す。README の更新日を変える。その繰り返しが、レビューの質を上げます。

次の段階は、作業そのものを分ける話です。計画と実行を分ける、調査と実装とレビューを別のエージェントに持たせる、並列に走らせる。ここで作った検査の Skill は、レビュー役に渡す指示としても使えます。第30章で扱います。

製品ごとの対応状況はAI図鑑の比較ページで並べられます。Skill やフックの対応は製品で差があるので、図鑑の値と公式ページの確認日を必ず突き合わせてください。
