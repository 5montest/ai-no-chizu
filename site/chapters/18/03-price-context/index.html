第18章 モデル比較と選び方

価格・文脈長・速度で選ぶ

トークン単価の読み方、文脈長とコストの関係、レイテンシの内訳を整理し、条件付きの比較表をどう使うかを説明する。

3行の要点

  • 価格は入力と出力で別々に決まり、出力のほうが高いことが多い。利用量の見積もりは両方を分けて計算する。
  • 文脈長は「入れられる量」であり、長く入れれば品質が上がるわけでも、費用が同じでもない。
  • 速度は初回応答（TTFT）と生成速度に分かれる。体感は用途によって変わる。

モデル選びでは、品質の話に注目が集まりがちです。しかし実際の運用では、価格・文脈長・速度が導入の可否を決めることが少なくありません。ここでは、この三つをどう読み、どう比べるかを整理します。

価格は「入力」と「出力」で別

APIの料金は、通常、100万トークンあたりの単価で示されます。入力と出力で単価が違い、出力のほうが高いのが一般的です。

たとえば、入力 $2／出力 $10（100万トークンあたり）のモデルで、次の処理を考えます。

  • 入力：会話履歴と資料で 2,000トークン
  • 出力：回答で 500トークン
  • 1回あたり：2,000 × 2/1,000,000 + 500 × 10/1,000,000 = 0.004 + 0.005 = $0.009

1回では小さく見えても、1日1万回なら約 $90 です。入力の量と出力の量を分けて、月間で積むことが基本です。

さらに、次の要素で実際の請求は変わります。

  • キャッシュ。同じ前置きを再利用すると、入力料金が下がる場合がある。
  • バッチ。即時性を犠牲にすると、割引が適用される場合がある。
  • 為替。ドル建ての料金が、円換算で変動する。
  • 失敗と再試行。やり直しの分も課金される。

見積もりには、余裕を持たせます。

文脈長は「入れられる量」

コンテキスト長は、一度に扱えるトークン数の上限です。100万トークンと聞くと、大量の資料をそのまま入れられそうに思えます。しかし、次の点に注意します。

  1. コスト。入れた分だけ入力トークンが増える。毎回全文を入れると高くつく。
  2. 速度。入力が長いほど、最初の応答までの時間が伸びる。
  3. 品質。長い文脈の中央にある情報が使われにくいことがある。
  4. 上限は「保証」ではない。公称の長さと、実用上の安定して扱える長さは別。

長い資料を扱う場合でも、検索で必要な部分に絞る、要約してから渡す、章ごとに分けて処理するといった設計のほうが、費用と品質の両面で有利なことが多いです。

速度は二つに分ける

体感速度は、一つの数字では表せません。

  • TTFT（Time to First Token）。リクエストから最初のトークンが出るまで。入力の処理時間を含む。
  • 生成速度（tokens per second）。最初のトークン以降、1秒あたりに出る量。

短い回答を大量に返す用途では、TTFTが体感を支配します。長い文章を生成する用途では、生成速度が効きます。ストリーミング表示なら、TTFTが短いほど「動き出した」感覚が早くなります。

また、速度は負荷で変わります。同じモデルでも、時間帯やリクエスト量によって遅くなることがあります。ベンチマークの速度は、自分の利用条件での速度とは限りません。

  • 入力単価は $0.10〜$10、出力単価は $0.42〜$50 の範囲に広がっている。
  • コンテキスト長は 50万〜約105万トークンで、モデルによる差がある。
  • オープンウェイトのモデルは、価格帯が低めの傾向がある。
  • 同じ提供元でも、上位・バランス・軽量で単価が大きく違う。

一方、この表からは言えないこともあります。

  • どのモデルが最も優れているか。この表は能力を測っていない。
  • 実際の請求額。キャッシュ、バッチ、為替、再試行で変わる。
  • 自分の用途での品質。代表タスクで試す必要がある。

この表に順位はありません。安い順に並んでいますが、安さは品質の代理指標ではありません。

よくある誤解

「コンテキストが最大のモデルを選べば、長文も安心」とは限りません。上限が大きくても、長文の中央の情報を使いにくい、入力コストが膨らむ、応答が遅くなるといった問題があります。長文処理は、検索・要約・分割を含めた設計で解くものです。

オープンウェイトという選択肢

重みが公開されているモデルは、自前の環境で動かせます。次の利点があります。

  • データを外に出さない。機密情報を扱える。
  • 固定できる。モデルの更新に左右されず、再現性を保てる。
  • カスタマイズ。ファインチューニングや量子化ができる。

一方で、次のコストがかかります。

  • ハードウェア。GPUメモリ（VRAM）が必要。モデルサイズと量子化で変わる。
  • 運用。推論サーバー、監視、スケーリング、セキュリティ。
  • 品質の確認。量子化で品質が変わる場合がある。

「APIが安いから自前」ではなく、総所有コストで比べます。利用量が少ないうちは、APIのほうが安く済むことが多いです。

深掘りKVキャッシュと長文のコスト

文章生成では、過去のトークンに対応するKeyとValueを計算し、再利用します。これをKVキャッシュと呼びます。長い文脈では、このキャッシュがメモリを圧迫し、同時に処理できるリクエスト数を減らします。

PagedAttentionなどの技術は、キャッシュをページ単位で管理し、メモリの断片化を減らします。長文対応の性能は、モデルのコンテキスト長だけでなく、こうした推論基盤の効率にも左右されます。

選定の順序

実務での選定手順は、次のとおりです。

  1. 制約を書き出す。予算、許容遅延、データの扱い、必要な入出力。
  2. 候補を絞る。制約を満たさないモデルを落とす。
  3. 代表タスクで試す。同じプロンプト、同じ採点で比べる。
  4. コストを積む。入力・出力・再試行を含めて月間で見積もる。
  5. 運用を確認する。レート制限、障害時の代替、ログ、監視。
  6. 定期的に見直す。価格とモデルは変わる。確認日を記録する。

単一の「最強」を探すのではなく、条件に合う組み合わせを設計する。それが、この章の結論です。

ここまでで、モデルを選び、動かすための基礎を見ました。次は、評価と安全な運用を、より深く扱います。モデルはどう選ぶのかの章トップから、他のページも確認できます。
