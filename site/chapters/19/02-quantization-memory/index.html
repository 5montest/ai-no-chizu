精度を落として載せる

量子化の考え方と品質への影響、VRAM と RAM の違い、メモリ帯域が生成速度の上限になる条件、容量不足の対処を扱う。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 量子化は、重みを表すバイト数を減らし、少ないメモリでもモデルを載せられるようにする工夫である。誤差は用途で目立ち方が異なる。
  • 1トークン生成するたびに重みを読み出す。Dense モデルを小バッチで動かすと、生成速度の上限は計算力よりもメモリ帯域で決まりやすい。
  • VRAM は速いが狭く、RAM は広いが遅い。モデルが VRAM に収まらない部分は遅れの原因になる。

「配布ページの説明では動かせるはずなのに、手元では生成がゆっくりでがっかりした。量子化を試したが、品質がどう変わったのか自信がない」。前ページで見たとおり、配布される重みは小数の数字の並びであり、その保存精度を選べます。このページでは、精度を落とす量子化という工夫とその代償、そしてローカル環境で生成速度がメモリ帯域で決まりやすい条件を扱います。

量子化は重みの分解能を下げる

重みは小数点以下を持つ連続的な値の並びです。1パラメータを数バイトで表すと、全体はすぐに大きくなります。量子化は、重みをより少ないバイト数で表す操作です。

  • 重みが取り得る値を、限られた数の刻みに限定する。
  • 各重みは、自分に最も近い刻みへ丸められる。
  • 1パラメータあたりのバイト数が減り、重み全体の容量が下がる。

連続的な値を粗い刻みで表すため、本来の値との差が必ず生じます。1つの重みに対するずれは小さいものの、数十億の重みで積み重なるため、出力の傾向に影響が現れないとは言い切れません。

影響は一様ではありません。数学的な推論や細かい指示への追従では失敗が増えることがあり、一方で日常的な会話や要約では、差がほとんど感じられないこともあります。どの精度でどのような品質になるかは、モデルと用途の組み合わせごとに異なります。だからこそ判定は、配布ページの評判ではなく、自分の代表タスクで確かめることになります。18章で述べた「代表タスクで試す」は、量子化の精度選びでも同じです。

生成速度を制約するのは何か

前ページで一度触れた通り、推論には入力全体を読み込む工程（prefill）と、1トークンずつ出力を続ける工程（decode）があります。手元で「遅い」と感じやすいのは、後者です。

decode では、1トークンを出すたびに、モデルの重みを読み出して計算します。この読み出しが速度の上限になるのは、次の条件がそろったときです。

  • モデルの形：すべての重みを毎回使う Dense モデルであること。一部の専門家だけを使う MoE では事情が変わります。
  • バッチの大きさ：1人分ずつ処理する小バッチであること。まとめて処理すると、1回の読み出しを複数のリクエストで共有できます。
  • 律速の位置：演算よりも、メモリからの読み出しが先に詰まっていること。

この条件のもとでは、目安として次の式が使えます。あくまで上限に近い粗い見積もりで、実際の速度はこれより低くなります。

生成速度（トークン/秒）≲ メモリ帯域（バイト/秒）÷ 1トークンあたりに読む重み（バイト）

具体的な数字で確かめます。70億パラメータのモデルを 4bit（1パラメータあたり 0.5 バイト）で保存すると、重みはおよそ 3.5GB です。メモリ帯域が毎秒 50GB の環境なら、50 ÷ 3.5 ≒ 14 トークン/秒が上限の目安になります。同じモデルを 16bit（1パラメータあたり 2 バイト）で動かすと重みは 14GB になり、上限は 50 ÷ 14 ≒ 3.6 トークン/秒まで下がります。計算装置は同じでも、読む量が 4 倍になれば、上限は 4 分の 1 です。

実際には、KVキャッシュの読み書きや処理の切れ目などの分だけ遅くなるため、実測値はこの上限より低くなります。それでも、速度の見通しを立てる順番としては役に立ちます。

この式から、量子化が速度にも効く理由が説明できます。1パラメータあたりのバイト数が減れば、読み込む重みの量が減ります。帯域を変えられなくても、読み込む量の側を減らせば速度は上がります。

ただし、容量の削減は確実でも、速度の改善は条件つきです。低いビット幅を計算装置が効率よく扱えるかは、演算の実装（カーネル）とデバイスに左右されます。4bit の重みを読み出しても、計算のたびに変換が挟まれば、その分の負担が加わります。対応する実装がない環境では、容量だけが減って速度は変わらないこともあります。

Dense と MoE では読む量が違う

ここまでの説明は、Dense モデルを前提にしています。最近の大きなモデルには、MoE（Mixture of Experts）を採用したものも少なくありません。MoE は、モデル内部に複数の専門家（エキスパート）を用意し、トークンごとにその一部だけを使う構造です。

この構造では、二つの数字を分けて考える必要があります。

  • 総パラメータ数：モデル全体が持つ重みの合計。必要な常駐メモリの目安になる。
  • 活性パラメータ数：1トークンの計算で実際に使う重みの数。トークンあたりの演算量と読み出し量の目安になる。

たとえば「総パラメータ 470 億、活性パラメータ 130 億」という構成なら、メモリには 470 億個分の重みを置く必要がありますが、1トークンの計算で読むのは、その一部です。Dense の 470 億パラメータモデルと同じ速さにはならず、メモリの必要量も Dense の 130 億パラメータモデルより大きくなります。

つまり、MoE は「容量は総パラメータ、速度は活性パラメータ」という、ねじれた性質を持ちます。カタログのパラメータ数だけを見て、速さや必要メモリを推測すると外れます。どちらの数字が書かれているかを確かめるのが先です。

帯域以外に速度へ効く要素

帯域の式は単純ですが、実際の速度はほかの要素でも動きます。どれも「速くなる」と一概には言えず、条件次第です。

  • KVキャッシュ：文脈が長くなるほど大きくなり、メモリ容量を圧迫します。読み書きの量も増えるため、長い文脈では帯域の式から外れやすくなります。
  • バッチング：複数のリクエストをまとめると、1回の重み読み出しを共有でき、全体の処理量あたりの速度は上がります。ただし1人分の応答が速くなるわけではなく、待ち時間は伸びることがあります。
  • メモリ階層とキャッシュ：CPU のキャッシュや GPU の内蔵メモリなど、帯域の違う階層があります。何度も読む小さなデータは上位の階層に載りますが、モデルの重みは大きすぎて載りきりません。
  • GPU へのオフロード：重みの一部を GPU に置くと、その部分は速くなります。置けない部分は CPU 側に残り、層をまたぐたびに受け渡しが発生します。

「量子化すれば速くなる」も、この表の一部です。読み出しが律速で、ほかの要素が詰まっていなければ、バイト数が半分になれば速度はおよそ2倍まで近づきます。逆に演算が律速だったり、オフロードで受け渡しが増えたりすると、効果は小さくなります。

VRAM と RAM は別の資源である

PC の中のメモリは一種類ではなく、GPU を積んだ一般的な構成では、LLMの動作に主に次の二つが関わります。

  • VRAM：GPU に近い位置にある専用メモリ。読み出しが速く、並列計算にも向くが、容量は狭い。
  • RAM：PC 本体のメモリ。総容量は大きいが、読み出しは VRAM に比べて遅い。

この構成では、モデル全体がVRAMに収まるかどうかが体験を左右します。収まる場合は、GPU の速さで計算が進みます。収まらない場合、重みの一部がRAMに置かれ、必要になるたびに読み出しが加わります。動きはするものの、RAM側に置かれた部分に関わる処理で遅れが生じます。

ただし、この二分法が当てはまらない構成もあります。Apple Silicon のように CPU と GPU が同じメモリを共有するユニファイドメモリ方式では、VRAM という区画が独立しておらず、広いメモリを GPU からも使えます。その代わり、帯域はその共有メモリ全体で分け合うことになります。「VRAMに載るか」ではなく「共有メモリの帯域と容量で足りるか」で見る必要があります。

つまり、VRAMに載る割合が高いほど、生成速度の期待値も上がります。逆に言えば、配布ページの数字とは別に、自分の環境でどのくらいの割合がVRAMに載るかを確認するのが、速度見通しの基本です。実際の速度は、1秒あたりの出力トークン数（tokens per second）として測定します。

よくある誤解

「量子化すれば、品質はまったく変わらない」とは言い切れません。量子化は重みの表現精度を下げるため、元の値との誤差が必ず発生します。誤差の出方は用途によって異なり、ある用途では気にならなくても、別の用途では目立つことがあります。精度を上げ下げした前後で、同じ代表タスクを比較することが、確実な確認手順です。

CPU・GPU・NPU の役割分担

メモリと並んで考えるべきなのが、重みを読み込んで計算を進める装置の種類です。

計算装置得意な点留意する点
CPU対応が広く、特別な部品が不要並列性が低く、帯域も中程度
GPU並列計算が速く、帯域も高い容量が狭く、載りきるかが壁になる
NPU低消費電力で推論に向いた設計対応するソフトや形式が限られる

実際の環境では、一つの装置だけでなく、組み合わせで動くことが多いです。重みの一部をGPUに置き、残りをCPUやNPUが担う構成も取れます。ただし装置が分かれると、装置間でデータを受け渡す分だけ調整が複雑になり、速度の見通しが立てにくくなります。まずは一つの装置で収まる構成から始め、必要が出てきたら分担を検討するのが手堅いです。

メモリが足りないときに起こること

必要なメモリ量が環境を超えると、次のような挙動になります。

  • 起動が失敗する。メモリ不足が原因という旨のエラーが出ることが多い。
  • 動作するが、重みの一部がRAMに置かれ、生成が遅くなる。
  • KVキャッシュの領域が確保できず、文脈を長く取れない。

軽めの介入として、次の方法があります。どれも品質や速度との折り合いを見ながら選びます。

  1. 文脈の長さを短くする。文脈に必要な領域が減る。
  2. 出力の長さを限る。処理中に保持される量が減る。
  3. 量子化の精度を下げる。重み本体の容量が減る。

どれも単純な操作ですが、品質と速度の実測を確認して選びます。配布ページの数字よりも、自分のタスクでの実感を記録に残すほうが、後の判断に役立つ知見になります。

深掘り速度の見積もりにKVキャッシュを含める

生成速度の指標として「メモリ帯域 ÷ 重みの容量」という式で考えるとき、分母に入れる量は重み本体だけではありません。長い文脈を保つKVキャッシュや、演算の作業領域も、同時に読み書きされます。したがって、正確な見込みは、重みの量とKVキャッシュの量を合わせて、帯域と引き比べる形になります。

とはいえ、文脈が短くバッチが小さいあいだは、decode 工程で重みの読み出しが支配的だとされ、重みの量を基準にした見積もりが使えます。ただし文脈が長くなるほどKVキャッシュの比率が高まり、重みだけの見積もりから外れやすくなります。MoE のモデルでは、分母を総パラメータではなく、1トークンで実際に読む活性パラメータ側に置き換えて考える必要があります。

重みの保存精度、メモリの仕組み、計算装置の分担が見えました。次は、同じ重みでも、動かすソフトの選択によって速度や使い勝手が変わる理由を見ます。動かすソフトを選ぶへ進みましょう。
