精度を落として載せる

量子化の考え方と品質への影響、VRAM と RAM の違い、メモリ帯域が生成速度を決める理由、容量不足の対処を扱う。

3行の要点

  • 量子化は、重みを表すバイト数を減らし、少ないメモリでもモデルを載せられるようにする工夫である。誤差は用途で目立ち方が異なる。
  • 1トークン生成するたびに重み全体を読む。生成速度の上限は、計算力よりもメモリからの読み出し速さで決まりやすい。
  • VRAM は速いが狭く、RAM は広いが遅い。モデルが VRAM に収まらない部分は遅れの原因になる。

「配布ページの説明では動かせるはずなのに、手元では生成がゆっくりでがっかりした。量子化を試したが、品質がどう変わったのか自信がない」。前ページで見たとおり、配布される重みは小数の数字の並びであり、その保存精度を選べます。このページでは、精度を落とす量子化という工夫とその代償、そしてローカル環境の生成速度がメモリ帯域で決まる理由を扱います。

量子化は重みの分解能を下げる

重みは小数点以下を持つ連続的な値の並びです。1パラメータを数バイトで表すと、全体はすぐに大きくなります。量子化は、重みをより少ないバイト数で表す操作です。

  • 重みが取り得る値を、限られた数の刻みに限定する。
  • 各重みは、自分に最も近い刻みへ丸められる。
  • 1パラメータあたりのバイト数が減り、重み全体の容量が下がる。

連続的な値を粗い刻みで表すため、本来の値との差が必ず生じます。1つの重みに対するずれは小さいものの、数十億の重みで積み重なるため、出力の傾向に影響が現れないとは言い切れません。

影響は一様ではありません。数学的な推論や細かい指示への追従では失敗が増えることがあり、一方で日常的な会話や要約では、差がほとんど感じられないこともあります。どの精度でどのような品質になるかは、モデルと用途の組み合わせごとに異なります。だからこそ判定は、配布ページの評判ではなく、自分の代表タスクで確かめることになります。18章で述べた「代表タスクで試す」は、量子化の精度選びでも同じです。

生成速度はメモリ帯域で決まりやすい

前ページで一度触れた通り、推論には入力全体を読み込む工程（prefill）と、1トークンずつ出力を続ける工程（decode）があります。手元で「遅い」と感じやすいのは、後者です。

decode では、1トークンを出すたびに、モデルの重み全体を一度読み込みます。出力が数百トークンなら、この読み込みが数百回続きます。ここで制約になるのが、1秒間にメモリからどれだけの量を読み出せるか、というメモリ帯域の指標です。

  • 計算装置が速くても、重みの読み出しが追いつかなければ、生成は待たされる。
  • 読み込む重みの量が大きいほど、1トークンあたりの時間が長くなる。

目安は、大まかに次の式で考えられます。

生成速度（トークン/秒）≒ メモリ帯域 ÷ 重みの容量（バイト数）

実装や環境で差はあるものの、重要なのは、生成速度の上限が計算力よりも先に読み出しの速さで決まる場合が多いことです。GPU を使っても計算能力が全開にならないことがあるのは、このためです。

この式から、量子化が速度にも効く理由が説明できます。1パラメータあたりのバイト数が減れば、読み込む重みの量が減ります。帯域を変えられなくても、読み込む量の側を減らせば速度は上がります。容量の節約と速度の改善が、同じ操作で同時に達成されます。

VRAM と RAM は別の資源である

PC の中のメモリは一種類ではなく、LLMの動作には主に次の二つが関わります。

  • VRAM：GPU に近い位置にあるメモリ。読み出しが速く、並列計算にも向くが、容量は狭い。
  • RAM：PC 本体のメモリ。総容量は大きいが、読み出しは VRAM に比べて遅い。

ローカルLLMの体験を左右するのは、モデル全体がVRAMに収まるかどうかです。収まる場合は、GPU の速さで計算が進みます。収まらない場合、重みの一部がRAMに置かれ、必要になるたびに読み出しが加わります。動きはするものの、RAM側に置かれた部分に関わる処理で遅れが生じます。

つまり、VRAMに載る割合が高いほど、生成速度の期待値も上がります。逆に言えば、配布ページの数字とは別に、自分の環境でどのくらいの割合がVRAMに載るかを確認するのが、速度見通しの基本です。実際の速度は、1秒あたりの出力トークン数（tokens per second）として測定します。

よくある誤解

「量子化すれば、品質はまったく変わらない」とは言い切れません。量子化は重みの表現精度を下げるため、元の値との誤差が必ず発生します。誤差の出方は用途によって異なり、ある用途では気にならなくても、別の用途では目立つことがあります。精度を上げ下げした前後で、同じ代表タスクを比較することが、確実な確認手順です。

CPU・GPU・NPU の役割分担

メモリと並んで考えるべきなのが、重みを読み込んで計算を進める装置の種類です。

計算装置得意な点留意する点
CPU対応が広く、特別な部品が不要並列性が低く、帯域も中程度
GPU並列計算が速く、帯域も高い容量が狭く、載りきるかが壁になる
NPU低消費電力で推論に向いた設計対応するソフトや形式が限られる

実際の環境では、一つの装置だけでなく、組み合わせで動くことが多いです。重みの一部をGPUに置き、残りをCPUやNPUが担う構成も取れます。ただし装置が分かれると、装置間でデータを受け渡す分だけ調整が複雑になり、速度の見通しが立てにくくなります。まずは一つの装置で収まる構成から始め、必要が出てきたら分担を検討するのが手堅いです。

メモリが足りないときに起こること

必要なメモリ量が環境を超えると、次のような挙動になります。

  • 起動が失敗する。メモリ不足が原因という旨のエラーが出ることが多い。
  • 動作するが、重みの一部がRAMに置かれ、生成が遅くなる。
  • KVキャッシュの領域が確保できず、文脈を長く取れない。

軽めの介入として、次の方法があります。どれも品質や速度との折り合いを見ながら選びます。

  1. 文脈の長さを短くする。文脈に必要な領域が減る。
  2. 出力の長さを限る。処理中に保持される量が減る。
  3. 量子化の精度を下げる。重み本体の容量が減る。

どれも単純な操作ですが、品質と速度の実測を確認して選びます。配布ページの数字よりも、自分のタスクでの実感を記録に残すほうが、後の判断に役立つ知見になります。

深掘り速度の見積もりにKVキャッシュを含める

生成速度の指標として「メモリ帯域 ÷ 重みの容量」という式で考えるとき、分母に入れる量は重み本体だけではありません。長い文脈を保つKVキャッシュや、演算の作業領域も、同時に読み書きされます。したがって、正確な見込みは、重みの量とKVキャッシュの量を合わせて、帯域と引き比べる形になります。

とはいえ、decode 工程では重みの読み出しが支配的だとされ、手元の見込みとしては重みの量を基準にするのが合理的です。ただし文脈が長くなるほどKVキャッシュの比率が高まり、重みだけの見積もりから外れやすくなる点には注意が必要です。

重みの保存精度、メモリの仕組み、計算装置の分担が見えました。次は、同じ重みでも、動かすソフトの選択によって速度や使い勝手が変わる理由を見ます。動かすソフトを選ぶへ進みましょう。
