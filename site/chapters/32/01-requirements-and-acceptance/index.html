第32章 製品を完成させる

製品にする前に、受け入れ条件を決める

「動いた」と「完成した」の間には、確かめた項目の一覧があります。条件を先に書き、テストの名前に落とし、通った条件と通らない条件を分けて残すところまでを扱います。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 受け入れ条件は、実装より先に、確かめ方と一組で書く。確かめ方が書けない条件は、まだ条件になっていない。
  • 判定の良し悪しは、人が書いた質問集で測る。よくある質問・境目の質問・意地の悪い質問の三種を混ぜる。
  • 条件はテストの名前に落とし、通った件数を残す。テストで表せない条件には、grep のような別の確かめ方を明記する。

第23章から第31章まで、道具を一つずつ見てきました。モデルの選び方、料金の読み方、端末からの使い方、指示の書き方、音声の扱い方。どれも単体では小さな部品です。この章では、それを一つの製品の形にまとめます。

題材は、社内の設備についての質問に答える小さな窓口です。会議室の予約、備品の場所、故障の連絡。そういう質問に対して、答えられるものは答え、答えられないものは人に回す。この題材を選んだ理由は三つあります。データを自分で書けること、正解を自分で決められること、そして外したときに何が起きるかを想像しやすいことです。

この記事の目標は、コードを書く前に「何ができていれば完成か」を決め、その条件をテストの名前まで落とせるようになることです。前提は、端末でコマンドを一つ実行できることだけです。第27章の CLI の読み方と、第29章の道具の分け方が分かっていれば、なお読みやすいでしょう。使うのは Node.js の標準のテストランナーで、追加のインストールは要りません。演習用のアプリは 設備ヘルプデスク に置いてあります。

図は、問い合わせ対応で人が送信前に確認する流れの一例です。この章で作る部分は、その手前にある「答えられる質問か、人に回すか」の振り分けで、語の一致と点差という単純な規則で決めます。生成モデルは使いません。

完成の定義を、コードより先に書く

作り始めるとき、いちばん危ないのは「動いた」で満足することです。質問を投げたら答えらしいものが返ってきた。それだけでは、何ができていて何ができていないか分かりません。別の質問を投げたら的外れな答えが返るかもしれません。答えを出してはいけない質問に、自信を持って答えてしまうかもしれません。

答えらしい文が返ってきたとき、見るべきなのは、その文が手元の資料に基づいているかどうかです。もっともらしい文が根拠から離れて出てくることを ハルシネーション と呼びます。この章の演習アプリは、モデルに文を作らせず、資料の本文をそのまま返す形にしました。作らせない仕組みにすれば、この種類の誤りは起きません。

このアプリを、ここではルールベースの版と呼びます。語の一致と点数の計算だけで行き先を決め、生成モデルは呼びません。生成AIにつないだ版は、同じ FAQ データと同じ受け入れ条件を使う、別の実装として扱います。つないだ場合に変わるのは、返す文の作り方、費用、そして同じ質問でも結果が変わりうるという性質です。この章に出てくる件数と費用は、ルールベースの版で測ったものです。二つを混ぜると、何を測った数字なのかが分からなくなります。

だから、コードより先に条件を書きます。条件とは「こうなっていたら完成」という文で、同時に「どうやって確かめるか」が決まっている文です。外部の評価の解説でも、評価を早く、何度も行うことが最初に挙げられています。日本語にすれば、作る前に測り方を決めておけ、ということになります。

この演習では、条件を十一つ書きました。多すぎるように見えますが、一つひとつは短い文です。たとえば「答えると決めたときは、本文と出典を返す」「単価が未入力のあいだ、費用は数値ではなく未設定として扱う」。どれも、実装を見なくても当てはまるかどうかを判断できます。

判断できない条件は、条件になりません。「使いやすいこと」「自然な答えを返すこと」では、通ったかどうかが人によって変わります。そういう言葉を書きそうになったら、その下に「何を見れば分かるか」を一行足します。「自然な答え」なら「評価用の質問集のうち、何件が期待どおりの行き先になるか」に置き換わります。

受け入れ条件は、確かめ方と一組で書く

条件を書くときは、表にします。左に条件、右に確かめ方。この形にすると、書いている途中で「これは確かめられない」と気づけます。

演習アプリの表から、六つを抜き出します。全体は ACCEPTANCE.md に十一行あります。

#受け入れ条件確かめ方
A-1質問に対して、答える・人に回す・答えないのどれかを必ず返すすべての質問に理由が付くことをテストで見る
A-2答えると決めたときは、本文と出典を返す本文の長さと、出典の文字列を見る
A-3答えない・人に回すと決めたときは、本文を返さず、連絡先を返す本文が空であることと、連絡先の文字列を見る
A-4機微な語を含む質問は、どれだけ当たっていても人に回す機微な語を含む質問を投げる
A-7単価が未入力のあいだ、費用は数値ではなく未設定として扱う費用が null であることをテストで固定する
A-8外部へ通信しない。APIキーを持たない呼び出しの文字列を grep で探す（テストではない）

A-1 が最初に来ているのは、これが製品の性格を決めるからです。答えられないときに黙る製品は、使う人から見ると壊れています。三つの行き先のどれかを必ず返し、その理由も返す。この形にすると、あとから「なぜこの答えになったか」を画面にも記録にも出せます。

A-8 だけは、書き方が違います。通信の不在は、動きのテストでは表せません。テストを一つ書いても、書かなかった通信の経路は見つかりません。だから確かめ方を「呼び出しの文字列を探す」にしました。実際に検索すると、出てくるのは同じフォルダのファイルを読む二件だけで、外部のホスト名は一つもありません。

この違いは、表の中で分けて書きます。テストで確かめた条件と、目で確かめた条件を混ぜると、あとから「どこまで保証されているのか」が分からなくなります。条件の数より、確かめ方の種類が大事です。

人が書いた質問集が、判定の基準になる

条件のうち、いちばん測りにくいのが「答えるべき質問に答え、答えるべきでない質問に答えない」という条件です。これを測るには、質問と期待する行き先の組を、人が書くしかありません。

公開されている ベンチマーク の点数で代用する、という選択は取れません。ベンチマークは共通の課題でモデルを比べるためのもので、自分の社内規程のどこを答えるべきかは測っていません。測っている対象が違えば、点数が高くても、この製品の条件を満たしたことにはなりません。

演習アプリには、FAQ の項目が十二件、評価用の質問が十四件あります。質問集は、三種類を混ぜて書きました。よくある質問、境目の質問、意地の悪い質問です。この三種を混ぜる書き方は、外部の評価の解説にも挙げられています。典型的な例だけを集めると、得意な範囲しか測れません。正解率（Accuracy） を一つの数字にまとめていると、この偏りは見えません。どの質問を落としたのかまで数えると、次にどこを直すかが決まります。

実際に投げた結果は、次のようになりました。これは手元の実行で見た値で、機械や素材が変われば動きます。

質問判定理由
会議室を予約したい答える候補が一つに絞れた（当たり 100%、差 23%）
コピーの紙が詰まった答える候補が一つに絞れた（当たり 78%、差 73%）
給与明細が見たい人に回す機微な語を含む（給与）ため、自動回答しない
経費の締め切りは？答えない質問の語のうち当たったのが 14%（下限 50%）

二行目と四行目に注目してください。コピーの質問は、当たりの割合が 78% で、一位と二位の差が 73% あります。経費の質問は、当たりが 14% しかありません。どちらも「点が低いから答えない」ではなく、別の理由で振り分けられています。条件を先に書いていなければ、この違いに気づかず、点の高さだけで判定する実装にしていたはずです。

質問集は、条件を書いた人が書きます。実装した人が自分の実装に合わせて質問を選ぶと、通る質問だけが集まります。この演習では、質問集を先に書き、あとから実装を合わせました。合わなかった箇所は、実装ではなく質問集の側を直しました。期待する行き先の書き間違いが見つかったためです。

条件を、テストの名前に落とす

条件は、そのままでは実行できません。実行できる形にしたものがテストです。Node.js の標準のテストランナーなら、追加の道具を入れずに書けます。ファイル名を *.test.mjs にしておき、node --test "test/*.test.mjs" でまとめて実行します。

条件とテストの対応は、名前で分かるようにします。条件の文を、ほぼそのままテストの名前にするのがこつです。

// test/acceptance.test.mjs から、条件 A-2 に対応する部分
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('答えるときは、本文と出典を返す', () => {
  const result = engine.ask('会議室を予約したい');
  assert.equal(result.route, 'answer');
  assert.equal(result.entry.id, 'room-booking');
  assert.match(result.text, /出典：/);   // 本文だけ返して、根拠を落としていないか
  assert.ok(result.text.length > 20);    // 空に近い文字列で通していないか
});

このテストは、四つのことを同時に見ています。行き先が答えるであること。選んだ項目が期待どおりであること。本文に出典が付いていること。本文が実質的に空でないこと。条件を一文で書いておくと、テストに何を見せるかが自然に決まります。

実行すると、三十九件が通ります。内訳は、文字の処理が七件、検索と順位づけが六件、振り分けが十一件、費用が六件、受け入れが九件です。件数そのものに意味はありませんが、どの層にテストが多いかは、どこを気にしているかの表れです。この演習では、振り分けにいちばん多く置きました。誤ると利用者に直接影響するのが、そこだからです。

テストは、条件ごとに一件とは限りません。A-4 の「機微な語を含む質問は人に回す」には、二件を置きました。一件は判定の結果を見るもの、もう一件は機微な語の一覧そのものを見るものです。前者だけだと、語の一覧から一語が消えても、たまたまその語を使わない質問だけで通ってしまいます。

うまくいかないときの見方

テストが通らないとき、最初に見るのは条件の側か、実装の側かです。条件の文が曖昧だと、テストが実装の都合で書かれます。「それらしい答えを返す」を通すために、文字列の長さだけを見るテストが生まれます。そうなったら、条件の文に戻ってください。

条件が多すぎて、どれも中途半端になっていることもあります。十一の条件のうち、公開に必須なのはどれか。この演習では、A-1 から A-4 までと A-7、A-8 を必須にしました。残りは、あったほうがよい条件です。必須と任意を分けておくと、時間が足りないときに削る場所が決まります。

評価用の質問集が、実装に合わせて書き換わっていることもあります。期待する行き先を、実装が出した行き先に合わせて直すのは、条件を捨てたのと同じです。直してよいのは、質問の書き方の誤りと、期待の書き間違いだけです。判定そのものを変えるなら、条件を書き直し、その理由を残します。

試す人向け演習・記入例と確認の観点

演習：自分の題材で、条件を六つ書く

自分の身の回りにある題材で、同じ表を作ります。社内文書の検索でも、問い合わせの仕分けでも、議事録の要約でも構いません。データを自分で用意できて、正解を自分で決められるものが適しています。

  1. 題材を一文で書く。「誰の、どの質問に、何を返すか」の形にする。
  2. 条件を六つ書く。うち一つは「返してはいけないときの動き」にする。
  3. 六つのそれぞれに、確かめ方を書く。テストで見るのか、目で見るのか、検索で見るのかを分ける。
  4. 評価用の質問を十件書く。よくある質問を六件、境目の質問を二件、意地の悪い質問を二件。
  5. 質問ごとに、期待する行き先を先に書く。実装はまだ書かない。
  6. 六つの条件のうち、公開に必須なものを三つ選ぶ。選んだ理由を一行ずつ添える。

期待する結果は、条件の表が先に埋まり、質問集の期待値が先に決まることです。この時点で実装が無くても、表は完成します。実装が始まってから表を埋めようとすると、条件が実装に引っ張られます。

この記事の演習では、自分でアプリを実装するところまでは求めていません。 手元で試したのは、この章の演習アプリに対してで、自分の題材での実装は未実機確認です。条件の書き方と、テストへの落とし方だけを持ち帰ってください。

評価

五つの観点で点検します。条件が実装より先に書かれているか。条件のそれぞれに、確かめ方が付いているか。テストで確かめた条件と、そうでない条件が分かれているか。評価用の質問集に、三種類の質問が混ざっているか。そして、期待する行き先を、実装を見る前に書いたか。

書き直しが要るのは、次の状態です。「使いやすいこと」のような、確かめ方の決まらない語だけで条件を書いた。テストの名前が、条件ではなく実装の関数名になっている。通信や秘密情報の条件を、テストが無いという理由で表から消した。質問集を、実装が通った質問だけに絞った。どれも、あとから同じ判断ができない記録です。

できあがるもの

手元に残るのは、条件の表、評価用の質問集、そして条件とテスト名の対応です。この三つがあると、次に何を作るときも同じ順番で進められます。条件を書き、質問集を作り、テストに落とす。実装は、そのあとです。

次の記事では、この条件に向かって実際に組み立てます。判定の順番をどう決めるか、どこで誤りを止めるか、通ったテストをどう残すか。条件が先にあるので、実装の判断は「条件を満たすか」の一点に絞られます。
