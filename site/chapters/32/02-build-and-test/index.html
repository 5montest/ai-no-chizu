第32章 製品を完成させる

先に、答えない道を作る

判定の順番を決めると、製品の性格が決まります。機微な語・当たりゼロ・下限という順に早期に止める実装を、設定ファイルとテストと一緒に作ります。

3行の要点

  • 判定の順番を先に固定する。機微な語、当たりゼロ、当たりの下限、点差の下限、そして答える。順番が挙動を決める。
  • 下限は設定ファイルに置き、コードに埋めない。値の出どころを変えずに、厳しさだけを変えられる。
  • 直して精度が上がるはずの変更でも、評価用の質問が一つ落ちたら戻す。戻した理由を弱点として書き残す。

前の記事で、条件の表と評価用の質問集を作りました。この記事では、その条件に向かって実装します。題材は同じ、設備についての質問に答える窓口です。

実装で最初に決めたのは、判定の順番でした。何をどの順で見るかが決まっていないと、条件を満たしているかどうかを、あとから確かめられません。順番を決めるというのは、製品の性格を決めることでもあります。同じデータと同じ点数でも、順番が違えば、答えたり答えなかったりします。

使うのは Node.js だけで、外部のモデルは呼びません。RAG（検索拡張生成） の考え方のうち、検索して候補を絞るところだけを、小さく作りました。本物の RAG（検索拡張生成） は、埋め込みと生成モデルを使います。この演習でそれを省いたのは、判定を測りやすくするためです。モデルを挟むと、同じ質問でも返る文が毎回変わります。変わらない部品で先に骨格を作り、あとからモデルを差し込む順にします。

順番を決めると、挙動が決まる

判定は五段です。上から順に見て、当たったところで止めます。

1. 機微な語を含むか        → 人に回す
2. 語が一つも当たらないか  → 答えない
3. 当たりの割合が下限未満か → 答えない
4. 一位と二位の点差が下限未満か → 人に回す
5. ここまで来たら          → 答える

一段目が、この製品の性格を決めています。返金、支払、契約、給与、個人情報、事故。こうした語を含む質問は、候補がどれだけ良く当たっていても自動では答えません。人が受け取ります。

順番を変えると何が起きるかを、一度は自分で確かめてください。たとえば点差の判定を一段目に移すと、給与の質問が「よく当たったので答える」経路に入ります。評価用の質問集では、この変更で一件が落ちます。落ちることをテストで固定してあるので、順番を入れ替えた瞬間に気づけます。

コードでは、早期に返す形にします。条件が増えても、読む順が一直線に保てます。

// lib/routing.mjs から、判定の骨格だけを抜き出す
export function decide(query, ranked, config) {
  const { min_coverage: minCoverage, min_margin: minMargin } = config.retrieval;

  const hits = sensitiveHits(query);
  if (hits.length > 0) {
    return { route: 'escalate', reason: `機微な語を含む（${hits.join('、')}）ため、自動回答しない`, hits };
  }

  if (!ranked.top || ranked.top.score === 0) {
    return { route: 'refuse', reason: '手がかりになる語が一つも当たらない', hits };
  }

  if (ranked.coverage < minCoverage) {
    return { route: 'refuse', reason: `質問の語のうち当たったのが ${Math.round(ranked.coverage * 100)}%（下限 ${Math.round(minCoverage * 100)}%）`, hits };
  }

  if (ranked.margin < minMargin) {
    return { route: 'escalate', reason: `一位と二位の差が ${Math.round(ranked.margin * 100)}%（下限 ${Math.round(minMargin * 100)}%）`, hits };
  }

  return { route: 'answer', reason: `候補が一つに絞れた（当たり ${Math.round(ranked.coverage * 100)}%、差 ${Math.round(ranked.margin * 100)}%）`, hits };
}

理由の文を、返り値に必ず入れていることにも意味があります。条件 A-1 が「どれかを必ず返す」だけでなく「理由も返す」形になっているのは、このためです。画面にも記録にも、なぜその判定になったかを出せます。人が受け取ったときに、最初に見るのもこの文です。

判定に使う値は、設定ファイルに置く

下限の二つは、コードに書きません。config.json に置きます。

{ "retrieval": { "min_coverage": 0.5, "min_margin": 0.15 } }

min_coverage は、質問の語のうち一位の項目に当たった割合の下限です。min_margin は、一位と二位の点差を一位の点で割った値の下限です。どちらも、厳しくすれば人に回る件数が増え、緩めれば自動で答える件数が増えます。

設定ファイルに置く理由は、二つあります。一つは、厳しさを変えるたびにコードを触らなくて済むこと。もう一つは、テストで「値がコードに埋まっていないこと」を確かめられることです。埋まっていると、設定を変えたつもりで変わらない事故が起きます。

外に出すと、値を間違える危険も出ます。この演習では、項目が欠けていれば起動した時点で止まります。欠けた値を既定値で補う形にはしていません。黙って既定値で動くと、厳しくしたつもりの設定が効いていないことに気づけないからです。

ただし、値の範囲は検査していません。0.5 と書くところを 0.05 と書いても、そのまま動きます。範囲を検査するなら、設定の読み込みに一件、テストを足すことになります。この演習では、そこまで作っていません（未実装）。

誤りは、二種類に分けて扱う

この窓口の誤りは、二つに分かれます。答えるべき質問に答えない誤りと、答えるべきでない質問に答えてしまう誤りです。

前者は、使う人に手間をかけます。もう一度聞くか、人に連絡するか。後者は、間違った情報を、正しい情報と同じ見た目で渡します。ハルシネーション と同じ性質の問題で、しかもこの場合は「それらしい文」ではなく「社内の規程の本文」が出てきます。読み手は、それが正しいと受け取りやすくなります。

だから、この演習では後者を強く避ける形にしました。その代わり、前者は増えています。前の記事で見た「会議室の鍵」が人に回るのは、その表れです。答えられたはずの質問を落としているので、正解率（Accuracy） だけを見れば損をしています。それでも、規程の本文を誤って出さないことを優先しました。

この判断が正しいかどうかは、題材によって変わります。設備の案内なら、人に回す手間は小さく、誤った本文の害は大きい。雑談の相手なら、答えないことのほうが害になります。自分の題材で、どちらの誤りが重いかを先に決めてください。 この記事は、その判断を代わりにはしません。

回帰テストは、直した跡に置く

実装を進めるなかで、語の切り方を変える実験をしました。2文字の組だけでなく、1文字の語も索引に載せる変更です。「鍵」だけの質問にも当たるようになるので、精度は上がるはずでした。

結果は逆でした。「会議室を予約したい」の点差が下限を割り、答えるはずの質問が人に回るようになりました。1文字の語が多くの項目に当たり、点数が薄く広がったためです。実験は戻しました。戻したあと、この割り切りは弱点として README に書きました。コードのコメントにも、同じ理由を残しています。

こういうとき、評価用の質問集が無いと判断できません。「精度が上がるはず」という予想は、たいてい当たりません。合否で比べる形にしておくと、変更の前後で一件ずつ数えられます。外部の評価の解説にも、合否や一対比較のほうが順位づけより安定すると書かれています。この演習の行き先は三つですが、評価の場面では「期待どおりか、そうでないか」の二つに潰して数えています。

同じ質問に同じ答えが返ることも、テストで固定しました。乱数を使っていないので、二度投げても判定も文面も変わりません。これが崩れると、テストの結果が実行のたびに変わります。テストが不安定になると、落ちたときに実装のせいか運のせいか分からなくなります。

実行結果は、手元で次のようになりました。

ℹ tests 39
ℹ pass 39
ℹ fail 0

内訳は、文字の処理が七件、検索と順位づけが六件、振り分けが十一件、費用が六件、受け入れが九件です。ファイルごとにテストを分けておくと、どこを壊したかが名前で分かります。Node.js のテストランナーは、ファイルごとに別の子プロセスで動かすので、片方の失敗がもう片方の状態に影響しません。

画面でも、同じ判定になること

端末から使う形と、ブラウザで使う形の二つを作りました。判定の理屈は lib/ にだけ置き、両方から同じ関数を呼びます。画面側に判定を書き写すと、片方だけ直したときに食い違います。

ブラウザで実際に確かめた結果です。1280×900 の画面で、四つの行き先がすべて出ることを見ました。

質問画面の判定画面の理由
会議室を予約したい答える候補が一つに絞れた（当たり 100%、差 23%）
給与明細が見たい人に回す機微な語を含む（給与）ため、自動回答しない
経費の締め切りは？答えない質問の語のうち当たったのが 14%（下限 50%）
会議室の鍵人に回す一位と二位の差が 0%（下限 15%）

色だけで区別しないようにしました。判定は色付きの枠で囲みますが、必ず「答える」「人に回す」「答えない」の文字を添えます。色が見分けにくい人にも、白黒で印刷した場合にも、判定が読めます。

画面の広さを 390×844 に変えても、横スクロールは出ませんでした。入力欄とボタンは縦に積まれ、どちらも幅いっぱいになります。コンソールのエラーは 0件、外部へのリクエストも 0件でした。この二つは、画面を作るときに必ず数えてください。エラーは見えないところで出ていることがあり、外部へのリクエストは、意図しない送信の証拠になります。

端末からの実行結果も、同じ判定でした。

$ node cli.mjs "会議室の鍵"
質問: 会議室の鍵
判定: 人に回す（escalate）
理由: 一位と二位の差が 0%（下限 15%）
候補: room-booking:7.27（次点 temperature:7.27、room-no-show:4.62）

この質問は自動では答えません。設備担当（内線 2100） へ連絡してください。

「次点」まで出しているのは、判定が際どいときに、どこで並んだかを見るためです。点数は、索引の語がいくつ当たったかを足しただけの値で、確率ではありません。0 から 100 の間に収まる値でも、そう読める形にはしていません。

うまくいかないときの見方

答えが出ないときは、まず語の切り方を見ます。日本語は語の区切りが無いので、この演習では2文字の組で索引を作っています。1文字の語は載りません。「鍵」「紙」「椅」のような一文字の名詞だけで聞かれると、当たりません。

判定が荒いときは、下限の二つを入れ替えて比べます。当たりの下限を上げると、答えない件数が増えます。点差の下限を上げると、人に回す件数が増えます。どちらを動かすと、どの誤りが減るかを、評価用の質問集で数えてください。体感で決めると、次に同じ判断ができません。

画面と端末で判定が違うなら、判定をどちらかに書き写しています。共通の関数を呼んでいるか、呼び出しの引数が同じかを確かめてください。設定ファイルを片方だけ読んでいる、という形の食い違いもよくあります。

テストが一件だけ落ちるなら、そのテストが条件のどれに対応するかを先に見ます。対応が分からないテストは、条件ではなく実装の都合で書かれたテストです。条件の表に戻って、確かめ方を書き直してください。

演習：判定の順番を入れ替えて、何が起きるか見る

演習アプリの写しを手元に置き、判定の順番を一つ入れ替えます。

  1. lib/routing.mjs を開き、機微な語の判定を、点差の判定のあとへ移す。
  2. node --test "test/*.test.mjs" を実行し、落ちるテストの名前を記録する。
  3. node cli.mjs "給与明細が見たい" を実行し、判定と理由を記録する。
  4. 変更を戻し、もう一度テストを実行する。
  5. 落ちたテストが、条件のどれに対応していたかを、ACCEPTANCE.md の表で確かめる。
  6. 順番を入れ替えたまま公開した場合に、どんな質問で何が起きるかを、三行で書く。

期待する結果は、機微な語のテストが落ち、給与の質問が「答える」に変わることです。理由の文も変わります。実際に試すのは自分の写しに対してで、公開版のファイルは書き換えないでください。 この演習は手元で実行していない箇所があるため、変更の結果がこの記事の記述どおりになるかは、自分の環境で確かめてください（未確認）。

評価

五つの観点で点検します。判定の順番が、コードを読まなくても説明できるか。答えてはいけない条件が、いちばん先にあるか。下限の値が設定ファイルにあり、読み込み時に検査されているか。評価用の質問集で、変更の前後を数えたか。そして、画面と端末で同じ判定になることを、実際に確かめたか。

書き直しが要るのは、次の状態です。順番が関数の並び順で決まっていて、意図を説明できない。下限がコードの中に三か所、別々の値で書いてある。評価用の質問を、実装が通ったものだけに絞った。画面側にも判定を書き写した。どれも、次に直すときに同じ判断ができない形です。

できあがるもの

手元に残るのは、判定の順番、設定ファイル、評価用の質問集で通った件数、そして弱点の一覧です。弱点を書いてあることが、この成果物のいちばん大事な部分かもしれません。できないことを書いておくと、次の変更で何を壊してはいけないかが分かります。

次の記事では、この製品を公開する前に見る項目を扱います。費用の出し方、ライセンスの書き方、そして「確かめていないこと」の残し方です。動くものはできましたが、公開できるかどうかは、まだ決まっていません。
