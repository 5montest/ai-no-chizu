第28章 ハーネス比較

ハーネスを、測れる観点で比べる

モデルが同じでも、ハーネスが違えば手順も失敗の仕方も変わります。比べる観点を八つに決め、公式ドキュメントで確認できた範囲だけを表にします。

3行の要点

  • モデルの性能とハーネスの使い勝手は別の軸で、同じ表の同じ列に並べると差が読めなくなる。
  • 比較の観点を八つに決め、公式ドキュメントで確認できた欄だけを埋め、残りは「未確認」と書く。
  • 同じモデルに固定できない組み合わせは、性能の優劣ではなく、制約つきの観察記録として扱う。

第27章で三つの CLI を触り、変更の検収まで通しました。ここからは「どれを使うか」を決める段階です。ところが、比較の話はたいてい混ざります。モデルの賢さ、料金、画面の使いやすさが一枚の表に並び、どの差が結果に効いたのか分からなくなります。

この記事の目的は、順位を付けることではありません。比べる前に観点を決め、確認できた事実だけを表に残す型を作ることです。順位は、その型で何度か記録したあとに、自分の条件の範囲でだけ言えるものです。

モデルとハーネスは、別の欄に書く

ハーネス は、モデルを呼び出して作業を進める側の道具です。同じモデルを載せ替えても、道具が変われば、指示の組み立て、道具の実行、コンテキストウィンドウ の扱い、許可の求め方、記録の残り方が変わります。エージェントループ の一回りをどこで切るかも違ってきます。

だから「Claude Code と GPT はどちらが賢いか」は、問いとして成立しません。層が違うからです。Claude Code は Anthropic のハーネスで、動かすモデルは --model で選ぶ Claude のモデルです。Codex CLI は OpenAI のハーネスで、/model で OpenAI のモデルを選びます。Codex はハーネスの名前で、モデル名ではありません。同じように、Claude Code はハーネス、Claude はモデルの系列です。

比較表の列は、ハーネス名にします。モデル名は、その隣の別の欄に書きます。

この記事で確認できた範囲

2026-10-28 に取得した公式ドキュメントは、Claude Code の概要と CLI リファレンス、Codex CLI のページ、OpenCode の入門ページです。この記事の表には、そこに書かれていることだけを入れます。

三つとも、このサイトの作成環境では動かしていません。つまり未実機確認です。表の内容は各社の公式記述にもとづきますが、あなたの環境での表示や所要時間とは一致しないことがあります。

Pi、Hermes、DeepSeek Harness については、公式ページを特定・取得できませんでした。そのため、この記事では機能を書きません。名前だけを並べて「たぶんこうだろう」と補うと、表全体の信用が落ちます。確認できた時点で追加します。

料金もこの記事では扱いません。料金は単位と通貨と確認日がそろわないと比べられないため、第25章とAI図鑑に分けて記録しています。

比べる観点は、八つ

観点は多いほどよいわけではありません。自分の環境で一回触れば埋まるかどうかで選びます。

  • モデルの選び方：どのモデルを、どこで切り替えるか。
  • 作業指示ファイル：毎回読ませる指示を、どのファイルに書くか。
  • 権限と承認：何を許すかを、どこで決めるか。
  • コンテキストの圧縮：会話が長くなったとき、何を残して何を捨てるか。
  • 拡張：Skills、Hooks、プラグイン、MCP（Model Context Protocol） サーバーのような追加の仕組み。
  • セッションの再開：前回の続きを、どう開くか。
  • 実行ログ：何をしたかの記録が、どこに残り、どう読めるか。
  • 画面：ターミナル以外に、どの入口があるか。

ベンチマークの点数を先に見たくなりますが、点数は条件を揃えないと読めません。この八つは、条件を揃えにくい代わりに、一回の利用でも埋まるかどうかが分かります。まずここを埋め、点数は条件を揃えられたときにだけ足します。

八つの観点で、三つを並べる

確認できた範囲で表にすると、次のようになります。

空欄を作らなかったことに意味があります。同じ規模の表を、三つとも「たぶん」で埋めると、見た目は揃いますが、判断には使えません。

未確認は、できないという意味ではない

表の「未確認」は、三つのどれでもありません。機能が無いという確認でも、使えないという評価でもなく、そのページを読んだ範囲では書かれていなかったという意味です。だから、あとで別のページを読めば変わる欄です。

記録では、次の三つを区別します。

  • 確認して「ある」と書ける：公式の記述を引用できる。
  • 確認して「無い」と書ける：公式に、その機能を持たないと読める記述がある（多くはありません）。
  • 未確認：記述が見つからない、またはページを取得できていない。

図鑑でも同じ区別を使っています。確認できていない値を 0 として扱うと、料金の計算や絞り込みが静かに狂います。表でも同じで、空欄を 0 や「なし」で埋めた時点で、あとから誤りを見つけにくくなります。

同じモデルに固定できないなら、性能比較と呼ばない

ハーネスを公平に比べる方法は、同じモデルを載せて同じ依頼を出すことです。ところが、今回の三つではそれができません。Claude Code は Claude のモデル、Codex CLI は OpenAI のモデルを前提にしています。OpenCode は提供元を選べますが、その提供元の一覧と対応モデルは入門ページでは確認できていません。

つまり、三つを並べた表から言えるのは「機能の有無と入口の違い」までです。「こちらのほうが仕事が速い」「こちらのほうが正確だ」は、この表からは言えません。

同じモデルに固定できない場合は、次のように書きます。同じモデルに固定できないため、これは性能比較ではなく、条件つきの観察である。そのうえで、条件（日時、ハーネスの版、モデル名、依頼文、許可した内容）を記録します。条件を書いてあれば、読む人は自分の環境との差を判断できます。

数字より先に、手間を数える

成功率は一回では測れません。同じ依頼を何度も出さないと、ばらつきと実力の区別が付かないからです。個人が試す範囲では、回数を増やすより、手間を数えるほうが現実的です。数えられるものは四つあります。

開始までの手間：導入から最初の依頼までの手順数と、詰まった箇所。インストール、サインイン、作業ディレクトリの指定、最初の許可までを、手順の数として書きます。

確認回数：許可を求められた回数と、その中身。回数が多いほど悪いとは限りません。書き込みの許可を求める回数と、読み取りの許可を求める回数を分けて数えると、設計の違いが見えます。

テスト実行：依頼の中にテストを含めたか、自分で走らせたか、走らせたコマンドと結果。ここは「通りました」ではなく、コマンドと出力で記録します。

エラー回復：失敗したときに、何をすれば戻せたか。同じ失敗を二度繰り返したか、一度で立て直せたか。回数として書けるので、一回の実験でも記録が残ります。

Sandbox の制約で通信が止められ、依存の取得に失敗する場合があります。これはハーネスの不出来ではなく、既定の設計です。失敗として数える前に、何が止められたのかを確かめます。

演習：一つ選んで、八つの欄を埋める

第27章の練習用リポジトリを使います。まだ作っていない場合は、三つのCLIを、同じ手順で試すの演習を先に済ませてください。

  1. すでに入っているハーネスを一つ選びます。三つ入れる必要はありません。
  2. 八つの観点を、メモの表に書き出します。欄は空けないで、分からない欄には「未確認」と書きます。
  3. 起動して、次の四つを実際に試します。--model か /model でモデルを表示する。作業指示ファイルの名前を確認する。権限の設定画面を開く。セッションを一度終了して、再開する。
  4. 詰まった箇所を、手順の番号と一緒に書きます。「サインインで止まった」ではなく「手順3で、ブラウザが開かず、表示された URL を手で開いた」のように書きます。
  5. 公式ページを開き、自分の表と食い違う欄を探します。食い違ったら、公式の記述と取得日を優先します。

期待する結果は、八つの欄のうち五つ以上が確認済みで、残りが「未確認」と理由つきで埋まっている状態です。八つ全部が埋まる必要はありません。埋まらなかった欄と、その理由が残っていることが成果です。

うまくいかないときの切り分けは、第27章と同じです。コマンドが見つからない場合は、新しいターミナルで PATH を反映させます。権限の画面が見つからない場合は、/help か公式のコマンド一覧で名前を確認します。名前が分からないまま勘で打つと、別の機能を触って記録が混ざります。

評価

四つの観点で点検します。観点ごとに欄があり、確認済みと未確認が区別されているか。モデル名とハーネス名が別の欄に書かれているか。未確認の欄に、参照したページと取得日が添えられているか。そして、表から「どちらが優れているか」を結論していないか。

書き直しが要るのは、次の状態です。確認していない欄を「なし」で埋めた。モデル名をハーネスの列に書いた。一回の結果から順位を付けた。どれも、あとで自分の記録を読み返したときに、何が事実だったのか分からなくなります。

できあがるもの

手元に残るのは、八つの観点で埋めた一枚の表と、詰まった箇所の記録です。この表は、次の記事でそのまま使います。

次の記事では、同じ依頼を二つのハーネスに出し、進み方を記録して評価表にまとめます。比較実験ログと評価表を作るへ進んでください。製品ごとの記録はAI図鑑の個別ページにもあり、比較ページで三つを並べられます。図鑑の値と自分の表が食い違ったら、確認日を比べて新しいほうを採ります。
