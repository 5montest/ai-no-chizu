第28章 ハーネス比較

同じ変更を2種類のハーネスに依頼して比較する

無害な演習リポジトリを一つ固定し、機械で判定できる課題を2つのハーネスに出します。条件をそろえ、実測した値だけを記録し、差分パッチと実験ログを残します。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 演習用のリポジトリを一つ作り、README の追記を小さなテストで機械的に判定できるようにする。
  • 比較は「モデルまで固定したハーネス差」と「各製品の標準構成どうし」の2本立てにし、ログの列で区別する。
  • 記録は harness-experiment-log.md と差分パッチで残す。別の人が同じ手順を再現できる状態を完成とする。

ここまでの3記事で、比べる観点、記録の列、製品の実名がそろいました。この記事では、実際に手を動かします。同じ依頼を2つのハーネスに出し、記録と差分パッチを残します。

使うのは、この演習のために作る害のないリポジトリです。本番のリポジトリや、秘密情報の入ったフォルダでは行わないでください。有料 API を新たに契約する必要もありません。すでに使える契約の範囲で、2回ずつ実行します。

演習用のリポジトリと、記録の置き場所を分ける

最初に、変更の対象と判定方法を固定します。判定が機械で決まれば、「なんとなく良さそう」という評価を排除できます。同時に、Git で管理する演習用リポジトリと、実験の記録を置くフォルダを分けます。記録をリポジトリの中に作ると、未追跡ファイルとして差分の判定に混ざるためです。

mkdir -p ~/harness-work/harness-lab/test
mkdir -p ~/harness-work/runs ~/harness-work/results/patches
cd ~/harness-work/harness-lab
git init

できあがる形は、次のとおりです。

harness-work/
├── harness-lab/         # Git 管理。README.md と test/readme.test.mjs
├── runs/                # 試行ごとの worktree（開始コミットに固定）
│   ├── harness-a-1/
│   └── harness-a-2/
└── results/             # Git 管理の外。記録とパッチ
    ├── environment.md
    ├── read-only-audit-a-1.txt
    ├── harness-experiment-log.md
    └── patches/

README.md を次の内容で作ります。

# 演習用リポジトリ

このリポジトリは、ハーネスの比較実験だけで使います。

test/readme.test.mjs を作ります。Node.js の組み込みテストだけで動くので、追加のパッケージは要りません。

import test from 'node:test';
import assert from 'node:assert/strict';
import { readFile } from 'node:fs/promises';

const readme = await readFile(new URL('../README.md', import.meta.url), 'utf8');

test('README に「使い方」の見出しがある', () => {
  assert.match(readme, /^## 使い方$/m);
});

test('「使い方」の節に手順が3つ以上ある', () => {
  const section = readme.split(/^## /m).find((part) => part.startsWith('使い方'));
  assert.ok(section, '「使い方」の節が見つからない');
  const steps = section.split('\n').filter((line) => /^\d+\. /.test(line));
  assert.ok(steps.length >= 3, `手順が ${steps.length} 件しかない`);
});

この状態で、テストが失敗することを先に確かめます。

node --test "test/*.test.mjs"

手元の環境（Node.js v24.22.1）では、2件とも失敗し、ℹ pass 0 と ℹ fail 2 が出ました。ここで失敗するのが正しい状態です。テストが最初から通る土台では、ハーネスが何をしたのか判定できません。node --test の引数の扱いが版によって違う場合は、引数なしの node --test でも同じファイルが見つかります。

失敗を確認したら、コミットします。このコミットが、すべての試行が共通で始める土台です。Git の名前とメールを設定していない環境では、コミットの前に git config --global user.name と user.email を確認してください。設定しないままではコミットできません。

git add README.md test/readme.test.mjs
git commit -m "演習用リポジトリの初期状態"
BASE=$(git rev-parse HEAD)
git log --oneline -1

表示されたハッシュを、あとでログに写します。

試行ごとに、同じ開始地点から始める

同じ作業ディレクトリで git restore README.md を繰り返すと、未追跡のまま残ったログやパッチが次回に影響します。git restore が戻すのは追跡済みファイルの変更だけで、新しく作られたファイルは消えません。試行を重ねるほど、前回の残り物が結果に混ざります。

そこで、試行ごとに Git の worktree を作り、毎回同じ開始コミットから始めます。worktree は、同じリポジトリの履歴を共有したまま、別のディレクトリに作業ツリーを用意する仕組みです。

cd ~/harness-work/harness-lab
git worktree add --detach ../runs/harness-a-1 "$BASE"
git -C ../runs/harness-a-1 status --porcelain --untracked-files=all

--detach は、ブランチを作らずに開始コミットへ固定する指定です。最後のコマンドが何も表示しなければ、開始地点はきれいです。--untracked-files=all を付けるのが要点です。git diff も git diff --stat も、追跡されていない新規ファイルは表示しません。追跡済みの変更だけを見て「差分なし」と判断すると、ハーネスが作ったファイルを見落とします。

2回目以降の試行も、同じ $BASE から新しいディレクトリを作ります。1つのディレクトリを使い回して git restore で戻す方式は、この演習では使いません。

最初は編集を許さず、環境を記録する

いきなり編集を許さず、まず調査だけの実行をします。この段階の目的は、変更をさせることではなく、環境を記録することと、追跡対象・未追跡のどちらにも変更が入らないことを確かめることです。

environment.md は、演習用リポジトリの外、~/harness-work/results/ に作ります。リポジトリの中に作ると、そのファイル自体が未追跡ファイルとして git status に現れ、「変更が無い」という判定と区別できなくなります。項目は次のとおりです。

# 実行環境

- OS と版：
- ハーネスの正式名と版（--version などで確認した値）：
- モデル ID：
- 提供元：
- 認証の方法（サブスクリプション / API キー / クラウドの認証）：
- 権限モードまたは承認の設定：
- 作業ディレクトリ（試行用の worktree のパス）：
- 開始コミット：
- 試行の番号（例：harness-a-1）：
- 確認日：

空欄は残さず、「未確認」と書きます。版とモデルは、起動時の表示をそのまま写します。

編集を止める設定は、製品ごとに入口が違います。 ここで大事なのは、承認を求めるモードと、書き込みそのものを止める仕組みを混同しないことです。

  • Claude Code：Manual（設定値 default）は、読み取りをそのまま実行し、書き込み・多くのコマンド・通信の前に許可を求めるモードです。許可すれば書き込めるため、読み取り専用ではありません。調査だけにしたいときは Plan モード（--permission-mode plan）を使います。ただし、編集が止まるだけで、シェルコマンドまで自動で止まるわけではありません。書き込みを確実に止めるには、サンドボックスや権限の設定で範囲を切ります。公式は、権限の設定とサンドボックスを、補い合う2つの層として説明しています。
  • Codex CLI：/permissions で、確認なしに許す範囲と書き込み可能なディレクトリを確認できます。読み取りだけにするなら、--sandbox read-only を指定します。これはサンドボックスの制限で、承認の設定とは別の仕組みです。
  • OpenCode：エージェント設定の permission で、read / edit / bash などを許可・確認・拒否に分けます。
  • Pi：ツール呼び出しのたびに確認を求めず、ツールと拡張は Pi のプロセスと同じ OS 権限で動きます。読み取りだけにしたい場合は、コンテナや別ユーザーなど、OS 側の隔離で書き込みを止めます。

依頼文に「編集しないでください」と書くだけでは、強制力のある制限になりません。制限は、権限の設定か実行環境の側に置きます。

.env と本番用の設定ファイルには、触らせません。権限の設定に拒否の規則を足すか、演習用ディレクトリの外を読めないサンドボックスで動かします。規則の書式は製品ごとに違うので、その製品の権限のページで確認してください。

読み取りの実行が終わったら、追跡対象と未追跡の両方に変更が入っていないことを確かめます。

git -C ~/harness-work/runs/harness-a-1 status --porcelain --untracked-files=all

何も表示されなければ、開始地点から何も増えていません。この結果を results/read-only-audit-a-1.txt に、実行した日時、ハーネス、実行した依頼、git status --porcelain --untracked-files=all の出力（空だったという事実）と一緒に書きます。何か表示された場合は、変更内容を確認してこの試行を「範囲外の変更」として記録し、その worktree は捨てて、新しい worktree を作り直します。git restore で消して続けると、消し残しが次の判定に混ざります。

読み取りでも外に出る

読み取りだけの実行でも、モデルの推論が外部 API なら、読ませた内容は送られます。演習用リポジトリには、秘密情報も顧客情報も入れないでください。ローカル実行かどうかと、データが外に出るかどうかは別です。

比べる前に、条件を五つ決める

実験の前に、次の五つを決めてファイルに書きます。実行のたびに変えると、結果を並べられません。

決めることこの演習での決め方
開始コミットgit rev-parse HEAD の値。すべての試行で同じ
依頼文下の四行に受け入れ条件を足したもの。一字も変えずに貼る
評価条件テスト2件が通る。変更が README.md だけ。未追跡ファイルを含めて他の差分が無い
タイムアウト1回あたり10分。過ぎたら中断し、その時点の状態を記録する
繰り返し回数各ハーネス2回。難しければ1回に減らし、減らしたことを書く

依頼文は次の形です。

目的：README に「使い方」の節を一つ足したい。
変更してよいファイル：README.md だけ。
変えないこと：他のファイル、既存の見出し、既存の文。
確認方法：`node --test "test/*.test.mjs"` を実行し、結果を示すこと。

受け入れ条件は、評価条件と同じ内容を依頼文にも書きます。ハーネスは依頼文しか読みません。評価条件を別のファイルに置いて「読んでいるはず」と期待すると、条件が伝わっていない実験になります。

タイムアウトは、開始から検収の終わりまでを測ります。10分は目安です。長い依頼を試すときは延ばしますが、両方のハーネスで同じ値にします。

比較は2本立てにする

ここが、この演習で最も間違えやすい点です。比べ方は2つあり、混ぜると何の差か言えなくなります。

A. ハーネス差の実験。 モデルと提供元まで、可能な範囲で固定します。同じモデルを2つのハーネスに接続できるかを、先に確かめます。OpenCode と Pi のように、複数の提供元や互換エンドポイントを選べる組み合わせでは成立しやすいです。Claude Code と Codex CLI のように、標準の接続先が異なる組み合わせでは、同じモデルに固定できないことがあります。固定できない場合は、A 実験に使わず、B 実験だけにします。

B. 利用体験の実験。 各製品の標準構成をそのまま使います。既定のモデル、既定の権限、既定の指示ファイルの扱いまで含めて、いつもの使い方で比べます。こちらは「その製品を導入すると、自分の作業がどう進むか」を見る実験です。

ログには、必ず実験の種類の列を作ります。A の行と B の行を同じ表に並べると、モデルの差とハーネスの差が混ざります。

記録する13項目

1回の実行につき1行を残します。項目は次の13です。

項目書き方
使用モデル ID画面に出た値をそのまま。エイリアスならエイリアスと書く
版--version などで確認した値
OSOS 名と版
認証サブスクリプション、API キー、クラウドの認証のどれか
確認回数許可を求められた回数。内容も一行で
ツール回数ファイル読み取り、検索、コマンド実行の回数。数えられなければ未測定
実行秒数開始から検収の終わりまで
成功テスト数ℹ pass の値
差分git diff --stat の行数と、触ったファイル。未追跡ファイルは git status --porcelain --untracked-files=all から数える
ロールバック戻したか、戻していないか。戻した方法
トークン画面や記録に出た合計。出なければ未測定
キャッシュキャッシュの利用が分かれば書く。分からなければ未測定
実質課金・枠消費契約の画面で確認できた値。確認できなければ未測定

ツール回数とトークン数は、製品によっては画面に出ません。出ない値を推定で埋めると、あとで実測値と区別できなくなります。未測定と書いてください。

確認回数は、読み取りの許可と書き込みの許可を分けて数えると、設計の違いが見えます。合計だけを書くと、どちらを多く聞かれたのか分かりません。

実行して、差分を取る

  1. 試行用の worktree を作り、そのディレクトリでハーネスを起動します。environment.md の項目を確認します。
  2. 調査だけの依頼を出し、git status --porcelain --untracked-files=all が空であることを確かめます。
  3. 依頼文をそのまま貼ります。開始時刻をメモします。
  4. 許可を求められたら内容を読み、何を許したかを書きます。断った場合も理由を書きます。
  5. 終わったら、テストを自分で実行します。ハーネスの「通りました」ではなく、自分の端末の出力を写します。
  6. 差分を確認します。git diff --stat -- README.md だけでなく、git status --porcelain --untracked-files=all も見ます。追跡済みの変更と、新しく増えたファイルの両方が、README.md だけかを確かめます。
  7. 結果を results/ に保存します。パッチは追跡済みの変更だけを写します。
R=~/harness-work/runs/harness-a-1
git -C "$R" status --porcelain --untracked-files=all > ~/harness-work/results/harness-a-1-status.txt
git -C "$R" diff -- README.md > ~/harness-work/results/patches/harness-a-1.patch
( cd "$R" && node --test "test/*.test.mjs" ) > ~/harness-work/results/harness-a-1-test.txt 2>&1
  1. 次の試行は、同じ $BASE から新しい worktree を作って始めます。前の worktree は、記録とパッチを保存したあと git worktree remove で片付けます。~/harness-work/harness-lab の作業ツリーには触れません。
  2. 2つ目のハーネスでも 1〜8 を繰り返します。同じ日に続けて行うと、条件がそろいやすくなります。

期待する成果物は、results/ に置く4つです。environment.md、read-only-audit-a-1.txt、harness-experiment-log.md、patches/ の差分パッチ。README の変更は、次のとおりです。

--- a/README.md
+++ b/README.md
@@ -1,3 +1,9 @@
 # 演習用リポジトリ
 
 このリポジトリは、ハーネスの比較実験だけで使います。
+
+## 使い方
+
+1. ターミナルでこのフォルダを開きます。
+2. `node --test "test/*.test.mjs"` を実行します。
+3. 失敗が0件なら、変更は受け入れ条件を満たしています。

この差分を当てると、テストは2件とも通ります。手元の環境では、ℹ pass 2 と ℹ fail 0 になりました。この確認は、開始コミットから作った別の worktree にパッチを当て、そこでも ℹ pass 2 になることまで確かめています。ハーネスが別の書き方をした場合も、受け入れ条件を満たしていれば合格です。差分が上と一字一句同じである必要はありません。見るのは、テストの結果と、触ったファイルの範囲です。

実測していない値と、二回の結果

2回ずつ実行しても、結果はばらつきます。同じハーネスでも、依頼の解釈、モデルの状態、通信の状況で変わります。2回の結果から性能ランキングを出さないでください。言えるのは「この条件で、こう進んだ」という観察までです。

ランキングの代わりに書くのは、次の3つです。

  • どの条件で、受け入れ条件を満たしたか。
  • どの条件で、詰まったか。詰まった箇所は手順の番号で書く。
  • 次に試すなら、何を変えるか。依頼文、権限、タイムアウトのどれを変えるか。

2回で同じ結果なら、その条件での再現性がある程度見えます。違う結果になったら、その差自体が記録です。差が出た理由を推測で書かず、確認できた事実だけを書きます。

つまずいたときの切り分け

テストが最初から落ちる。 開始コミットが違うか、test/readme.test.mjs が壊れています。git -C "$R" rev-parse HEAD が $BASE と一致するか、git status --porcelain --untracked-files=all が空かを確認します。ずれていたら git restore で直さず、その worktree を捨てて作り直します。

git status に、作った覚えのないファイルが出る。 environment.md やログを演習用リポジトリの中に作っていないかを確認します。記録はすべて ~/harness-work/results/ に置きます。リポジトリ内に残っていたら、results/ へ移してから、worktree を作り直します。

README 以外のファイルに差分が出た。 依頼文の「変更してよいファイル」が伝わっていません。権限の設定で他のファイルの編集を拒否し、依頼文にもう一度書いて試します。この実行は「範囲を超えた」として記録します。失敗として消さないでください。

10分を過ぎた。 中断し、その時点の git status と差分を残します。中断した時刻も書きます。タイムアウトは失敗ではなく、条件つきの結果です。

差分が空のまま終わった。 依頼が届いていないか、編集の許可を断っています。ログの確認回数の欄と、断った理由を見ます。

サンドボックスでコマンドが止まる。 何が止められたかを確認します。依存の取得が止められたのなら、環境の制約であって、ハーネスの評価とは別です。原因を分けて書きます。

費用と利用枠の注意

新しい有料契約は要りません。すでに使える契約の範囲で、2回ずつ実行します。実行の前に、その契約の利用枠と、モデルごとの消費単位を確認してください。最小権限で始めれば、意図しない外部送信も減らせます。

契約がない場合の代替は3つです。過去のログを静的に並べる。模擬の応答を返す小さなスクリプトで手順だけを練習する。公開されているサンプルの記録を読む。どれも練習には使えますが、模擬で動かしたものを実機の実測として扱わないでください。記録の種類の欄に「模擬」と書きます。

常駐させるプロセスは作りません。実験が終わったら、起動したハーネスを終了し、残ったプロセスがないことを確認します。バックグラウンドで動かした場合は、起動した PID を記録し、終了時に回収します。

この演習で分かること、分からないこと

この演習が測るのは、指示追従、許可を求められた回数、差分の範囲、テストを実行したかです。README に節を足してテストを通す課題は、これらを見る入門としては十分ですが、ハーネスの総合的な性能を比べる課題ではありません。

この結果から、長期記憶、自律性、複数エージェントの分担、大きなリポジトリでの調査力の順位は分かりません。分からないものを、分かったことにしないでください。目的が変わったら、課題も評価項目も変えます。

段階課題の例主に評価すること
1：単純な編集README に節を追加し、テスト2件を通す編集範囲、許可の回数、差分、テストの実行
2：不具合の修正失敗するテストを先に用意し、小さな不具合を直す原因の調べ方、失敗からの復旧、テストの質
3：長期の作業中断と再開を挟む変更を、複数回に分けて進めるコンテキストの圧縮、引き継ぎ、進捗の記録
4：分担調査・実装・レビューを別の担当に分けるサブエージェント、チームの統合、衝突の回避

段階を上げると、記録する項目も増えます。段階3なら中断の回数と、再開時に何を渡したか。段階4なら、誰が何を決めたかと、衝突をどう解いたかです。A（モデルまで固定）と B（標準構成）の区別は、どの段階でも保ちます。まだ試していない段階は「未実施」と書きます。

再現チェックリスト

記録が完成したかは、自分以外の人が同じ手順をたどれるかで決まります。次の6つを確認してください。

  1. 開始コミットのハッシュだけで、同じ土台を用意できるか。worktree の作り方まで書かれているか。
  2. 依頼文が省略されずに残っているか。
  3. 評価条件が、実行したコマンドまで書かれているか。
  4. 実行したハーネスの版とモデル ID が書かれているか。
  5. 未測定と未実施が、空欄ではなく言葉で書かれているか。
  6. 差分パッチが patches/ にあり、当てるとテストが通るか。

6番目は、パッチを別の worktree で当てて確かめます。開始コミットから作った新しい worktree なら、記録ファイルの有無に左右されません。

git -C ~/harness-work/harness-lab worktree add --detach ~/harness-work/runs/verify-patch "$BASE"
git -C ~/harness-work/runs/verify-patch apply --check ~/harness-work/results/patches/harness-a-1.patch

--check は、実際には変更せずに当てられるかだけを確認します。エラーが出たら、パッチが古いか、土台が違います。

評価

四つの観点で点検します。五つの条件が記録の先頭にそろっているか。A と B が列で分かれているか。未測定の欄が、推定値で埋まっていないか。そして、2回の結果から順位を付けていないか。

書き直しが要るのは、次の状態です。実験の途中で依頼文を直した。失敗した実行を消した。トークン数の空欄を 0 で埋めた。どれも、記録を読んだ人が同じ実験をやり直せなくなります。

できあがるもの

手元に残るのは、環境の記録、読み取り監査の記録、4行のログ、そして差分パッチです。この4つがそろっていれば、ハーネスを乗り換えるかどうかを、印象ではなく記録で決められます。
