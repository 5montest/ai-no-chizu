第31章 専用モデルの組合せ

三つのモデルを、一本の線につなぐ

書き起こし・生成・読み上げをつなぐと、待ち時間も費用も区間ごとに分かれます。全体の合計ではなく、どこで待っているかを測る形に組み直します。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 音声の入出力は、書き起こし・生成・読み上げの三区間でできている。全体の待ち時間は区間の和になる。
  • 読み上げの音声形式は、遅れを縮めたいなら wav か pcm が推奨されている。pcm はヘッダの無い生データなので、保存するときに扱いが要る。
  • 費用は区間ごとに単位が違う。合計だけを見ると、どの区間を削るべきか分からない。

ここまでの二つの記事で、音声を文字にする方法と、画像を数える方法を扱いました。この記事では、それらをつないで一本の線にします。声を入れて、文字にして、応答を作って、声で返す。この形は、音声アシスタントでも、読み上げ付きの問い合わせ窓口でも、同じ骨格です。

つなぐと分かることがあります。全体の待ち時間は、どこか一つのモデルの速さでは決まりません。三つの区間の和で決まります。費用も同じで、区間ごとに単位が違います。この記事の目的は、合計だけを見る状態から、区間ごとに見る状態に移ることです。

前提は、第31章の前の二記事です。書き起こしの手順と、画像の数え方を押さえてある前提で進みます。用意するのは、自分で録った90秒程度の音声と、その正解の文字起こしです。

この記事は、三つの区間を API でつなぐ形を扱います。手元で書き起こしや読み上げを動かす場合は、速さが機械ごとに変わるので、OS・CPU・GPU・メモリ・使ったモデルと版を区間ごとに記録してください。API を使う場合は、提供元・モデルID・送信先・料金・提供終了予定を、実行した日に確かめて日付と一緒に残します。どちらの記録も、この記事の数値を写しただけでは自分の環境の記録になりません。

つなぐ順番は、ほぼ決まっている

音声を入れて音声を返す構成は、次の順に並びます。

声 → [書き起こし] → 文字 → [生成] → 応答文 → [読み上げ] → 声

区間は三つです。書き起こし、生成、読み上げ。この順番を入れ替えることは、まずありません。文字を経由するかどうかは選べますが、経由したほうが待ち時間を区間ごとに測れます。音声を直接モデルに渡す構成もありますが、その場合、どこで待っているのかが一つの数字に潰れます。

区間の間に、処理を挟めます。書き起こした文字を整える、禁止語を検査する、前の記事の判定モデルに通す。挟むほど待ち時間は増えますが、増えた分がどの区間に載ったかは分かります。分かることが、この構成を選ぶ理由です。

生成の区間は、推論（Inference） の待ち時間がそのまま出ます。長い応答を返させると、読み上げの区間も長くなります。最初の一文だけを早く返して読み上げを始める形にすると、体感の待ちは縮みます。TTFT を測る理由がここにあります。

遅れは、区間ごとに分けて測る

測る前に、表を用意します。空欄のまま作って、実測値だけを後から入れます。

区間何が起きるか測る点実測値
録音の終わり → 送信ファイルの確定と送信送信にかかった時間
書き起こし音声 → 文字最初の文字まで / 最後まで
生成文字 → 応答文最初の トークン まで / 最後まで
読み上げ応答文 → 音声最初の音まで / 最後まで
再生の待ち受け取って鳴らす鳴り始めるまで
合計

書き起こしと生成には、二つの測り方があります。最初の単位が出るまでの時間と、最後まで出るまでの時間です。会話の相手としては、最初の音が出るまでの時間が効きます。全部が出るまでの時間は、聞き終わるまでの長さに効きます。両方を測ってください。

この表で大事なのは、合計の行ではなく、空欄の多い行です。埋められない区間があれば、そこは測っていないという意味です。合計だけを書いて、内訳が空の表は、次に何を直すかを教えてくれません。

測る順番も決めておきます。まず一度、通しで動かして合計を出します。次に、各区間に時刻を打つログを入れて、もう一度動かします。二回目で内訳が出ます。一度目と二度目で合計が大きく違うなら、機械の状態か、ネットワークの状態が変わっています。同じ条件で測り直してください。

手元で合計を出すだけなら、次の計算で足ります。

# budget.py — 区間ごとの秒数から、合計と割合を出す
import sys

# 秒で渡す: 書き起こし, 生成, 読み上げ
stt, gen, tts = (float(v) for v in sys.argv[1:4])
total = stt + gen + tts

print(f'合計 {total:.2f} 秒')
for name, value in (('書き起こし', stt), ('生成', gen), ('読み上げ', tts)):
    share = value / total * 100 if total else 0
    print(f'  {name}: {value:.2f} 秒（{share:.0f}%）')
print(f'1000回で {total * 1000 / 60:.1f} 分')

この記事には、三つの区間をつなぐ実行コードを収録していません。接続の書き方は提供元のSDKと認証の方法で変わり、筆者は通しの実行をしていないためです（未実機確認）。代わりに載せるのが、つないだ結果を測るこの計算です。三つの秒数は、手順どおりに一度ずつ動かして、自分で記録してください。

割合の列が要点です。合計が同じでも、内訳が違えば打つ手が違います。書き起こしが七割を占めるなら音声の長さを削る。読み上げが七割を占めるなら応答文を短くする。合計だけ見ていると、どちらの判断もできません。

読み上げの形式と、声

読み上げは POST /v1/audio/speech で行います。既定の形式は mp3 で、ほかに opus、aac、flac、wav、pcm が選べます。待ち時間を短くしたいときは、wav か pcm が推奨されています。圧縮の処理が入らないぶん、最初の音が早く出ます。

pcm には注意が要ります。中身は 24kHz、16ビット符号付き、リトルエンディアンの生のサンプルで、ヘッダが付いていません。そのままファイルに書いても、多くのプレイヤーは開けません。再生するなら wav を選ぶか、自分でヘッダを付ける処理を入れます。「早い」と「そのまま使える」は別の性質です。

応答は chunked transfer encoding で流れてくるので、全部が届くのを待たずに鳴らし始められます。最初の音までの時間を測るときは、この流れを止めないようにしてください。全部受け取ってから再生する実装にすると、形式を wav にしても待ち時間は縮みません。

ストリーミングに対応していないモデルや、全部を受け取ってから返す形の API では、この値は取れません。その場合は「未対応」または「未測定」と書き、代わりに何を測ったかを添えてください。推定値で空欄を埋めないでください。

声の数は、公式ページの中で数字が合っていません。冒頭には11種類と書かれ、声の一覧の節には13種類と書かれています。名前が13個並んでいるので、選べるのは13種類と見て、実際に使える一覧は手元のAPIで取得して確かめてください。この記事では、一覧の取得結果を実測値として挙げません（未実機確認）。 品質の面では、marin と cedar が勧められています。

読み上げの速さを変える専用のパラメータは、このエンドポイントには書かれていません。速さは、指示文で調整する形になっています。だから「少しゆっくり読ませたい」は、パラメータではなく原稿と指示で作ります。

モデルの移行も済ませておきます。tts-1、tts-1-hd、gpt-4o-mini-tts は非推奨で、2027年1月6日に停止します。移行先は gpt-realtime-2.1-mini で、Realtime API から使います。ただし公式には、この移行先は /v1/audio/speech では使えないと明記されています。つまり、同じエンドポイントのままモデル名を差し替える移行ではありません。手順書に「モデル名を変えるだけ」と書くと、停止日以降に動かなくなります。

費用は、区間ごとに数える

費用も、区間ごとに分けます。三つの区間で、数える対象が違います。

区間何を数えるかどこで確かめるか
書き起こし送った音声の量料金ページの単位を読む
生成入力と出力のトークン第25章の数え方
読み上げ読み上げた量料金ページの単位を読む

課金の単位は、製品とモデルで違います。文字の数で数えるもの、音声の長さで数えるもの、トークンで数えるものがあります。単位が分からないまま単価だけを写すと、桁を間違えます。この記事では単価を挙げません。 使う製品の料金ページで、単位そのものを先に確かめてください。確認した日付を、単価と同じ行に書きます。

区間ごとに分けると、削る場所が決まります。読み上げの費用が大きいなら、応答文を短くします。書き起こしの費用が大きいなら、無音を切ってから送ります。生成の費用が大きいなら、前の記事の判定を軽いモデルに移します。

見積もりの形は、1000回あたりで揃えます。1回あたりの小数は、桁を読み違えます。1000回で何円か、という形にすると、他の区間とも比べられます。

読み上げ原稿は、書き言葉と別に作る

読み上げには、書き言葉をそのまま渡さないでください。数字、記号、略語、URL は、読み方が一通りに決まりません。「1,200円」をどう読むか、「/」を何と言うか、「API」をアルファベットで読むか語で読むか。渡した側は決めていないのに、読む側は何かを選びます。

だから、読み上げ用の原稿を別に持ちます。決めたことは三つです。数字は読み下した形に直す。記号と URL は、読ませたい形に開く。略語は、初出の一回だけ開いて読む。

長さも見ます。読み上げの時間は原稿の長さに比例するので、長い応答は待ち時間になります。画面に出す文章と、読み上げる文章を分けて、読み上げるほうを短くする形が扱いやすい。

マルチモーダル のモデルに、音声を直接入力する形もあります。それでも、この記事の構成を先に作っておくと、あとで一部を入れ替えたときに、どこが変わったかを測れます。

試す人向け演習・記入例と確認の観点

演習：90秒の音声を、文字にして読み上げ直す

前の記事で作った音声と正解の文字起こしを使います。音声は、自分で録った機密のないものに限ってください。第三者の声が入った録音を、試すためだけに外部へ送らないでください。

API を使って読み上げる場合は、実行する前に、提供元・モデルID・送信先・料金・提供終了予定の五つを公式ページで確かめ、その日の日付と一緒に記録してください。 料金の額は契約によって変わるので、この記事には書きません。短い音声でも課金されます。

この記事の執筆時点で、私はこの通しの実行をしていません（未実機確認）。手元で書き起こしや読み上げを動かした記録もありません。以下の手順は公式ページの記述から組み立てたもので、実測した結果ではありません。手元で動かす場合は、OS・CPU・GPU・メモリ・使ったモデルと版を区間ごとに記録してください。API と手元の値は同じ表に混ぜず、別の行に分けてください。

  1. 90秒の音声を書き起こす。時刻を二つ記録する。始めた時刻と、最初の文字が出た時刻。
  2. 書き起こした文字を、生成の区間に入れる。指示は「三文で要点を答えよ」のように、出力の長さが決まる形にする。最初のトークンが届くまでの時刻を記録する。
  3. 応答文を、読み上げ用の原稿に直す。数字と記号を開き、三文を超えていたら削る。
  4. 読み上げを実行する。形式は wav か pcm を選ぶ。最初の音が届いた時刻を記録する。
  5. budget.py に三つの秒数を渡し、合計と割合を出す。
  6. 表を埋める。埋まらない行には「未測定」と書く。測り方の無い項目は「未対応」と書き、推定値で埋めない。
  7. 読み上げた音声を聞き直し、聞き取れない箇所を数える。原稿と違って聞こえた箇所があれば、その原因を原稿側に書く。
  8. いちばん割合の大きい区間を一つ選び、削る案を一つ書く。実際に削って、もう一度測る。

期待する結果は、区間ごとの秒数と割合が表に埋まり、いちばん大きい区間が一つに決まっている状態です。どの区間が最大になるかは、機械・回線・素材・モデルの組み合わせで変わります。書き起こしが最大になることもあれば、生成や読み上げが最大になることもあります。この記事では実測値を挙げません。値は条件で動くので、順番を決め打ちせず、自分の条件で測って決めてください。測った結果が想定と違ったら、その違いがこの演習の成果です。

うまくいかないときの見方

全体が遅いのに、どの区間も遅くないなら、区間の間で待っています。ファイルの確定、送信の待ち、応答の組み立て、再生の開始。区間の中ではなく、区間の境目にログを打ってください。

読み上げが始まらないなら、まず形式を確かめます。mp3 のまま全部受け取ってから再生していないか。pcm を保存して、開けないプレイヤーに渡していないか。この二つは、どちらも「形式は正しいが使い方が違う」型の失敗です。

書き起こしが長引くなら、音声の前後に無音が残っています。切ってから送ると、費用も待ち時間も減ります。

読み上げた声が不自然に聞こえるなら、原稿を疑います。数字と記号が混ざった原稿は、読み方が揺れます。原稿を開いてから、声や形式を変えてください。順番を逆にすると、声をいくつ試しても直りません。

移行先のモデルが見つからないと言われるなら、エンドポイントが違います。/v1/audio/speech に無いモデルは、Realtime API の側にあります。手順書の移行の節を読み直してください。

手元で書き起こしや読み上げを動かしていて、メモリ不足で止まるなら、モデルを一段下げます。下げると条件が変わるので、表は別の行に分けて測り直してください。whisper や ffmpeg が見つからないと言われる場合は、仮想環境に入ったか、which で場所を確かめます。この二つは、第31章の最初の記事に書いた手順と同じです。

声を配る前に決めること

読み上げた声を外に出すときは、二つの権利を見ます。読ませるテキストの権利と、声そのものの扱いです。

テキストは、自分で書いたものか、利用条件の明確なものに限ります。第三者の文章を読み上げて配るのは、引用の範囲を超えれば複製になります。

声については、特定の人の声に似せる使い方をしません。実在の人の声を再現する形は、本人の同意が無ければ作りません。このサイトの実習でも、その形の課題は扱いません。

音声を外部のAPIに送るということは、原稿と音声を外のサーバーに預けることでもあります。第31章の最初の記事で書いた三つ、何のために、どこに送るか、いつ消すかを、ここでも同じように決めてください。

評価

六つの観点で点検します。三つの区間すべてに時刻を記録したか。合計ではなく割合で見たか。読み上げの形式を、用途に合わせて選んだか。読み上げ原稿を、書き言葉と分けて作ったか。単価と単位の両方を、確認日つきで書いたか。そして、測れない項目に「未対応」「未測定」と書いたか。

書き直しが要るのは、次の状態です。合計の時間だけを記録した。読み上げの形式を既定のままにして、待ち時間を測らなかった。数字の入った原稿をそのまま渡した。単価だけを写して、単位を確かめていない。どれも、条件を変えたときに同じ判断ができない記録です。

できあがるもの

手元に残るのは、区間ごとの待ち時間の表、区間ごとの費用の表、そして読み上げ用の原稿の作り方です。この三つがあれば、別の製品に替えたときに、どこが良くなってどこが悪くなったかを言えます。

ここまでで、第31章の三つの記事は、音声を文字にする、画像と文書を数える、それらをつないで測る、という順に並びました。どの記事も、API を呼ばずに済む演習を先に置いています。数え方と測り方が分かっていれば、課金を伴う実行は一度で足ります。

第23章から第31章までの道具は、どれも単体では小さな部品です。次の目標は、この部品を組み合わせて、一つの製品の形にすることです。第32章では、社内の設備について答える窓口を題材に、受け入れ条件から公開前チェックまでを一巡します。ほかの章は実践編の入口からたどれます。
