第31章 専用モデルの組合せ

音声を、まず文字にする

音声を扱う最初の一歩は書き起こしです。VAD・認識・話者分離の役割を分け、送れる形と大きさの制限を確かめてから、誤りを WER で数えます。

仕組みや開発手順を詳しく扱うページです。業務で必要な範囲だけ先に読みたい場合は、学習ルートで別の入口を選べます。

3行の要点

  • 書き起こしは、音声区間の検出・認識・話者分離の三つに分かれる。要る工程は素材で変わる。
  • API には送れる形式と25MBの上限があり、長い音声は切って送る。
  • 誤りは WER で測る。分母は正解の単語数なので、単語の分け方を記録しないと比較できない。

会議の録音、取材の音声、歩きながら吹き込んだメモ。この記事では、こうした音声を一度文字にしてから扱います。音声を入力に取れるモデルに要約させることはできますが、文字にしたほうが扱いやすい道具が多くあります。文字になれば、あとは第5章から第10章で扱ったトークンの世界に入ります。検索も要約も、文字を前提にした道具がそのまま使えます。

この記事の目的は、書き起こしを「とりあえずAPIに投げる」で終わらせず、どこで何が起きているかを分かったうえで実行できるようにすることです。誤りが出たときに、どの工程を直せばよいかを判断できる状態を目指します。

前提は、ターミナルでコマンドを一つ実行できることです。音声ファイルを一つ用意してください。自分で録った90秒程度の声で足ります。手元で動かす場合と API に送る場合では、記録しておく項目が変わります。手元なら OS・CPU・GPU・メモリ・使った版、API なら提供元・モデルID・送信先・料金・提供終了予定です。どちらも、実行したその日に確かめて、日付と一緒に残します。この記事の数値を写しても、自分の環境の記録にはなりません。

音声のままでは、扱える道具が少ない

16kHz のモノラル音声は、1秒あたり一万六千個の数値の列です。10分で960万個になります。音声を入力に取れるマルチモーダル のモデルはありますが、この記事で使う検索・要約・差分の道具は、文字を入れる前提で作られています。波形のままでは、その道具の対象になりません。

文字にすると、事情が変わります。単語に分けられ、数えられ、引用できます。会議の記録を後から探す、決まった形式に抜き出す、要約する。ここで使う道具は、どれも文字を前提にしています。

だからこの記事では、音声の処理を書き起こしから組み立てます。書き起こしを経由する利点は、途中の文字を人が読めることです。誤りに気づけますし、どの工程を直すかを決めやすくなります。費用と待ち時間も、区間ごとに分けて測れます。音声を直接モデルに渡す製品もありますが、そこではこの分け方が使えません。

書き起こしは、三つの工程に分かれる

書き起こしと一口に言っても、中で起きていることは三つに分かれます。この分け方を知らないと、誤りの原因を取り違えます。

**音声区間検出（VAD）**は、音声のどこに人の声があり、どこが無音かを切り分けます。長い録音を、モデルが扱える長さに切るために使います。無音や雑音を認識に回さないぶん、費用も誤りも減ります。

**音声認識（ASR）**は、区間ごとの音声を文字に変えます。STT とも呼びます。ここが本体です。

用語：話者分離（ダイアリゼーション）とは、音声の中で「誰が話したか」を区切って割り当てる処理です。認識の結果に話者のラベルを付ける工程で、文字にする処理そのものとは別です。

工程何を決めるか無いとどうなるか
音声区間検出どこを切り出すか無音や雑音まで認識に回り、誤りと費用が増える
音声認識何と言ったか文字が得られない
話者分離誰が言ったか複数の声が混ざった記録で、発言者が分からない

三つ目は、必ず要るものではありません。一人のナレーションや、自分一人のメモなら不要です。要るのは、会議やインタビューのように複数の声が混ざる素材です。そして、話者分離まで頼むかどうかで、使えるモデルと料金が変わります。ここを一まとめにすると、見積もりが合いません。

手元で回すか、API に送るか

書き起こしには二つの道があります。手元の機械で動かすか、API に送るかです。どちらを選ぶかは、音声を外に出せるかで半分決まります。

手元で動かすなら、Whisper のモデルの重みが公開されています。リポジトリには大きさの違うモデルが並び、速度を優先した turbo も含まれます。公式の表には、パラメータ数、必要な VRAM の目安、相対速度が載っています。相対速度は A100 で英語を書き起こしたときの値で、large を1倍とした比です。

モデルパラメータVRAM の目安相対速度
tiny39M約1GB約10倍
base74M約1GB約7倍
small244M約2GB約4倍

この表は公式の README にある目安で、手元の環境で必ず同じ値になるものではありません。turbo は large-v3 を速くするために調整したモデルで、精度の低下は最小だと説明されています。英語専用の .en 版が用意されているのは tiny から medium までです。

API に送る場合は、POST /v1/audio/transcriptions を使います。公式が推奨しているのは gpt-transcribe です。whisper-1、gpt-4o-transcribe、gpt-4o-mini-transcribe、gpt-4o-transcribe-diarize は非推奨になり、2027年2月26日に停止すると書かれています。手順書を書くときは、この日付を確かめてから使うモデルを決めてください。半年後に同じ手順が動くとは限りません。

API を使う手順を書くときは、次の五つを実行した日に確かめ、日付と一緒に記録します。提供元（どの会社の API か）、モデルID（gpt-transcribe のような識別子）、送信先（どのエンドポイントへ送るか）、料金（課金単位と単価）、モデルの提供終了予定です。この記事では料金の額を書きません。額は変わるうえ、同じモデル名でも契約によって条件が違うからです。公式の料金ページで確かめ、確認した日を添えてください。音声は、機密のない短い録音を使います。第三者の声が入った音声を、試すためだけに外部へ送らないでください。

未確認：この記事の執筆時点で、私は API を実際に呼んでいません。手元で whisper を回した記録も、この記事にはありません。以下の制限も演習の手順も、公式ページと公式 README の記述にもとづくもので、実機で確かめた結果ではありません。手元で試したら、結果を自分の記録に残してください。

送れる形と、大きさの上限

API に送れるファイルには制限があります。上限は25MB、形式は mp3、mp4、mpeg、mpga、m4a、wav、webm です。25MB は音声の長さではなく、ファイルの大きさです。ビットレートが高い録音ほど、短い時間で上限に当たります。同じ10分でも、mp3 の低いビットレートなら収まり、wav のままなら超えることがあります。

長い音声は、切って送ります。公式には、30秒を超える音声に対して chunking_strategy を指定する方法と、VAD の設定を渡す方法が説明されています。切ったあとの文が途中で分断されるので、つなぐときに前後の文脈を見る処理が要ります。

結果の形は、パラメータで変わります。response_format は text、verbose_json、diarized_json から選びます。timestamp_granularities[] で単語や区間の時刻を要求できますが、これは whisper-1 のみと書かれています。prompt で固有名詞や専門用語の表記を誘導でき、whisper-1 では224トークンまでです。languages で言語を指定でき、ISO 639-1、639-3、zh-cn のような形を受け付けます。単数の language を置き換えるものだと説明されています。

stream=true を付けると、transcript.text.delta、transcript.text.done、transcript.segment のイベントが流れてきます。長い音声を画面に出すときは、最初の一文が出るまでの待ち時間を縮められます。この待ち時間は、第8章で扱った TTFT と同じ考え方で測ります。

ストリーミングに対応していないモデルや API では、この値は取れません。その場合は「未対応」または「未測定」と書き、全体の待ち時間で代用したことだけを添えてください。推定値で空欄を埋めないでください。同じことは、話者分離にも当てはまります。対応が公式に書かれていないモデルでは、試していない項目を「非対応」と断定せず、「未確認」と書きます。

誤りは、単語の数で測る

書き起こしの質は、感想ではなく数字で測ります。標準的な指標が WER（Word Error Rate）です。

WER = (S + D + I) / N

S は置換、D は削除、I は挿入、N は正解の単語数です。N は S + D + C と定義されます。C は正しく一致した単語数です。0 が完全一致で、値が小さいほど良い、と説明されています。

分母が正解の単語数である点が大事です。認識結果が長くなっても分母は変わりません。挿入が多いと分子が分母を超え、1を上回る計算になります。ただし、この定義を載せている資料には、1を超える場合についての記述はありません。式から出る結果として自分で確かめてください。

手元で出すなら、次のスクリプトで足ります。外部のライブラリを使わず、単語列の編集距離をそのまま計算します。

# wer.py — 正解と認識結果の単語列から WER を出す
import sys


def wer(ref, hyp):
    d = [[0] * (len(hyp) + 1) for _ in range(len(ref) + 1)]
    for i in range(len(ref) + 1):
        d[i][0] = i
    for j in range(len(hyp) + 1):
        d[0][j] = j
    for i in range(1, len(ref) + 1):
        for j in range(1, len(hyp) + 1):
            cost = 0 if ref[i - 1] == hyp[j - 1] else 1
            d[i][j] = min(
                d[i - 1][j] + 1,           # 削除
                d[i][j - 1] + 1,           # 挿入
                d[i - 1][j - 1] + cost,    # 置換（一致なら0）
            )
    return d[len(ref)][len(hyp)] / len(ref)


if __name__ == '__main__':
    ref = sys.argv[1].split()
    hyp = sys.argv[2].split()
    if not ref:
        raise SystemExit('正解の単語列が空です')
    print(f'{wer(ref, hyp):.3f}')

実行すると、誤り率が小数で出ます。正解と認識結果を引用符で囲んで渡してください。

日本語には、単語の区切りが書かれていないという問題があります。WER を出すには、まず単語に分ける必要があり、分け方で値が変わります。係り助詞を前の語に付けるか、後ろに付けるか。固有名詞を一つと数えるか、二つに割るか。だから WER は、分け方とセットで記録します。分け方を書いていない WER は、他の回と比べられません。

文字単位で同じ式を使う CER（Character Error Rate）という測り方もあります。日本語ではこちらのほうが安定することがありますが、本記事では定義だけを挙げ、実測値は出しません。

速さは、音声の長さとの比で測る

書き起こしの速さも、秒では測りません。音声の長さで割ります。

RTF（Real Time Factor） = 処理にかかった時間 ÷ 音声の長さ

1未満なら、実時間より速く処理できたことになります。10分の音声を2分で書き起こせば0.2です。この比なら、モデルの大きさや機械の違いをまたいで比べられます。

この記事では RTF の実測値を挙げません。 RTF の定義を公式の一次資料で確認できなかったためです。手元で測った値だけを、機械とモデル名を添えて記録してください。

待ち時間は、二つに分けて測ります。最初の文字が出るまでの TTFT と、最後まで出るまでの レイテンシ です。長い会議の録音では、最初の一文が早く出ることのほうが体感に効きます。最後まで出るまでの時間は、分割の回数と、モデルの大きさで決まります。

試す人向け演習・記入例と確認の観点

演習：90秒の音声を書き起こし、WER を出す

自分で録った90秒の音声を一つ用意して、最後まで通します。

  1. 音声を録る。内容は何でもよいが、あとで正解を手で書ける範囲にする。周りに第三者の声が入らない場所で録る。
  2. 正解の文字起こしを手で作る。200字から300字程度になる。
  3. 手元で回す場合は、先に環境を記録する。OS とその版、CPU、GPU とメモリ、Python の版（python --version）、whisper の版（pip show openai-whisper）を控える。そのうえで whisper audio.m4a --model turbo --language ja を実行する。turbo は翻訳を学習していないので、--task translate は使わない。言語コードの書き方は whisper --help で確かめる。
  4. API に送る場合は、機密のない自分で録った音声だけを使い、25MB 以下と形式を確かめる。同じ日に、提供元・モデルID・送信先・料金・提供終了予定を公式ページで確認し、日付と一緒に記録する。response_format を verbose_json にして時刻も受け取る。秘密鍵は環境変数に置き、ブラウザ側のコードには書かない。
  5. 結果と正解を、同じ基準で単語に分ける。分け方の規則を一行で書く。
  6. 上のスクリプトで WER を出す。
  7. 誤りを三種に分類する。置換・削除・挿入のどれが多いか。固有名詞に偏っているなら、prompt に表記を入れて再試行する。
  8. 数字と、誤りの実例を三つ、記録に残す。

未実機確認：この記事を書いた時点で、私はこの八つの手順を通していません。手元で whisper を回した結果も、API を呼んだ結果も、ここにはありません。以下は公式ページと公式 README の記述から組み立てた手順で、実機で確かめた記録ではありません。

費用についても書いておきます。API に送ると、短い音声でも課金されます。無料の枠や試用があるかは契約によって違うので、実行する前に料金ページで確かめてください。手元で回す場合は API の料金はかかりませんが、モデルの重みのダウンロードに時間と通信量がかかります。

期待する結果は、誤りが固有名詞と数字に集中する、という形です。人名、社名、型番、金額。ここは文脈から補えないので、モデルが聞き取れなければ落ちます。

この記事では数値を挙げません。90秒の音声一つで出た値を、そのモデルの一般的な精度として書かないでください。素材も話者も違えば、値は動きます。

うまくいかないときの見方

whisper が見つからないと言われるなら、仮想環境を作ってから入れ、which whisper で入った場所を確かめます。ffmpeg が無いと音声を読めない、と公式 README に書かれています。音声を開けないというエラーは、まずここを疑ってください。

メモリが足りないと言われるなら、モデルを一段下げます。turbo から small、small から base へ。下げたら条件を変えたことになるので、WER は別の行として測り直します。前の行と混ぜて比べないでください。

無音の多い録音で誤りが増えるなら、区間の切り方に問題があります。VAD で声の部分だけを切り出すか、chunking_strategy を指定して短く切ります。

同じ語だけ毎回間違えるなら、表記を prompt で渡します。whisper-1 は224トークンまでなので、長い用語集は入りません。本当に効かせたい語を十個ほど選びます。

25MB を超えると言われるなら、まず形式を変えます。wav のまま送っているなら mp3 にすれば小さくなります。それでも超えるなら分割します。分割した境目の文は、必ず前後と突き合わせて直します。

複数の声が混ざって読めないなら、話者分離が要ります。ただし公式に手順が載っているのは、非推奨になった gpt-4o-transcribe-diarize です。移行先の一覧を引き、どのモデルで話者分離ができるようになったかを確認してから手順を書いてください。確認できないまま、動く手順として書かないこと。

応答が遅いなら、stream=true を有効にして、最初の文字までの時間を測ります。全体の時間だけを見ていると、どこで待っているのか分かりません。

音声を扱う前に決めること

音声には、話した人の声そのものが入っています。文字起こしの前に、三つを決めてください。何のために録るか、どこに送るか、いつ消すかです。

自分の声だけなら判断は簡単です。問題は、同僚の声、顧客の声、取材相手の声が入るときです。その音声を外部のAPIに送ることは、声を国外のサーバーに預けることになります。送信先と保存期間を確かめ、必要なら相手の同意を取ります。同意の記録は、口約束ではなく日付つきで残します。

このサイトの実習では、自分で録った声か、利用権が明確な素材だけを使ってください。第三者の音声を無断で組み込んだ課題は作りません。教材として配る場合も同じです。

評価

四つの観点で点検します。正解の文字起こしを自分で作ったか。単語の分け方を記録したか。誤りを置換・削除・挿入に分けたか。そして、出た数値をそのモデルの一般的な精度として書かなかったか。

書き直しが要るのは、次の状態です。正解を作らずに「だいたい合っている」と判断した。WER を出したが、分け方を書いていない。一回の結果を、条件の違う別の音声に当てはめた。どれも、次の音声で同じ判断ができない記録です。

できあがるもの

手元に残るのは、正解つきの音声、WER を出すスクリプト、誤りの分類表です。この三つがあれば、モデルを替えたときに同じ条件で比べられます。

次の記事では、画像と文書を扱います。画像は、音声と違って「送る前」に数えられます。パッチの数から費用が出るので、送る前に見積もりが立てられます。次の記事で、その数え方を確かめてください。

製品名から探したいときは AI図鑑 を使ってください。図鑑の値にも確認日があるので、この記事の日付と見比べてください。
