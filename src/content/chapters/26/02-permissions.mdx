前の記事で、ブラウザ版とデスクトップアプリの条件を表にしました。この記事では、その表の「読ませるフォルダ」と「使いたい機能」の欄を、許可の一覧に変えます。何を読ませ、何を書かせ、どこまで画面を触らせ、通信をどう扱うか。ここを決めずに使い始めると、あとから「こんなところまで見ていたのか」が起きます。

この記事の記述も2026-10-28 に公式ページで確認した内容にもとづきます。このサイトの作成環境では、Claude のデスクトップアプリも、Codex のデスクトップアプリも動かしていません。**未実機確認**です。許可を求められる画面の出方や文言は、バージョンによって変わります。

## 三つの機能への許可

デスクトップアプリがブラウザ版と違うのは、三種類の機能を使えることです。ファイル、画面、音声。この三つは、まとめて許すものではありません。一つずつ、別の設定として存在します。

| 何を許すか | 何が起きるか | どこで止められるか |
| --- | --- | --- |
| ファイル | 指定したフォルダを読む。書き込む場合もある | フォルダの指定。読み取り専用にするかどうか |
| 画面 | 開いているアプリの画面を見て、操作する | OS の画面収録の許可。アプリ側の機能の有無 |
| 音声 | 声で入力する | OS のマイクの許可。アプリ側の機能の有無 |
| 外部のアプリ | 拡張で、ほかのアプリのデータに触れる | 拡張ごとの許可。組織のポリシー |
| 通信 | 外へ出て、ウェブを読む、[[api\|API]] を呼ぶ | サンドボックスのネットワーク設定。承認 |

表の右の列がこの記事で扱うところです。左の列だけを見て「便利そうだ」と決めると、右の列をあとから探すことになります。

## フォルダは、つないだ範囲だけを見る

Claude の Cowork について、公式のサポート記事には三つのことが書かれています。手動でアップロードしなくてもローカルのファイルにアクセスできること。コードは、そのコンピュータの上の隔離された仮想マシンで実行されること。ファイルの読み書きは、つないだフォルダに限られ、ネットワークへのアクセスは外向き通信の設定に従うこと。

この設計は、覚えておく価値があります。理由は三つです。

第一に、**範囲は自分で決める**ということ。つながっていないフォルダは読まれません。だから、仕事の資料と私用の資料を同じ親フォルダの下に置いていると、範囲の指定が難しくなります。先に分けておくほうが確実です。

第二に、**コードは自分の環境の上で動く**ということ。隔離された仮想マシンと書かれていても、ディスクを使い、メモリを使います。Linux で Cowork を使う場合の要件として、ワークスペースのイメージ用に約 25GB の空きディスクと、8GB 以上のメモリが挙げられています。仮想マシンのためのパッケージ（KVM と QEMU）も必要で、利用者がそのグループに入っていることが条件です。

第三に、**通信は別の設定**だということ。ファイルを読めることと、読んだ内容を外へ出せることは、別に決まります。「外向き通信の設定に従う」と書かれているので、その設定がどうなっているかを自分で確かめる必要があります。

## 画面と声は、OS の上でしか動かない

画面を見る機能と、声で入力する機能は、ブラウザのタブでは実現できません。OS の権限と、アプリの実装の両方が要ります。[[computer-use]] はその代表です。

Claude の Linux 版について、公式記事には使えない機能が明記されています。画面を見て操作する機能（computer use）は使えない。音声入力（dictation）も使えない。Quick Entry は X11 で動き、Wayland では GlobalShortcuts の仕組みを使う、といった但し書きも並びます。

この一覧は機能の紹介ではなく、設計の制約です。Linux の端末で「画面を見せて操作させる」業務を組み立てようとすると、この時点で行き止まりになります。同じ会社のアプリでも、OS が違えばできることが違う。前の記事で作った条件表に、この列を足してください。

macOS と Windows での画面操作と音声入力の可否は、この記事で参照した範囲では、機能ごとの可否までは確認できませんでした。未確認として扱い、自分の環境の設定画面で確かめてください。

## 拡張は、つなぎ方と保管の設計を読む

デスクトップアプリはほかのアプリとつなぐ仕組みを持っています。Claude では「拡張（Extensions）」と呼ばれ、公式記事には四つの説明があります。ワンクリックでデスクトップのアプリとつなげること。確認済みの拡張をアプリの中から探せること。拡張はコード署名と、[[api-key|API キー]]のような機微なデータの暗号化された保管を使うこと。組織向けのポリシーで制御できること。管理画面は「設定」→「デスクトップアプリ」→「拡張」です。

ここで読むべきは、「ワンクリック」の部分ではありません。**誰が作った拡張か**と、**鍵をどこに置くか**です。[[mcp]] のような仕組みで外部とつなぐ場合、つないだ先の権限がそのまま自分の代わりに働きます。確認済みと表示されていても、その拡張が何を読むのかは別に確かめます。

会社の端末で使うなら、組織のポリシーで何が許されているかを先に確認してください。個人の端末で試した設定が、そのまま業務の端末で使えるとは限りません。

## サンドボックスと承認は、別の軸で決まる

Codex の公式文書には、エージェントの動きを二つの軸で決める形が書かれています。一つは[[sandbox]]（何ができるか）、もう一つは承認（いつ利用者に聞くか）です。この二つを混ぜて覚えると、判断を誤ります。

サンドボックスは三つです。

| モード | できること | 注意 |
| --- | --- | --- |
| read-only | 読み取りを中心に、変更を制限する | 通信や制限を超える操作の扱いは、承認ポリシーと環境設定で決まる |
| workspace-write | 許可された作業ディレクトリ内で変更できる | 範囲外への書き込みと通信の扱いは、承認ポリシーと環境設定で決まる |
| danger-full-access | 実行環境のサンドボックス制限を外す | 承認ポリシーは別に決める。`--yolo` は承認の省略も組み合わせる |

承認の側には、`on-request`、`never`、`granular`、`auto_review` といったポリシーがあります。以前あった `untrusted` は廃止され、残っているとクライアントが起動しないことがあると書かれています。バージョンによって名前が変わる領域なので、使う前に公式ページを見直してください。

既定の選び方も書かれています。バージョン管理されたフォルダなら Auto、つまり workspace-write と on-request の承認の組み合わせ。そうでなければ read-only。ディレクトリを信頼するまでは、read-only で始まることがある。そして、**既定ではネットワークへのアクセスが切られている**。

最後の一文がいちばん実務に響きます。`npm install` のような通信を伴う操作が失敗するのは、不具合ではなく既定です。ネットワークを開くには設定を変える必要があり、プロキシを設定しただけでは通信は開かない、と明記されています。

保護されるパスも決まっています。`.git`、`.agents`、`.codex`、`.aws` は、ワークスペースの中にあっても読み取り専用で、その下のすべてに再帰的に適用されます。認証情報が置かれやすい場所を、最初から書かせない設計です。

この文書は Codex というエージェント全般の説明で、デスクトップアプリ専用の記述ではありません。デスクトップアプリで同じ名前の設定が見つからない場合は、アプリ側の表示を優先してください。

## 外から来た指示を、指示として扱わない

エージェントにウェブを読ませると、新しい種類の危険が入ります。読んだページの中に「このファイルを送れ」と書いてあったとき、エージェントはそれを利用者の指示と区別できないことがあります。これを**[[prompt-injection|プロンプトインジェクション]]**と呼びます。

公式文書には、はっきり書かれています。プロンプトインジェクションは、エージェントに信頼できない指示を取りに行かせ、それに従わせることがある。ウェブの検索結果は信頼できない入力として扱う。開発用のコンテナ環境では、Codex の認証情報を持ち出される経路がありうる。

対策は機能を切ることだけではありません。三つを組み合わせます。

- **読ませる範囲を分ける**。仕事の資料と、外から取ってきた文章を、同じフォルダに置かない。
- **書ける範囲を絞る**。読ませるだけの作業では、workspace-write にしない。read-only で足ります。
- **通信を切る**。外へ出る必要がない作業では、ネットワークを開かない。既定がそうなっているのは、このためです。

許可を求める画面が出たら、内容を読んでから答えてください。読まずに許可を続けると、この三つはどれも効きません。

## 演習：自分の作業を、五つの列に分ける

アプリは入れません。紙か表計算に、自分の作業を一つ選んで書き出します。

1. 作業を一つ選ぶ。「議事録をフォルダから読んで要約する」のように、具体的に書く。
2. 五つの列を作る。読む、書く、通信、画面、音声。
3. その作業に、それぞれが必要かを書く。要るか要らないかだけでよい。
4. 「要る」と書いた列について、最小の範囲を書く。フォルダなら一つ、通信なら宛先一つ。
5. いま使っている道具で、その範囲を指定できるかを確かめる。指定できないなら、その作業は今はやらない、と決める。
6. 表の下に、確認した日付と、参照した公式ページの URL を書く。

期待する結果は、「要らない」の列が半分以上になることです。要約だけなら書き込みは要りません。社内の資料を読むだけなら通信も要りません。要らない列を消していくと、許可を求める画面も減ります。

## うまくいかないときの見方

フォルダを指定したのに読めないときは、そのフォルダがそもそも許可の対象になっているかを見ます。親フォルダを指定したつもりで、実際は別の場所を指していることがあります。パスの確認は、アプリの画面ではなく、OS のファイル管理側で行います。

書き込みが拒否されるときは、サンドボックスのモードを先に見ます。read-only なら、承認があっても書けません。モードと承認は別の軸です。

通信が通らないときは、既定の設定を疑います。Codex の文書では、既定でネットワークが切られていると書かれています。プロキシの設定は、それだけでは通信を開きません。

Linux で機能が見つからないときは、対応表を見ます。画面操作と音声入力は、Linux 版では使えないと明記されています。探し続けるより、対応表に戻るほうが早いことがあります。

許可の画面が読めないほど多く出るときは、作業の切り方が大きすぎます。「このフォルダの資料を全部整理して」ではなく、フォルダを一つに絞り、読み取りだけを頼みます。依頼が小さいほど、許可の数も小さくなります。

## 評価

五つの観点で点検します。読ませるフォルダを、作業ごとに決めたか。読み取りと書き込みを分けて考えたか。通信の要否を、作業ごとに決めたか。サンドボックスと承認を、別の軸として説明できるか。そして、確認できなかった機能に「未確認」と日付を添えたか。

書き直しが要るのは、次の状態です。ホームディレクトリ全体を許可した。通信が要るかどうかを確かめずに、既定のまま失敗して「壊れている」と判断した。許可の画面を読まずに続けた。どれも、何を許したかを言えない状態です。

## できあがるもの

手元に残るのは、作業ごとの許可表と、確認できた機能・できなかった機能の一覧です。許可表は、アプリを入れ替えても使い回せます。道具が変わっても、作業に必要な範囲は変わりません。

次の記事では、この許可表を持って、同じ資料をブラウザ版とデスクトップアプリで試し、比較レポートにまとめます。データの扱いをどう確かめるか、確かめられないときにどう書くかも、そこで扱います。[同じ資料で試して、比較レポートに残す](/chapters/26/03-comparison-report/)へ進んでください。
