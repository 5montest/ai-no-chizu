先に断っておきます。ここに載せるのは、**2026-10-28 に各公式サイトで確認できた記述**だけです。このサイトの作成環境では8製品のどれも動かしていないため、すべて**未実機確認**です。動作の速さ、応答の質、費用対効果の優劣は、この記事からは言えません。言えるのは「どの用途に向くと公式が説明しているか」「どの権限の仕組みがあるか」「どこで詰まりやすいか」までです。

## 製品名を見る前に、4つを分ける

同じ製品名が、モデルにもハーネスにも操作画面にも使われます。分けずに読むと、比較の対象が入れ替わります。カードを読む前に、次の4つを別の欄として用意してください。

- **モデル**：推論を行う本体。名前と版で指定する。
- **ハーネス**：モデルを呼び出し、ツールを実行し、作業の状態を保つ側。[[agent-loop]] を回す部分。
- **操作画面**：ターミナル、IDE、デスクトップアプリ、ブラウザ。同じハーネスが複数の画面を持つことがある。
- **契約と課金**：誰のアカウントで、何を単位に支払うか。

[[harness|ハーネス]]と画面は、よく同じ言葉で呼ばれます。CLI は操作方法の名前で、それ自体がハーネスというわけではありません。ChatGPT や Claude のデスクトップアプリは利用するアプリの名前で、その中のエージェントがハーネスです。5層の整理は[第23章](/chapters/23/01-five-layers/)で扱っているので、ここでは4つに絞ります。

実行場所も別の軸です。手元で動かしていても、モデルの推論が外部 API なら、入力した内容は外部へ送られます。ローカル実行かどうかと、データが外に出るかどうかは別に確認してください。

## 8製品のカード

以下、各カードの並びは同じです。見出しが正式名、本文が特徴と典型的な用途、箇条書きが公式・入口・モデル・権限・拡張・分担・保存・契約・導入・不向きの10項目です。「不明」は、参照した公式ページに記載が見つからなかったという意味で、機能が無いという意味ではありません。

### Claude Code

Anthropic のエージェント型コーディングツールです。リポジトリを読み、ファイルを編集し、コマンドを実行し、開発ツールと統合します。差別化点は、**権限モードと指示ファイルの分離**です。6つの権限モードで、読み取りのみから全許可までを切り替え、deny ルールはどのモードでも有効です。典型的な用途は、リポジトリを読ませて修正・テストまで一巡させる作業です。

- **公式**：[Claude Code の概要](https://code.claude.com/docs/en/overview)。
- **入口**：ターミナル、VS Code、JetBrains、デスクトップアプリ、ブラウザ（claude.ai/code）。インストール手段は macOS / Linux のスクリプト、Homebrew、winget、apt / dnf / apk。
- **モデル**：`--model` にエイリアスかフル名。ターミナル・VS Code・JetBrains は第三者の提供元にも接続できる。
- **権限**：`manual`（読み取りのみ）、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions` の6モード。deny ルールは全モードで有効。
- **拡張**：Skills、Hooks、MCP、Plugins、サブエージェント、Agent SDK。
- **分担**：サブエージェント。Agent Teams は**実験的で既定は無効**。有効にするとリードとチームメイトが別のコンテキストで動き、共有のタスク一覧を使う。
- **保存**：セッションの transcript を残して再開できる。`CLAUDE.md` を毎セッション読み、`AGENTS.md` を代わりに読ませられる。自動メモリ。
- **契約**：サブスクリプション、または Anthropic Console のアカウント。料金は[第25章](/chapters/25/)。
- **導入**：公式 Overview のインストール節。手順の通しは[第27章](/chapters/27/)。
- **不向き**：Agent Teams は実験的で、単一セッションよりトークン消費が大きい。標準構成は Claude の契約が前提。

### Codex CLI

OpenAI のコーディング用ハーネスです。差別化点は、**ローカルの CLI とクラウド側の実行を同じ製品群で扱う**ところにあります。対話の TUI のほか、`codex exec` で自動化やパイプラインに組み込めます。典型的な用途は、端末での対話的な修正と、CI や定型処理への組み込みです。

- **公式**：[Codex CLI](https://learn.chatgpt.com/docs/codex/cli)。
- **入口**：対話 TUI、`codex exec`、IDE 拡張、デスクトップアプリ、Codex Cloud、GitHub Action。対応OSの一覧は不明。
- **モデル**：セッション内の `/model` でモデルと推論の強さを選ぶ。画面例は `gpt-6.1-sol medium`。
- **権限**：`/permissions` でファイル編集とコマンド実行を確認なしで許す範囲を選ぶ。有効なサンドボックスと書き込み可能なディレクトリを確認できる。
- **拡張**：`AGENTS.md`（`/init` で作成）、Skills、plugins、`codex mcp`、subagents。
- **分担**：subagents。ワークスペースエージェントは Beta 表示。
- **保存**：`AGENTS.md` とセッション。`codex resume` で再開し、`codex exec --json` でイベントを JSONL に出力できる。
- **契約**：ChatGPT でのサインインが案内されている。利用枠と料金は契約ごとに異なるため[第25章](/chapters/25/)で扱う。
- **導入**：公式 Codex CLI ページの導入節。手順の通しは[第27章](/chapters/27/)。
- **不向き**：既定の入口が ChatGPT の契約前提。クラウド実行は、ローカル実行とデータの送信先が異なる。

### OpenCode

オープンソースの AI コーディングエージェントです。差別化点は、**提供元を選べることと、エージェントを定義ファイルで分けられること**です。primary エージェントを Tab で切り替え、subagent を @ で呼びます。組み込みは Build（全ツール）と Plan（制限あり）、読み取り専用の Explore などです。典型的な用途は、契約中のモデルを入れ替えながら同じリポジトリで試す作業です。

- **公式**：[OpenCode の Intro](https://opencode.ai/docs/)。
- **入口**：ターミナル、デスクトップアプリ、IDE 拡張。対応OSの一覧は不明。
- **モデル**：`/connect` で提供元を選び API キーを設定する。任意の LLM プロバイダーに対応。選別済みモデルの OpenCode Zen という経路もある。
- **権限**：エージェント設定の `permission` で read / edit / bash / webfetch などを許可・確認・拒否に分ける。最後に一致した規則が優先される。
- **拡張**：plugins、custom tools、MCP サーバー、SDK、server。Skills は `SKILL.md` を置き、必要になったときだけ `skill` ツールで読む。
- **分担**：primary と subagent を分ける。subagent は呼び出されたときだけ別のコンテキストで動く。
- **保存**：`/undo` と `/redo`。セッションの保存と再開の手順は導入した版で確認する。
- **契約**：提供元ごとに API キーと料金が分かれる。合計は利用者側で集計する。
- **導入**：公式 Intro の導入節。手順の通しは[第27章](/chapters/27/)。
- **不向き**：費用が提供元ごとに分かれる。Plan の編集権限は版と設定に依存するため、実機で確認する。

### Pi

ターミナルで動く拡張可能なエージェントです。差別化点は、**最小構成から TypeScript で作り込む前提**であることです。対話のほか、print モード、JSON イベントストリーム、RPC、TypeScript SDK という入口があります。セッションは作業フォルダごとに自動保存され、続きから再開しても分岐しても履歴を失いません。典型的な用途は、自分の作業に合わせてツールを足す使い方です。

- **公式**：https://pi.dev/docs/latest。
- **入口**：対話ターミナル、print、JSON イベントストリーム、RPC、SDK。インストールは shell スクリプト（macOS / Linux）、PowerShell、npm（Node.js 22.19 以上）、Nix。
- **モデル**：サブスクリプション、API キー、ローカルモデル、互換エンドポイントを `/login` と `/model` で接続する。
- **権限**：読み取り・検索・コマンド・編集を表示するが、**ツール呼び出しのたびに確認は求めない**。公式はコンテナなどのサンドボックスを勧めている。
- **拡張**：TypeScript の Extension。ライフサイクルイベント、独自ツール、コマンド、ツール呼び出しの横取り、コンテキスト注入、モデルプロバイダーの登録。`~/.pi/agent/extensions/` と `.pi/extensions/` を1階層だけ自動で読む。
- **分担**：サブエージェントの記載は不明。
- **保存**：セッションを作業フォルダごとに自動保存。`pi --continue` と `/resume` で再開し、分岐できる。
- **契約**：モデルの契約は接続先ごと。Pi 自体の料金は不明。
- **導入**：公式 Quickstart。手順の通しは[第27章](/chapters/27/)。
- **不向き**：確認を都度求めないため、本番ファイルや秘密情報のある環境にそのまま置かない。Extension は同じ OS 権限で動くので、出所の知れないものを入れない。

確認日 2026-10-28。検証状態：未実機確認。

### Hermes Agent

Nous Research のエージェント環境です。差別化点は、**常駐とメッセージ連携、永続メモリ**です。6つのターミナルバックエンド（local、Docker、SSH、Daytona、Modal、Vercel Sandbox）を持ち、VPS やサーバーレスに置けます。Telegram、Discord、Slack など20以上のプラットフォームを1つのゲートウェイから扱います。典型的な用途は、チャットから呼び出して継続的に働かせるタスクです。公式は、IDE に結びついたコーディング支援ではないと位置づけています。

- **公式**：[Hermes Agent Documentation](https://hermes-agent.nousresearch.com/docs)。
- **入口**：CLI、デスクトップインストーラ（Windows / macOS）。6つのターミナルバックエンド。VPS・GPU クラスタ・サーバーレスに常駐できる。
- **モデル**：Nous Portal、OpenRouter、OpenAI、任意のエンドポイント。OAuth 1つでモデルと4つの Tool Gateway ツールをまとめて認可する。
- **権限**：コマンド承認、認可、コンテナ分離。
- **拡張**：60以上の組み込みツール、`execute_code`、agentskills.io 互換の Skills、Skills Hub、plugins、MCP。
- **分担**：サブエージェントの記載は不明。
- **保存**：セッションをまたぐ永続メモリ、定期的な保存の促し、FTS5 による横断検索と要約、Honcho による利用者モデル。
- **契約**：モデルの契約は接続先ごと。本体は MIT ライセンス。料金は不明。
- **導入**：公式ドキュメントの導入節。手順の通しは[第27章](/chapters/27/)。
- **不向き**：公開ステージの区分は不明。ローカル推論の同梱はない。常駐させると、利用枠の消費が動いている間ずっと続く。

確認日 2026-10-28。検証状態：未実機確認。

### DeepSeek Harness

DeepSeek が公開しているオープンソースのエージェント実行環境です。**公開プレビュー中**で、Cordis の「すべてがプラグイン」という構成を採ります。差別化点は、**機能の追加をプラグインで行う設計**です。デスクトップアプリと Web UI の両方から使え、ワークスペース、ファイルとドキュメントのプレビュー、モデル選択、プラグインマネージャ、自動化、スケジューリング、実行経路（trajectory）の表示を持ちます。

- **公式**：[DeepSeek Harness](https://www.deepseek.com/en/harness/)。
- **入口**：デスクトップアプリ（macOS Apple silicon、Windows 64-bit）と Web UI（`npx @deepseek-ai/dsh web`、Node.js が必要）。
- **モデル**：画面のモデル選択で切り替える（例：`DeepSeek-V41-Flash High`）。接続方法と認証の詳細は不明。
- **権限**：自動承認の見直し（Auto approval review）は Experimental 表示。権限モードの一覧は不明。
- **拡張**：Creator mode でプラグインを作り、`dsh-plugin` トピックで共有する。プラグインマネージャから管理する。
- **分担**：Agent teams は Experimental 表示。Subagents と Agent loop も Experimental として並んでいる。
- **保存**：ワークスペースとチャット。保存期間の設定は不明。
- **契約**：オープンソース（MIT）。モデルの契約と料金は不明。
- **導入**：公式サイトのインストール案内。
- **不向き**：公開プレビュー中で、コアプラグインと API が変わると明記されている。安定版の標準機能として前提にしない。

## 用途から候補を絞る

8枚のカードを、よくある6つの用途で引き直します。ここでも順位は付けません。公式の記述から「候補になりやすい」と言えるものだけを並べます。

- **コーディング**：候補は Claude Code、Codex CLI、OpenCode、Pi、Aider、Gemini CLI。いずれも端末からリポジトリを読み、編集とコマンド実行を行います。Gemini CLI は企業向け Code Assist の契約が前提です。
- **一時的な調査**：候補は OpenCode の Explore、Claude Code の `manual`、Codex CLI の読み取り側の設定。読み取り専用のサブエージェントや、読み取りのみの権限モードがあります。調査だけなら書き込みを許可しません。
- **長期常駐**：候補は Hermes Agent、DeepSeek Harness。前者は6つの実行環境と20以上の連携、後者はスケジューリングを持ちます。どちらも利用枠を消費し続けます。
- **独自拡張**：候補は Pi、DeepSeek Harness、OpenCode、Claude Code、Hermes Agent。Pi は TypeScript の Extension、DeepSeek Harness はプラグイン、OpenCode は plugins と custom tools、Claude Code は Skills・Hooks・Plugins・MCP です。
- **モデルの自由度**：候補は OpenCode、Pi、Aider、Hermes Agent。提供元や互換エンドポイントを選べます。Claude Code もターミナルと IDE では第三者の提供元に接続できます。
- **クラウド実行**：候補は Codex CLI（Codex Cloud、GitHub Action）、Hermes Agent（VPS・サーバーレス）。手元に置かずに動かせます。ただし、手元で動かしてもモデル推論が外部 API なら内容は送信されます。

この整理は、候補を2つに絞るための入口です。絞ったあとは、次の記事で同じ課題を出して比べます。この段階で「こちらのほうが良い」と決めないでください。

## 具体例で比べる

### 小さな修正（README に節を一つ足す）

第27章の練習用リポジトリで、README に「使い方」の節を足すだけの依頼です。候補は、すでに契約しているモデルを使えるハーネスになります。Claude Code なら `--model`、Codex CLI なら `/model` で、使うモデルを先に表示しておきます。

この規模では、ハーネスの差より、**確認回数と差分の読みやすさ**が判断材料になります。編集の許可を何回求められたか、差分が依頼の範囲に収まっているかを記録します。Aider のように自動でコミットする製品では、コミットが一つの単位になるので、あとから戻す手順も変わります。

### テストを伴う修正（テストを走らせて判定する）

依頼に「テストを実行し、結果を示す」を含める場合、テストコマンドの許可が論点になります。Claude Code では `Bash(npm test)` のような規則で許可を絞れます。Codex CLI では `/permissions` で、どこまで確認なしで実行するかを決めます。OpenCode では `permission` の `bash` を確認つきにできます。Pi はツール呼び出しごとに確認を求めないため、サンドボックス側で範囲を切ります。

ここで比べられるのは、**テストを実行したかどうか**と、**出力をどこまで見せたか**です。「通りました」という要約だけの記録は、あとで再現できません。実行したコマンドと、落ちたテスト名まで残します。

### Discord 連携の継続タスク

チャットから呼び出して、決まった時刻に動き続けるタスクです。候補の第一は Hermes Agent です。20以上のプラットフォームを1つのゲートウェイから扱い、永続メモリと定期実行を持ちます。DeepSeek Harness もスケジューリングを持ちますが、公開プレビュー中である点を条件に含めます。

コーディング用のハーネスで同じことをする場合は、Bot のコードを自分で書き、Claude Code や Codex CLI でそのコードを保守する形になります。継続タスクは、一回の修正とは評価の仕方が違います。**動き続ける間ずっと利用枠を消費する**こと、外部への送信が続くこと、止まったときに誰が気づくかを、費用と一緒に記録してください。

## 似た名前のモデルと、別の製品

混同しやすい組み合わせを3つ挙げます。

**DeepSeek と DeepSeek Harness。** DeepSeek はモデルと API の提供元を指す名前で、DeepSeek Harness はその上で動くエージェント実行環境です。DeepSeek のモデルを Claude Code や OpenCode から呼ぶ場合と、DeepSeek Harness を使う場合は、比べている層が違います。

**Claude と Claude Code。** Claude はモデルの系列、Claude Code はそれを呼び出すハーネスです。Claude Code のモデルは `--model` で選ぶので、同じ Claude Code でもモデルを替えれば結果は変わります。モデルを替えた実験を、ハーネスの比較と呼ばないでください。

**Codex CLI と ChatGPT のデスクトップアプリ。** ChatGPT はアプリの名前で、Codex CLI は端末から使うハーネスです。同じ Codex でも、端末の CLI、IDE 拡張、デスクトップアプリ、クラウドでは入口が違います。どの入口で試したかを記録しないと、あとで条件を再現できません。

## うまくいきやすい進め方と、つまずきやすい進め方

実際の記録ではなく、公式の注意書きから読み取れる型として書きます。

**うまくいきやすい型。** 先に読み取りだけで対象ファイルを絞り、次に編集を許可する。テストのコマンドを依頼文に書く。作業前に `git status` と直前のコミットを控える。権限は、必要になった操作だけを足す。どの製品でも、この順は変わりません。

**つまずきやすい型。** 最初から全許可で始める。`CLAUDE.md` や `AGENTS.md` を読ませずに、毎回同じ指示を貼る。サンドボックスで通信が止まったのを、製品の不具合と書く。一度の結果で順位を付ける。Agent Teams のような実験的な機能を、安定版の標準機能として前提にする。

サンドボックスで依存の取得に失敗するのは、既定の設計であることがあります。失敗として数える前に、何が止められたのかを確かめてください。

## 最新の状態を追う

この記事の内容は、確認日から先に変わります。追い方は次の5つです。

1. **公式ページを最初に読む。** 紹介記事や動画より、提供元のページと、そのページの更新日を見ます。
2. **提供状態を書き分ける。** 一般提供、プレビュー、実験的のどれかを、製品名の横に書きます。Claude Code の Agent Teams は実験的で既定は無効、DeepSeek Harness は公開プレビューです。
3. **版を記録する。** `--version` などで確認した値と、確認した日をセットで残します。版が変われば、同じ手順でも結果が変わります。
4. **見つからない機能は「不明」と書く。** 参照したページに記載が無いだけなら、非対応とは書きません。あとで別のページを読めば変わる欄です。
5. **モデル名と製品名を混ぜない。** モデルの更新とハーネスの更新は別に起きます。片方だけが変わったときに、何が変わったのか分かるように記録します。

確認できた事実と、そこから言える範囲を分けて書く。この記事のカードが「不明」を残しているのは、そのためです。

## 演習：用途を一つ選び、候補を二つに絞る

8製品すべてを試す必要はありません。試す前に、紙かテキストファイルで候補を2つに絞ります。

1. 6つの軸から、やりたいことを一つ選びます。「コーディング」「一時的な調査」「長期常駐」「独自拡張」「モデルの自由度」「クラウド実行」のどれかです。
2. 4つの欄を書きます。モデル、ハーネス、操作画面、契約と課金。まだ決まっていない欄は「未定」と書きます。
3. 上の用途の整理から、候補を2つ選びます。理由を一行ずつ書きます。
4. 2つの公式ページを開き、カードの12項目のうち6項目を自分の言葉で埋めます。埋まらない欄は「不明」と書き、参照した URL と確認日を添えます。
5. 2つのうち、次の記事で実際に試すものを一つ決めます。もう一つは「今回は試さない」と理由つきで残します。

期待する成果物は、選定メモ1枚です。4つの欄、候補2つと理由、6項目の確認結果、確認日がそろっていれば完成です。12項目すべてを埋める必要はありません。

うまくいかないときの切り分けです。候補が4つ以上残る場合は、軸を一つに絞れていません。「速いほう」で選ぼうとしている場合は、この記事から言える範囲を超えています。公式ページが英語で読みにくい場合は、見出しだけを拾い、インストール、権限、拡張の3節だけを読めば足ります。

## 評価

四つの観点で点検します。4つの欄が分かれているか。候補の理由が、公式の記述か自分の用途に結びついているか。不明の欄に、参照先と確認日があるか。そして、この記事の整理から優劣を結論していないか。

書き直しが要るのは、次の状態です。モデル名をハーネスの欄に書いた。候補を1つに決め打ちして、比較する相手を残さなかった。確認していない機能を「非対応」と書いた。どれも、次の記事で実験の条件が定まらなくなります。
