前の記事で、比べる観点を八つに決めました。この記事では、その観点を使って一度実験し、あとから読み返せる記録にします。目的は勝者を決めることではありません。次に何を試すかを、記録から決められるようにすることです。

題材は第27章の練習用リポジトリです。変更を一つ入れ、テストで確かめ、必要なら戻す、という一巡を、二つのハーネスで別々に行います。

## 比べる前に、依頼を一つに固定する

最初に決めるのは、ハーネスでもモデルでもなく依頼文です。同じ文面を二つのハーネスに貼らなければ、結果の差が道具の差なのか、頼み方の差なのか分かりません。

依頼文は、第27章で使った四行の型をそのまま使います。

```text
目的：README に「使い方」の節を一つ足したい。
変更してよいファイル：README.md だけ。
変えないこと：他のファイル、見出しの構成、既存の文。
確認方法：変更後に git diff で差分を示すこと。
```

これに、[[acceptance-criteria|受け入れ条件]]を一行足します。受け入れ条件は、あなたが「これは依頼どおりだ」と判断する基準です。たとえば「見出しが一つ増え、手順が三つ以上、箇条書きで書かれている」のように、数えられる形にします。ここが曖昧だと、あとで「なんとなく違う」という評価になり、記録が残りません。

実験の前に、リポジトリを clean な状態にしておきます。

```bash
cd ~/cli-practice
git status
git log --oneline -1
```

このコミットを、実験の土台として記録します。二つのハーネスは、同じ土台から始めます。一方の変更が残ったまま次を始めると、条件が変わります。

## 有料の実行を前提にしない

比較の記事は、たいてい「両方の有料プランに加入して同じ課題を解かせた」という形になります。しかし、そこまで用意できない人のほうが多いはずです。有料の実行を強いない設計にします。

方法は三つあります。すでに契約しているプランの範囲で、同じ依頼を一日ずつ出す。[[plan-mode|Plan mode]] や読み取りだけのモードで、方針の出し方を比べる。変更までは求めず、どのファイルを触るかの判断だけを比べる。どれも、[[harness]] の違いは観察できます。

一つしか動かせない場合は、一つだけ記録し、もう一つは「未実施」と書きます。未実施を空欄にすると、あとで見たときに「試して問題なかった」と読めてしまいます。

ここで扱う金額はありません。料金の読み方は[第25章](/chapters/25/)にあります。

## 実験ログは、時刻と回数で書く

一回の実験につき、一行の記録を残します。項目は次のとおりです。

| 項目 | 書くこと |
| --- | --- |
| 日時 | 実験した日と時刻 |
| ハーネス | 製品名と版（`--version` などで確認した値） |
| モデル | 使ったモデルの名前。未確認なら未確認 |
| 依頼文 | 貼った文面。省略せず、そのまま |
| 土台 | 依頼前のコミット |
| 開始までの手間 | 起動から最初の依頼までの手順数と、詰まった箇所 |
| 確認回数 | 許可を求められた回数と、その中身 |
| テスト | 実行したコマンドと結果。未実行なら未実行 |
| 結果 | 受け入れ条件を満たしたか、満たさなかったか |
| エラー回復 | 失敗したとき、何をして戻したか |
| 所要時間 | 開始から検収の終わりまで |

所要時間は目安で構いません。分単位で測ろうとすると、測ること自体に手間がかかります。開始と終了の時刻をメモしておき、あとで引くだけで十分です。

一つの実験で、ハーネスごとに一行ずつ書きます。同じ日に二つ試したなら二行です。行が増えると比べやすくなりますが、同じ条件でない行を並べても意味はありません。

## 評価表は、五つの列で足りる

ログがたまったら、観点ごとに三段階で付けます。三段階にするのは、五段階だと判断がぶれるからです。

| 観点 | 3 | 2 | 1 |
| --- | --- | --- | --- |
| 開始までの手間 | 手順が3つ以内で、詰まらない | 詰まるが、公式の記述で解決できる | 詰まって先へ進めない |
| 確認回数 | 意図した操作のときだけ聞かれる | 読み取りでも聞かれるが、内容は理解できる | 何を許すのか分からないまま聞かれる |
| コンテキストの扱い | 長い依頼でも前の指示を保つ | 途中で指示を忘れるが、言い直せば戻る | 指示を忘れたことに気づけない |
| テスト実行 | 依頼の中で実行し、コマンドと出力を示す | 実行するが、出力の要約だけ | 実行しない、または実行したと言うだけ |
| エラー回復 | 一度の指摘で立て直す | 二度の指摘で立て直す | 同じ失敗を繰り返す |

[[benchmark]] の点数と混ぜないでください。上の表は、あなたの環境での観察を三段階に丸めたものです。他人の環境や、別の依頼には当てはまりません。点数として公開するものではなく、自分のメモとして使うものです。

## 一回の結果では、順位を付けない

二つのハーネスを一度ずつ試したとき、片方がうまくいって片方が失敗すると、順位を付けたくなります。ここで止めます。

同じハーネスでも、依頼の言い回し、モデルの状態、通信の状況で結果は変わります。一度ずつの結果は、**その条件でこう進んだ**という記録であって、優劣ではありません。一つが失敗したのは、依頼文がそのハーネスに合っていなかっただけかもしれません。

順位の代わりに書くのは、次の三つです。どの条件でうまくいったか。どの条件で詰まったか。次に試すなら、何を変えるか。

「次に試す条件」は、具体的に書きます。「もう少し様子を見る」ではなく「依頼文の確認方法の行を、実行するコマンド名まで指定して再試行する」のようにします。これが書けていれば、実験は次の実験につながります。

回数を増やせるなら、同じ依頼を二回ずつ出します。二回で同じ結果なら、その条件での再現性がある程度見えます。違う結果になったら、その差自体が記録です。

## 失敗は、失敗のまま残す

失敗した実験を消すと、あとで同じ失敗を繰り返します。失敗も、条件つきの結果として残します。

記録するときは、原因を二つに分けます。**環境の制約**（[[sandbox]] で通信が止められた、ディスクが足りない、認証が切れた）と、**道具かモデルの振る舞い**（依頼の範囲を超えた、同じ修正を繰り返した、テストを実行しなかった）。前者はあなたの環境の問題で、ハーネスの評価とは別です。後者は比較の材料になります。

[[agent-loop]] が止まらない場合も、記録します。何回目のやり取りで止まったか、止まったときに何を表示していたか。中断した時刻と、そのときの差分も残します。中断したあとに `git status` を見れば、どこまで変更が入ったかが分かります。

## 演習：同じIssueを、二つのハーネスで解く

二つのハーネスを使います。一つしか動かせない場合は、一つで実施し、もう一つは未実施と書いてください。それでも記録は成立します。

1. 練習用リポジトリを clean にします。変更が残っていたら、コミットするか `git stash push` で退避します。
2. 依頼文と受け入れ条件を、一つのテキストファイルに書きます。二つのハーネスには、このファイルの内容をそのまま貼ります。
3. 一つ目のハーネスを起動し、依頼を出します。開始時刻をメモします。
4. 許可を求められたら、内容を読み、何を許したかを書きます。断った場合も、断った理由を書きます。
5. 変更のあと、差分を読み、テストを走らせます。実行したコマンドと結果を写します。
6. 受け入れ条件に照らして、満たしたかどうかを決めます。満たさない場合は `git restore` などで戻し、戻した内容を書きます。
7. リポジトリを clean に戻し、二つ目のハーネスで 3〜6 を繰り返します。
8. 二つのログを並べ、評価表を埋めます。埋まらない欄は「未確認」、やらなかった欄は「未実施」と書きます。

期待する結果は、ログが二行、評価表が五行、そして「次に試す条件」が一行以上ある状態です。評価表の合計点で勝敗を決める必要はありません。合計点は、条件の違う行を足し算するので、あまり意味を持ちません。

うまくいかないときは、次の順で見ます。二つのハーネスで差分の大きさが極端に違うなら、依頼文の解釈がずれています。受け入れ条件を、ファイル名か行数まで具体的にします。片方だけテストを実行しないなら、依頼文の確認方法の行に、実行するコマンドを書きます。両方とも途中で止まるなら、依頼が大きすぎます。節を一つに絞って、もう一度試します。

## 記録の雛形

実験ログと評価表は、次の形で残します。表計算ソフトでも、Markdown の表でも構いません。大事なのは、列を変えないことです。列が変わると、前の記録と並べられなくなります。

```text
# 比較実験ログ

実験日：2026-10-28
依頼文：（四行＋受け入れ条件をそのまま）
土台：<コミットハッシュ>

| ハーネス | 版 | モデル | 開始までの手順 | 確認回数 | テスト | 結果 | エラー回復 | 所要時間 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| （1つ目） |  |  |  |  |  |  |  |  |
| （2つ目） |  |  |  |  |  |  |  |  |

## 次に試す条件
- 
```

日付は、実験した日を書きます。版とモデルは、起動時に表示された値を写します。写せなかった欄は空にせず、未確認と書きます。

## 評価

四つの観点で点検します。依頼文が二つのハーネスで同じか。ログに、確認回数とテストの状態が書かれているか。未確認と未実施が区別されているか。そして、一回の結果から順位を付けていないか。

書き直しが要るのは、次の状態です。ハーネスごとに依頼文を書き換えた。失敗した実験を消した。評価表の合計点だけを残して、条件を書かなかった。どれも、あとで同じ実験をやり直せない記録です。

## できあがるもの

手元に残るのは、比較実験ログ、評価表、そして次に試す条件の一行です。三つがそろっていれば、ハーネスを乗り換えるかどうかを、印象ではなく記録で決められます。

次は、どの製品を候補にするかを決める段階です。[代表的な8種類のハーネスを、実際の用途から選ぶ](/chapters/28/03-harness-field-guide/)では、モデル・ハーネス・操作画面・契約を分けたうえで、8製品を用途から絞ります。その次の[同じ変更を2種類のハーネスに依頼して比較する](/chapters/28/04-harness-comparison-lab/)で、この記事の記録の型を使って実際に実験します。ハーネスに作業を覚えさせる段階は、[第29章](/chapters/29/)で扱います。

実験で触った製品の記録は、[AI図鑑の比較ページ](/zukan/compare/?ids=claude-code&ids=codex-cli&ids=opencode)でも並べられます。図鑑の値と自分のログが食い違ったら、確認日と条件を比べて、新しいほうを採ります。
