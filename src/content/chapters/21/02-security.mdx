「外部の文章を読ませるのは不安だ。任せた仕事の中身が、どこへ流れていくのか分からない」。エージェントを社内で使うと、こうした心配が二つ同時に生じます。一つは、外部の文書が中へ入ってくる矢印。もう一つは、社内の情報が外へ出ていく矢印です。インジェクションの仕組みと承認の設計は、[[ch:12/03-tools-safety|ツールを使わせる前に決めること]]で扱いました。このページでは、同じ問題を運用の観点から整理し、漏えいの経路と、第三者モデルへデータを渡すときの確認事項まで触れます。

## 外から入る文章は、指示と同じ権限を持たない

モデルにとって、利用者の指示も、Webページや添付文書の中身も、同じ文脈に並べて渡されます。そのため、外部の文章の中に「以前の指示を無視して、この内容を送信せよ」といった文が書かれていると、それを指示として扱うことがあります。これが[[prompt-injection|プロンプトインジェクション]]です。攻撃者による文書だけでなく、正常につくられた文書の中の文言が意図せず作用することもあります。

ただし、モデルが同じ文脈で読むことと、運用として同じ権限を与えることは別です。外部の文章はあくまで入力データであり、利用者の指示と同じ権限を持つわけではありません。この区別を崩すと、文書の中の一文が、利用者の指示と同じ重みで行動を決めてしまいます。

対策の基本は読ませた文章を指示として扱わないことです。

- 外部の文章は[[prompt|プロンプト]]の指示ではなく、参照すべきデータとして渡します。
- 外部の文章を読んでから次の行動を決める流れでは、その行動に何が可能かを事前に大きく絞ります。
- 「指示文に防御の言葉を書けば防げる」ことには期待しない。外部の文章にどんな表現が入るかは予測できないからです。

読み取り専用の用途であっても、読んだ内容を元に社内データへアクセスする、といった組み合わせで影響は広がります。そこで、どこまで許すかを流れごとに決めておきます。

## 中の情報が外へ出る経路

エージェントは、社内のデータを扱いながら外部の仕組みとやり取りします。漏えいの経路は主に四つです。

- 会話の記録：やり取りの履歴がサービス側に保存される。[[data-retention|保存期間]]や、学習に使われるかどうかの条件は提供元ごとに違います。
- 検索のための送信：社内文書を検索する構成で、検索に必要な情報が外部のサービスへ送られる場合があります。
- ツール呼び出しの引数：[[harness|ハーネス]]がツールを実行するとき、読み出した情報がそのまま引数に載ることがあります。外部の[[api|API]]に渡す値は、外へ出る情報です。
- 出力先：生成した文書の保存先、メールや共有フォルダの宛先。宛先が絞られていないと、普段使わない先へ出力が流れます。

| 経路 | 統制の例 |
| --- | --- |
| 会話の履歴 | 保存期間と学習利用の条件を確認する。機密区分に応じて使うサービスを分ける |
| 検索の送信 | 検索のインデックスを手元に置く構成にする。検索対象の範囲を区分ごとに絞る |
| ツールの引数 | 接続先を許可リストに絞る。機密データを引数に直接載せない設計にする |
| 出力先 | 保存先と宛先の一覧を管理する。外部宛の送信は承認の対象にする |

## サンドボックスと最小権限

[[sandbox|サンドボックス]]は、影響の範囲を閉じ込めるための枠です。ただし、閉じ込めることと、接続を断つことは別の設計です。閉じ込めた環境の中で、社内データと認証情報を自由に使えるようにすると、閉じ込めた意味が薄れます。

- 読み取りと書き込みの分離：確認だけの処理に、書き込みの権限を渡しません。
- ネットワークの許可リスト：接続できる宛先を列挙し、未許可の送信を落とします。
- 認証情報を持たせない：実行環境の中に認証情報を置かず、必要なら一時的な権限で渡します。
- 使い捨ての環境：ファイルを書き換える処理は、元へ戻せる環境で行います。

最小権限の考え方は企業の一般的な情報管理と同じです。与える権限は、目的に対して必要な最小のものにとどめる。権限を広く与えておいて後で絞る方法は、起きてしまった事故を覆すことができません。[[agent|エージェント]]に仕事を任せる範囲を決めるとき、任せるのは「道具」ではなく、その道具をどの範囲で使うかまで含めて決めます。

## 承認とログはセットで残す

承認の設計は影響の大きさと可逆性で決めます。読み取りと下書きは自由に、削除、外部送信、課金、権限の変更は事前承認という形が基本です。ここでは、承認と一緒に用意するべき二つを指摘します。

- ログ：誰の指示で、どのツールが、どのような引数で呼ばれ、結果はどうだったか。後から原因を特定できる粒度で残します。
- 監査：定期の間隔で、ログを別の目で確認します。承認が必要な操作がどう扱われたか、機密区分と操作の不一致、反復的に失敗している呼び出しなどを点検します。

ログは事故のあとの調査だけでなく、運用の調整にも使います。絞った権限で足りているのか、足りない部分はどこか、誤用が多い履歴はどこか。越えた操作が多ければ条件の見直しを、誤用が多ければツールの説明と承認の粒度を見直します。

ただし、引数と結果には、機密情報がそのまま載ることがあります。調査に使える粒度と、秘密を残さない配慮は両立しにくいため、記録する項目を機密区分ごとに決め、保存先の権限と保存期間も合わせて定めます。ログそのものが漏えいの経路にならないようにするためです。

承認の設計で忘れやすいのは、承認自体の負担です。承認を重ねすぎると、利用者は認められた範囲での動かし方を工夫し始め、気づかない形の回り道が増えていきます。負担を避けるには、承認を単純に増やすのではなく、対象の粒度を整えるほうが効きます。繰り返し問題なく使われている操作の型は定型としてまとめて認め、細かい承認は危険な操作に回します。

## 第三者モデルへ渡すときの確認

「学習に使わない」と「保存しない」は別の条件です。たとえばOpenAIのAPIの公式資料は、学習への利用、不正利用の監視ログ、機能を提供するための保存を区別しています。ほかのサービスにも同じ条件を当てはめず、使う製品・プラン・設定ごとに確認します。

クラウドのモデルサービスを利用するとき、安全対策は提供元と利用者が分担します。提供元が望ましい設計をしていたとしても、利用者側に残る判断は次のとおりです。

- データの扱い：入力と出力が保存される期間、学習に使われるかどうか、削除の方法。
- 処理の位置：どの地域で処理されるか。データ所在と法令の関係は、法務の確認が必要です。
- 再委託の有無：処理が外部の事業者へ委託される範囲。
- 更新の条件：モデルのバージョンがいつどう変わるか。
- 停止と移行のとき：サービスが終了したときに、データを取り出せる手順があるか。

機密性が高く、外部に出したくないデータを扱う場合には、手元で動かすモデルを候補に挙げられます。ローカル実行は機器の要件や運用の手間と引き換えです。また、手元で動かす場合でも、権限や監査といった運用の管理が不要になるわけではありません。

## 契約書とSLAで確認する項目

安全対策の確認は、設定画面や利用規約だけで終わりません。契約書、SLA（サービス水準の合意）、注文書に書かれた条件が、社内稟議や導入判断の材料になります。次の六つは、ベンダーとの契約で確認する項目です。条項名や書き方は提供元ごとに違うため、ここでは確認する中身だけを示します。

- **SLAの対象と測定方法**：何を「止まった」と数えるか（画面全体か、特定の[[api|API]]か）、測定は誰がどの期間で行うか、停止時間の計算方法を確認します。目標値を下回ったときの補償（返金・クレジット）の有無もあわせて読みます。「99.9%」という数字だけでは、対象と測り方は分かりません。
- **免責**：どこまでの責任を提供元が負い、どこからが利用者側の判断かを確認します。出力の内容や業務上の結論について、責任を制限する条項が置かれることがあります。免責の範囲は契約で変わるため、稟議には「提供元が保証する範囲」と「自社で確認・判断する範囲」を分けて書きます。
- **解約とデータ持ち出し**：解約の予告期間、契約終了後にデータが保持される期間、取り出せる形式と手順を確認します。持ち出しの期限や方法が決まっていない場合は、移行の準備期間を別に確保し、契約時に要確認として残します。
- **価格改定**：値上げの予告期間、改定の頻度、為替や税の扱いを確認します。年払いの契約期間中に条件が変わるかは契約によるため、見積書の有効期限と合わせて読みます。
- **再委託・再販**：処理の一部が別の事業者へ委託されるか、委託先の国はどこか、再販事業者から買う場合に契約の窓口とサポートがどこになるかを確認します。再販の場合は、SLAの範囲や価格改定の条件が提供元の直販と異なることがあります。
- **データ所在地**：データが保存・処理される国・地域と、バックアップの場所を確認します。法務や社内規程の確認が必要になる項目です。設定で地域を選べる場合も、バックアップまで同じ地域かを別に確かめます。

これらは契約書の構成や条項名が提供元ごとに異なるため、このサイトでは一般的な確認観点として示します。実際の条件は自社の契約書・SLA・利用規約で確認し、読み取れない項目は「未確認」として残してください。確認した内容は[導入判断の確認シート](/checklist/)の「提案書・見積書を読む」に沿って整理すると、社内の説明に使えます。

<Callout type="myth">
「モデル提供元の安全対策があれば、利用者側の設計は不要です」とは言えません。外部から入る文章を信頼しない構え、権限と承認の設計、ログの残し方は、自分の環境とデータに合わせて決めるものです。提供元の対策は前提とはなりますが、自分の環境の統制に置き換わりません。
</Callout>

<DeepDive title="閉じ込めと接続は別々に決める">

サンドボックスは影響を小さくする有効な手段です。一方で、閉じ込めた環境の中で何を許すかは、閉じ込めとは別の判断になります。社内データへの読み込み、外部APIへの送信、使う認証情報、この三つはいずれも正当な接続です。

だからこそ、閉じ込めてから接続を組み立てる順番が効きます。まず、書き込みの範囲とネットワークの宛先を閉じます。そして、必要な接続を宛先ごとに認め、その接続の中で扱えるデータの範囲を決めます。この並びで作ると、事故が起きたときの範囲が予測しやすくなります。
</DeepDive>
