「結局、どのモデルが一番いいの？」。この問いに対して、このサイトは**単一の答えを出しません**。理由は、モデルの優劣が、使う場面の条件に強く依存するからです。ここでは、その理由と、代わりに持つべき選定の軸を整理します。

## 一つの順位に押し込められない

モデルに求めるものは、場面によって変わります。

- 長い契約書を読み、根拠付きで要約したい。
- 問い合わせに、1秒以内で一次回答を返したい。
- 社内のコードベースを理解して、修正案を出したい。
- 大量の商品説明を、低コストで分類したい。
- 画像や表を含む資料から、数値を抽出したい。

これらは、必要な能力も、許容できる遅延も、単価も違います。一つの総合スコアで並べると、**どの条件をどれだけ重く見たか**が失われます。

## 選定の軸を自分で持つ

実務では、次の軸を並べて比較します。

| 軸 | 見ること |
| --- | --- |
| 品質 | 自社の代表タスクで、正答率・根拠の正確さ・指示追従を測る |
| 速度 | 初回応答までの時間（TTFT）、1秒あたりの出力トークン数 |
| 価格 | 入力・出力の単価、キャッシュ、バッチ割引、想定利用量 |
| 文脈長 | 扱いたい文書の長さ、長文での品質低下 |
| 入出力 | 画像・音声・PDF・ツール呼び出しへの対応 |
| データ | 入力が学習に使われるか、保存期間、リージョン |
| 運用 | APIの安定性、レート制限、障害時の代替、サポート |
| 移植性 | オープンウェイトか、自前環境で動かせるか |

すべてを満たすモデルは通常ありません。**何を犠牲にできるか**を決めるのが、選定です。

## 条件が変われば答えも変わる

同じ会社でも、用途ごとにモデルを分けることは珍しくありません。

- 一次対応や分類には、安くて速いモデル。
- 複雑な推論や最終確認には、品質の高いモデル。
- 機密性の高い処理には、自前環境のオープンウェイトモデル。
- 長文の処理には、コンテキスト長と長文品質を確認したモデル。

これは「上位モデルを一部だけ使う」というより、**工程ごとに適した道具を割り当てる**考え方です。ルーティングやフォールバックを組み合わせる設計も、この延長にあります。

<Callout type="myth">
「ベンチマークで1位のモデルを選べば間違いない」とは限りません。ベンチマークは特定の課題・条件での測定で、汚染や形式の違い、測定日の差があります。また、1位の差が実用上意味のある差とは限りません。自社のタスクで試すまで、そのモデルが自社にとって最適かは分かりません。
</Callout>

<DeepDive title="評価は平均ではなく分布で見る">
  モデルの品質を一つの平均値で見ると、苦手な入力を見落とします。たとえば、平均正答率が高くても、特定の形式の表や、専門用語の多い文書で急に失敗することがあります。

  自社の評価では、代表タスクを分類し、それぞれの成功率と失敗の種類を見ます。「どのくらい正しいか」だけでなく、「どう間違えるか」を知ることが、運用の設計に直結します。
</DeepDive>

## ランキングとの付き合い方

ランキングは、候補を絞る入口としては便利です。ただし、次の点を確認します。

1. 何を測っているか。課題、言語、入力の長さ、評価方法。
2. いつ測ったか。モデルは更新される。古い順位は参考にならない。
3. 誰が測ったか。提供元、独立系、コミュニティ。利害関係。
4. 差はどれくらいか。誤差の範囲か、実用上意味のある差か。
5. 自分の条件に近いか。言語、文書の種類、ツール利用の有無。

ランキングは「答え」ではなく「仮説」です。採用の判断は、自社の小さな評価で行います。

## このサイトが順位を出さない理由

モデルは頻繁に更新され、価格も条件も変わります。固定した順位を載せると、すぐに古くなり、誤解を生みます。そこでこのサイトでは、**比較の軸と読み方**を示し、具体的な価格・文脈長は確認日付きのデータとして掲載します。
