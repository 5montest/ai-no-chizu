エージェントが返す変更はたいてい筋が通って見えます。文章も整っていて、意図も説明されています。それでも、そのまま受け取ってはいけません。他人の書いたコードを受け取るときと同じで、差分を読み、テストを走らせ、説明と現物が合っているかを確かめる必要があります。この記事では、その一連を**検収**と呼びます。

前の記事で作った練習用リポジトリをそのまま使います。まだ作っていない場合は、[三つのCLIを、同じ手順で試す](/chapters/27/01-three-clis/)の演習まで済ませてください。

## 検収は三つの問いで足りる

読むべき量を増やしすぎると、かえって読まなくなります。問いは三つに絞ります。

**何が変わったか**：変更されたファイルと行を、実際の差分で見ます。エージェントの説明ではなく、`git diff` の出力が根拠です。

**頼んだとおりか**：頼んだ範囲を超えていないか、頼んだ内容が入っているか。余計な整形や、関係のないファイルの変更が混ざっていないかを見ます。

**戻せるか**：まずいと分かったときに、元へ戻す手段があるか。Git で戻せる状態を保っていれば、判断を間違えてもやり直せます。

この三つが埋まらないまま次の依頼へ進むと、変更が積み上がって、どれがどの依頼の結果か分からなくなります。

## 依頼の前に、戻せる状態を作る

最初に作業ツリーの状態を見ます。

```bash
git status
```

変更が何も無い、または自分が意図した変更だけであることを確かめます。心当たりのない変更があれば、先に処理します。コミットするか、あとで使うなら退避します。ここを飛ばすと、エージェントの変更と自分の変更が同じ差分に混ざり、切り分けられなくなります。

```bash
git status --short
git log --oneline -1
```

`git log` は、いまどのコミットを土台にしているかの記録です。検収メモにこの二つを写しておくと、あとで同じ状態を再現できます。

## 依頼は一つ、変更は小さいほど読める

依頼文は次の四つを含めて書きます。長い文章は要りません。四行で足ります。

```text
目的：README に「使い方」の節を一つ足したい。
変更してよいファイル：README.md だけ。
変えないこと：他のファイル、見出しの構成、既存の文。
確認方法：変更後に git diff で差分を示すこと。
```

**変更してよいファイル**を名指しすると、検収の対象が狭まります。名指ししないと、エージェントは目的を達成するために周辺のファイルへ手を広げることがあります。悪意ではなく、親切の結果です。

**変えないこと**は、依頼の意図を守るための行です。整形だけの変更や、ついでの修正は、差分を読む負担を増やします。

大きな依頼を一つ出すより、小さい依頼を三つ出したほうが、検収は速く終わります。差分が読める大きさを保つことが、結果として品質を上げます。

## テストは、プロジェクトに元からあるコマンドで走らせる

テストの話になると、いちばん危ないのが「通りました」の一言です。実行したコマンドと出力が示されていない「通りました」は、確認済みではありません。**未確認**として扱い、何を実行したかを尋ねます。

まず、プロジェクトに元からあるテストの実行方法を自分で探します。`package.json` の `scripts`、`Makefile`、`README` の開発手順のどれかに書かれています。そこに無いコマンドをエージェントが提案してきたら、そのコマンドが何をするのかを先に読みます。存在しないテストを「追加して通した」と言われた場合は、追加されたテスト自体が検収の対象になります。

結果は三つに分けて記録します。実行して成功した。実行して失敗した。実行していない。この三つを混ぜると、あとで「たしか通っていたはず」という記憶だけが残ります。失敗した場合は、失敗の出力をそのまま残します。要約させると、原因の行が落ちることがあります。

サンドボックスの制約で通信が止められている場合、依存の取得を伴うテストは失敗します。これはコードの問題ではありません。環境の制約としてメモに分けて書き、判断を混ぜません。

## 新規ファイルは、git diff に出ない

エージェントがファイルを新しく作った場合、`git diff` にも `git diff --stat` にも出ません。追跡されていないファイルは差分の対象外だからです。差分が空でも「変更なし」とは限りません。

```bash
git status --short
git status --porcelain --untracked-files=all
```

`??` は追跡されていないファイル、`M` は変更されたファイル、`A` はステージに追加されたファイルです。`??` の行があれば、その中身を読み、依頼の範囲内かを確かめます。範囲外なら、その試行は「範囲を超えた」として記録し、作業ディレクトリごと捨ててやり直します。

`--untracked-files=all` を付けると、ディレクトリ単位ではなくファイル単位で `??` が出ます。付けないと、新規ディレクトリの中身がまとめて1行になり、何が増えたかを読み落とします。同じ手順は[同じ変更を2種類のハーネスに依頼して比較する](/chapters/28/04-harness-comparison-lab/)でも使っています。

どのコマンドが何を見せて、何を見せないかを並べると、次の表になります。

| コマンド | 何が出るか | 見落としやすいもの |
| --- | --- | --- |
| `git diff` | 追跡済みファイルの、まだステージしていない変更 | ステージ済みの変更、新規ファイル |
| `git diff --staged` | ステージに上げた変更 | 作業ツリーに残る未ステージの変更 |
| `git diff --stat` | ファイルごとの変更行数 | 行数が0件のファイル、新規ファイル |
| `git status --short` | `M`（変更）`A`（追加）`??`（未追跡）の一覧 | 変更の中身（差分そのもの） |
| `git status --porcelain --untracked-files=all` | 未追跡ファイルを1件ずつ | 中身は別途、ファイルを開いて読む |

`git diff` だけを見て「変更なし」と判断しないのは、この表の2列目と3列目がずれるためです。検収では、状態の一覧（`git status`）で範囲を確かめ、差分（`git diff`）で中身を読み、テストで結果を確かめる、という順に重ねます。

## git diff は上から全部読む

差分は、量が少ないうちに全部読みます。

```bash
git diff --stat
git diff
```

`--stat` で全体の大きさを見てから、ファイルごとの差分を読みます。読み方を決めておくと速くなります。削除された行（`-`）から先に読み、何が失われたかを見る。追加された行（`+`）は、その意図を一行ずつ確かめる。行末の空白だけの変更や、改行コードの変更が混ざっていたら、それは内容の変更ではありません。混ざったままにすると、次から本当の変更が見えにくくなります。

読み飛ばしてよいのは、生成物と明示されているファイルだけです。 lock ファイルやビルド成果物は、差分が大きく、目で追っても意味が取りにくいものです。ただし、勝手に更新されていないかを確認する対象ではあります。更新が必要な場面なら、内容の変更とは別のコミットに分けます。

差分が大きすぎて読めないときは、読むのを諦めるのではなく、依頼を分割してやり直します。読めない差分を受け入れることは、検収しないことと同じです。

## 要約と差分を突き合わせる

エージェントは最後に変更の要約を返します。この要約は便利ですが、根拠ではありません。要約と差分が食い違ったら、差分が正しいと考えるのが原則です。

食い違いはいくつかの型で現れます。触っていないと言ったファイルが差分に出ている。頼んでいない整形が混ざっている。テストを実行したと書いてあるが、出力が無い。意図した変更の一部が入っていない。どれも、要約を読んだだけで済ませると見落とします。

突き合わせは要約の各行を差分の該当箇所へ対応づける作業です。対応づかない行があれば、その行は未確認です。

## 戻す手段は Git にする

戻す操作はGit のコマンドで行います。エージェントに「元に戻して」と頼む方法もありますが、その結果もまた検収の対象です。自分で戻せる状態を保っておけば、判断を誤っても被害は小さく済みます。

作業ツリーの変更を捨てて、インデックスの内容に戻すには次のとおりです。

```bash
git restore README.md
```

ステージに上げた変更を取り消して、インデックスの状態を戻すには `--staged` を付けます。

```bash
git restore --staged README.md
```

公式の説明では、`git restore` は作業ツリーのパスを復元するコマンドで、既定ではインデックスから、`--staged` を付けたときは HEAD から復元します。つまり、**コミットしていない変更は、この操作で失われます**。実行する前に `git diff` で内容を確かめ、残したい変更はコミットするか退避します。

いったん横に置いて、あとで戻したい場合は退避を使います。

```bash
git stash push -m "検収前の状態"
git stash list
git stash pop
```

`git reset --hard` は使いません。作業ツリーの変更をまとめて消すため、消えた内容は戻せません。使う場面が本当にあるとしても、検収の練習では使いません。

[[plan-mode|Plan mode]] のある道具では、変更の前に方針だけを出させ、方針と差分を比べることもできます。OpenCode なら Tab キーで切り替えます。方針と実装が食い違ったときは、どちらが正しいかを決めるのは自分です。

## 演習：小さな変更を一巡する

前の記事の練習用リポジトリで、変更を一つだけ入れて、検収まで通します。

1. リポジトリへ移動し、状態を確認します。

```bash
cd ~/cli-practice
git status
```

2. エージェントを起動し、四行の依頼を出します。ファイルは `README.md` だけ、見出しの構成は変えない、と明示します。

3. 許可を求められたら、内容を読んでから許可します。書き込みの許可と、コマンド実行の許可は別ものです。何を許したかをメモに残します。

4. 変更のあと、差分を読みます。

```bash
git diff --stat
git diff
```

5. 期待と違う点があれば、戻します。まず内容を確かめてから実行します。

```bash
git restore README.md
```

6. 期待どおりなら、コミットします。メッセージは自分で書きます。エージェントに書かせた場合は、要約が差分と合っているかを確かめてから使います。

```bash
git add README.md
git commit -m "README に使い方の節を追加"
```

期待する結果は、差分が1ファイルだけ、追加行が十数行以内、他のファイルに変更が無い状態です。加えて、許可の記録とテストの状態（実行したか、していないか）がメモに残っていれば成功です。

うまくいかないときは、次の順で見ます。差分に身に覚えのないファイルが出たら、`git status` で全体を確認し、そのファイルを触った心当たりを探します。`git restore` で戻したはずの変更が残っていたら、ステージに上がっていないかを `git status` で確かめます。テストが環境の制約で落ちるなら、コードの問題と分けて記録します。エージェントが同じ変更を繰り返し提案する場合は、依頼文の「変えないこと」が伝わっていない可能性があります。依頼を短くして、条件を一行増やします。

## 検収メモの形

一件の依頼につき、次の項目を残します。表にしておくと、あとで見返せます。

| 項目 | 書くこと |
| --- | --- |
| 依頼 | 目的と、変更してよいファイル |
| 土台 | 依頼前のコミット |
| 差分 | 変更ファイル数と、読んだ範囲 |
| テスト | 実行したコマンドと結果、または未実行 |
| 許可 | 何を許可したか |
| 判断 | 受け入れた、戻した、やり直した |
| 気づいたこと | 要約と差分のずれ、迷った点 |

## 評価

四つの観点で点検します。差分を最後まで読んだか。テストの状態を、実行・失敗・未実行のどれかで書いたか。要約ではなく差分を根拠に判断したか。戻す操作の前に、失われる内容を確かめたか。

書き直しが要るのは、次の状態です。差分を読まずに受け入れた。テストの「通りました」をそのまま信じた。戻したときに、消えた変更の内容を説明できない。どれも、次に同じ状況が来たときに再現できない進め方です。

## できあがるもの

手元に残るのは、検収メモと、意図した変更だけを含むコミットです。差分が読める大きさに保たれていれば、次の依頼も同じ調子で進められます。

ここまでで、CLI エージェントを導入し、変更を検収する一巡ができました。次は、同じ仕事を複数のハーネスで比べる段階です。[第28章](/chapters/28/)では、比較の観点を決めて記録する型を作ります。触った製品の記録は[AI図鑑の比較ページ](/zukan/compare/)で並べられるので、自分のメモと突き合わせておくと、判断の材料が揃います。
