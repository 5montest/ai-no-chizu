前の記事では、一つの作業ディレクトリの中で役割を分けました。この記事では、作業ディレクトリそのものを分けます。二つの仕事を同時に進めたいとき、同じ場所で動かすと、片方の変更がもう片方の足元を崩します。Git の worktree を使えば、履歴は共有したまま、作業場所を分けられます。

前提は、第27章の練習用リポジトリと、Git の基本操作です。`git status`、`git diff`、`git commit` が分かっていれば足ります。

## 並列の費用は、統合のときに払う

並列にすると速くなる、という説明は半分だけ正しい。二つの作業が同時に進むので、終わるまでの時間は縮むことがあります。しかし、そのあとに統合の作業が残ります。マージし、競合を解決し、統合後の状態でもう一度テストを走らせ、差分を読み直す。この時間は、並列にした分だけ増えます。

起動の時間も馬鹿になりません。worktree は新しいチェックアウトなので、依存のインストールや環境ファイルの用意が要ります。エージェントの起動そのものより、この準備のほうが長くかかることがあります。

だから、並列の評価は「終わるのが何分早かったか」ではなく「統合まで含めて何分かかったか」で行います。この記事の演習では、統合の時間を項目として記録します。

## worktree は、履歴を共有して作業場所を分ける

Git の公式の説明では、リポジトリは複数の作業ツリーを持て、`git worktree add` で作った作業ツリーは「linked worktree」と呼ばれます。元の場所は「main worktree」で、リポジトリには main worktree が一つと、linked worktree がゼロ個以上ある、という形です。

共有されるのは履歴とリモートです。共有されないのは、HEAD やインデックスといった、作業ツリーごとのファイルです。この違いが、並列の練習では重要になります。コミットは全員の履歴に載りますが、ステージの状態は場所ごとに別です。

作り方は二通りあります。パスだけを渡すと、パスの最後の要素を名前とするブランチが自動で作られます。ブランチ名を決めたいときは `-b` を使います。

```bash
git worktree add ../cli-practice-readme -b task-readme
git worktree add ../cli-practice-test -b task-test
```

同じブランチを二つの worktree で同時に使うことはできません。既に他の worktree でチェックアウトされているブランチを指定すると、`--force` を付けない限り拒否されます。これは制限ではなく、事故を防ぐ仕組みです。同じブランチを二か所で触ると、どちらの変更が正しいかを Git が判断できません。

一覧と削除は次のとおりです。

```bash
git worktree list
git worktree remove ../cli-practice-readme
```

`remove` は、未追跡ファイルも変更も無い、きれいな worktree しか消せません。汚れている場合は `--force` が要ります。main worktree は消せません。

## エージェントに worktree を使わせる

Claude Code という[[harness]]には、起動時に worktree を作る指定があります。`claude --worktree <name>` で、`.claude/worktrees/<name>/` に作業場所ができ、ブランチ名は `worktree-<name>` になります。作成先を `.gitignore` に入れておく必要がある、と公式に書かれています。

注意すべきは、これが新しいチェックアウトだという点です。依存パッケージや `.env` のような、コミットされていないファイルは入っていません。公式には、必要なファイルを `.worktreeinclude` に書いて持ち込む方法が説明されています。

サブエージェントに worktree を割り当てることもできます。frontmatter に `isolation: worktree` を書くと、その実行ごとに一時的な worktree が作られ、変更が無ければ終了時に削除されます。

ただし、隔離は完全ではありません。worktree は作業場所を分ける仕組みで、[[sandbox]]のように触れる範囲を制限するものではありません。公式には、検査の仕組みが追える操作と追えない操作が分かれていて、シェルのコピーやリダイレクトによる書き込みは追わないと書かれています。読み取れない形のコマンドについては、検査を無効にできないとも書かれています。worktree を使っていても、`git status` で本体側の状態を確かめる習慣は残してください。

## 分担はファイルの境界で切る

並列にしてよいかどうかは、仕事の形で決まります。基準は一つで、触るファイルが重ならないことです。

重ならない例は、README の節を足す仕事と、テストファイルを一つ足す仕事です。ディレクトリが違えば、まず競合しません。モジュールを分けた実装も同じです。

重なる例は、同じ関数を直しながら、その関数のテストも直す仕事です。これは一つの仕事として、順番に回します。テストと実装を別の人に任せると、同じファイルを触りがちです。

境界を決めるときは、依頼文に「触ってよいファイル」を書くだけでは足りません。worktree ごとに、触ってよいディレクトリを明記します。書かないと、エージェントは目的を達成するために、隣のディレクトリへ手を広げます。

## 統合の順番と、競合したときの判断

統合は、小さい差分から行います。小さいほうを先にマージすると、大きいほうが追従する範囲が狭く済みます。逆にすると、大きい差分の上に小さい差分を載せることになり、競合の解決が難しくなります。

競合が出たときは、「どちらが正しいか」ではなく「どちらの意図を残すか」で考えます。両方の意図が要るなら、両方を残す形に書き直します。片方が古い前提に立っているなら、新しいほうを採ります。判断がつかないときは、その場でマージを中断し、両方の依頼文を読み返します。競合は、多くの場合、依頼の切り方の問題です。

統合後のテストは、必ずまとめて走らせます。worktree ごとに通っていたテストは、統合後の状態で通るとは限りません。テストの実行結果は、統合前と統合後の二つを記録します。

統合が終わったら、結合済みの差分を自分で読みます。ここは第27章の検収と同じです。二つの差分を合わせたものが、依頼の全体として筋が通っているかを見ます。片方ずつは正しくても、合わせると重複した実装になっていることがあります。

## 演習：二つのworktreeを作り、統合まで通す

練習用リポジトリで、競合しない仕事を二つ用意します。片方は `README.md` の節を一つ足す仕事、もう片方は `test/` に小さなテストを一つ足す仕事です。

1. 本体のリポジトリを clean にします。`git status` と `git log --oneline -1` で土台を記録します。
2. worktree を二つ作ります。ブランチ名は `task-readme` と `task-test` にします。
3. 一つ目の worktree に移動し、エージェントを起動します。依頼文に「触ってよいのは `README.md` だけ」と書きます。開始時刻を記録します。
4. 差分とテストを確かめ、コミットします。終了時刻を記録します。
5. 二つ目の worktree でも同じ手順を繰り返します。こちらは「触ってよいのは `test/` 配下だけ」と書きます。
6. 本体に戻り、小さいほうのブランチから順にマージします。マージの開始と終了の時刻を記録します。
7. 統合後の状態でテストを走らせます。実行したコマンドと結果を記録します。
8. 統合後の差分を読み、二つの仕事が重複していないかを確かめます。
9. `git worktree remove` で二つの作業場所を片付けます。残っていたら `git worktree list` で確認します。

余力があれば、同じファイルを触る仕事を二つ用意して、わざと競合させます。競合の解決にかかった時間が、そのまま「同じファイルを並列にした費用」になります。

期待する結果は、競合しない仕事では統合が数分で終わり、競合する仕事では解決に時間がかかる、という形です。どちらも結果として残します。速く終わらなかった演習は、失敗ではなく、判断の材料です。

この記事では、実測値を挙げません。手元のリポジトリの大きさや、依存の数で結果は変わります。

## つまずいたときの見方

`git worktree add` が拒否されるときは、ブランチが既にどこかでチェックアウトされています。`git worktree list` で確認し、別のブランチ名にするか、既存の作業場所を片付けます。

worktree でテストが動かないときは、依存が入っていません。新しいチェックアウトなので、インストールからやり直します。`.env` が要るプロジェクトなら、`.worktreeinclude` に書くか、手で用意します。

エージェントが本体側のファイルを書き換えているときは、隔離の検査が追えない操作を使っています。`git status` を本体で実行し、差分を確かめます。worktree の中だけで作業しているつもりでも、確認は省けません。

マージで同じ行が何度も競合するときは、二つの仕事の境界が曖昧です。片方の依頼を、別のファイルへ移せないかを考えます。

## 統合コストの記録

並列の実験では、次の項目を残します。起動と待ちの時間より、統合の列のほうが大事です。

| 項目 | 書くこと |
| --- | --- |
| 土台 | 開始時のコミット |
| worktree | パスとブランチ名、作成にかかった時間 |
| 準備 | 依存のインストールや環境ファイルの用意にかかった時間 |
| 実行 | 二つの仕事の開始・終了時刻 |
| マージ | 順番と、マージにかかった時間 |
| 競合 | 件数と、解決にかかった時間 |
| 検証 | 統合前と統合後に実行したコマンドと結果 |
| 合計 | 起動から検収までの時間 |
| 単独との比較 | 同じ二つの仕事を順番にやった場合の時間（推定でよい。推定と書く） |

最後の行は、推定でかまいません。推定と明記すれば、記録として使えます。実測したように書くことだけが問題です。

## 評価

四つの観点で点検します。二つの仕事の触るファイルが重なっていないか。競合が出たときに、意図で判断したか。統合後のテストを実行したか。そして、統合の時間を記録したか。

書き直しが要るのは、次の状態です。並列にした回の時間だけを比べて、統合の時間を除いた。競合を消すために片方の変更を捨てた。統合後のテストを、統合前の結果で代用した。どれも、並列が得だったかどうかを判断できない記録です。

## できあがるもの

手元に残るのは、統合済みの差分と、統合コストの表です。この二つがあれば、次に同じ形の仕事が来たときに、分けるか順番に回すかを、記録で決められます。

第30章の三つの記事で、計画と実行を分けること、役割を分けること、作業場所を分けることを扱いました。どれも、分けたあとの統合まで含めて測るのが要点です。分担は、速さを買う方法ではなく、独立した視点と作業場所を買う方法です。費用は統合で払います。

次は、テキスト以外を扱うモデルに進みます。音声の書き起こし、読み上げ、画像の理解、判定用の小さなモデルを、どう組み合わせるか。[第31章](/chapters/31/)で扱います。

作業の記録は、[AI図鑑の比較ページ](/zukan/compare/?ids=claude-code&ids=opencode&ids=codex-cli)の値と並べておくと、あとで製品を選び直すときの材料になります。図鑑の値にも確認日があるので、自分の記録の日付と見比べてください。
