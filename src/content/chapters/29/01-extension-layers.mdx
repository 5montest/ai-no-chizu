「[[skill|Skills]] を入れた」「MCP につないだ」「[[hook|Hook]] を書いた」。どれも拡張の話ですが、拡張している対象は別々です。同じ「拡張」という言葉でまとめると、何を設定すれば何が変わるのかが分からなくなります。

この記事では、五つの名前を層に分けます。製品ごとに呼び名が違うものもあるので、まず概念の名前を置き、そのあとで各製品が何と呼んでいるかを並べます。

<GuideImage name="extension-layers" />

## 名前が混ざるのは、層が違うから

混ざりやすいのは、次の五つです。

- Tool：モデルが呼び出せる一つの操作。ファイルを読む、コマンドを実行する、検索する、といった単位。
- MCP：Tool を外から持ち込むための規格。サーバーを立て、クライアントが接続する。
- Hook：ハーネスの決まった時点で、自動で走る処理。ツール実行の直前、セッションの終了など。
- Skill：手順書。名前を付けた作業の進め方を、必要なときだけ読み込ませる。
- [[plugin|Plugin]]：機能や設定をまとめて配布する単位。含まれる部品や、有効にするための操作は製品によって異なる。

層として見ると、順番があります。Tool は一番下の部品です。MCP はその部品を外から供給する経路です。Hook はハーネスの動きに割り込む差し込み口です。Skill はモデルに渡す指示の束です。Plugin はそれらを梱包して配る箱です。

箱（Plugin）と中身（Skill・Hook・MCP）を同じ段に並べると、話がかみ合わなくなります。「Plugin を入れたら Skill が使えるようになった」は、箱を開けたら手順書が入っていた、というだけの話です。

## 五つを、一枚の表にする

表にすると、どこを拡張するのかが見えます。配置先とスコープの例はClaude Codeのものです。CodexやOpenCodeへ、そのまま同じ設定ファイルを移すことはできません。

| 名前 | 拡張する対象 | 何を書くか | 有効になる範囲 |
| --- | --- | --- | --- |
| Tool | モデルが呼べる操作 | 名前・説明・入力の形 | ハーネスが用意した分と、MCP から来た分 |
| MCP | 外部のツールとデータへの接続 | サーバーの起動方法か接続先 URL | ローカル・プロジェクト・ユーザーの三つのスコープ |
| Hook | ハーネスの決まった時点の処理 | イベント名と実行するコマンド | 設定ファイルの階層ごと |
| Skill | 作業の手順と判断基準 | `SKILL.md` に手順と注意 | プロジェクト、個人、プラグイン |
| Plugin | 複数コンポーネントの配布単位 | manifest と中身のディレクトリ | インストールしたスコープ |

[[mcp]] は規格の名前で、製品名ではありません。Claude Code も Codex も OpenCode も、それぞれ独自に MCP のクライアントを持っています。だから「MCP に対応している」は、MCP で接続する機能があるという意味で、つなげば何でも使えるという意味ではありません。[[function-calling]] との違いも、ここで分かれます。Tool を呼ぶ仕組みはハーネス側にあり、MCP はその Tool の供給元を外に開く規格です。

## Skill は、手順書で、コマンドにもなる

Skill の実体は`SKILL.md` という一つの Markdown ファイルです。公式ページの表現では、指示を書いたファイルを置くと、その作業を Skill として呼べるようになります。

大事な性質が二つあります。一つは、本文が使うときだけ読み込まれること。指示ファイルのように毎セッション全文が載るのではなく、必要になった時点で読み込まれます。

もう一つは、コマンドと統合されていることです。`.claude/commands/deploy.md` と `.claude/skills/deploy/SKILL.md` は、どちらも `/deploy` という呼び出しを作ります。

置き場所は、プロジェクトなら `.claude/skills/<skill-name>/SKILL.md`、個人用なら `~/.claude/skills/<skill-name>/SKILL.md` です。プラグインに入っている Skill は `/plugin-name:skill-name` の形で呼びます。

frontmatter はすべて任意で、`description` だけ書くのが推奨されています。本文は 500 行未満が目安とされています。長い手順書を一つの Skill に詰め込むより、分けたほうが読み込まれる量を抑えられます。

[[context-window]] の使い方として見ると、Skill は「必要なときだけ文脈を食う指示」です。毎回読ませたい方針は指示ファイルへ、たまにしか使わない手順は Skill へ、という住み分けになります。

## Hook は、決まったイベントに処理を結び付ける

Hook はハーネスのイベントに処理を結び付けます。設定の読み込み、マッチ条件、タイムアウト、失敗時の扱いを確認し、実行ログで動作を確かめます。

セッションの開始、プロンプトの送信前、ツールの実行前後、終了といった時点ごとにイベントが定義されています。実行するものは、シェルコマンドだけではありません。HTTP のエンドポイント、MCP のツール呼び出し、モデルへのプロンプト、[[subagent|サブエージェント]]も指定できます。

設定は JSON で、イベント名の下にマッチャーを置き、その下にハンドラを並べる三段の入れ子になります。置き場所は `~/.claude/settings.json`（個人）、`.claude/settings.json`（プロジェクトで共有）、`.claude/settings.local.json`（手元だけ）、プラグインの `hooks/hooks.json` などです。

終了コードの扱いがHook を理解する鍵になります。`0` は成功、`2` はブロックするエラー、それ以外はブロックしないエラーです。公式ページには、方針を強制したいなら `2` を使う、という趣旨の記述があります。

ここが指示ファイルとの決定的な違いです。公式ページは、指示ファイルの内容を「強制された設定ではなく文脈」として扱うと説明しています。どんなに強く書いても、モデルの判断は残ります。

必ず起きてほしいことは Hook に置く。逆に、判断の幅を残したい方針は指示ファイルに書く。この分担を覚えておくと、設定の置き場所で迷いません。

Hook は並列に走ります。一つのイベントに複数のハンドラを置くと、順番は保証されません。前の処理の結果を使って次の処理をしたいなら、一つのコマンドの中で順に書きます。

## MCP は、規格と接続の作法

### つなぎ方と、登録のコマンド

MCP のサーバーには、いくつかのつなぎ方があります。公式ページが推奨しているのはリモートの HTTP です。SSE は非推奨とされ、ローカルの stdio は手元のコマンドをサーバーとして起動する形です。

登録はコマンドで行います。リモートなら `claude mcp add --transport http <name> <url>`、ローカルなら `claude mcp add --env <変数名>=<値> --transport stdio <name> -- <起動コマンド>` の形です。`claude mcp list` で一覧、`claude mcp get` で個別の設定を確認できます。

### スコープは三つ

スコープは三つです。

- **ローカル**：既定で、そのプロジェクトの自分の設定。
- **プロジェクト**：リポジトリ直下の `.mcp.json`。バージョン管理に入れて共有できる。
- **ユーザー**：すべてのプロジェクトで使う設定。

同じ名前のサーバーが複数のスコープにあると、ローカル、プロジェクト、ユーザー、プラグイン、アカウント接続の順で優先されます。公式ページは、優先された側のエントリが丸ごと使われ、欄が混ざることはないと説明しています。

### 他人のリポジトリの `.mcp.json`

`.mcp.json` はリポジトリに含められるファイルです。つまり、他人が用意したリポジトリを開くと、そこに MCP サーバーの定義が入っていることがあります。

公式ページは、接続する前にサーバーを信頼できるか確かめること、外部の内容を取得するサーバーは[[prompt-injection|プロンプトインジェクション]]の経路になりうることを注意として挙げています。プロジェクトの `.mcp.json` のサーバーは、対話の中で承認するまで有効になりません。

### 認証情報の扱い

認証情報の扱いにも決まりがあります。環境変数の展開は `${VAR}` と `${VAR:-既定値}` の形が使えます。認証系の環境変数は URL やヘッダーの展開では空として扱われ、`claude mcp get` の表示では伏字になります。秘密を設定ファイルに直書きせず、環境変数から渡す作りです。

## 指示ファイルは、Skills とは別の層

指示ファイルは上の五つとは別の層にあります。モデルに読ませる文脈ではありますが、呼び出しの単位でも、接続の規格でもありません。

`AGENTS.md` は、エージェント向けの README として提案されている形式です。決まった欄はなく、見出しも指定されていません。リポジトリの直下に置き、パッケージが分かれる場合はその中にも置きます。公式ページの表現では、編集するファイルに最も近い `AGENTS.md` が優先され、チャットでの明示的な指示がそのすべてに優先します。

`CLAUDE.md` はClaude Code 側の指示ファイルです。読み込み方が `AGENTS.md` と違います。起動時のカレントディレクトリと、その親ディレクトリのファイルがすべて読まれます。

公式ページは、見つかったファイルは上書きではなく連結されると説明しています。順序は根から現在のディレクトリへ向かい、同じディレクトリでは `CLAUDE.md` のあとに `CLAUDE.local.md` が続きます。サブディレクトリのファイルは、そこのファイルを読んだときに初めて読み込まれます。

| | `AGENTS.md` | `CLAUDE.md` |
| --- | --- | --- |
| 想定 | 複数のエージェント製品で共有する指示 | Claude Code 向けの指示 |
| 優先の決め方 | 編集するファイルに最も近いものが優先 | 見つかった分をすべて連結 |
| 階層の読み込み | 近いものが上書きする | 根から現在地へ積み上がる |
| 1 ファイルの目安 | 定めなし | 200 行未満が推奨 |

Claude Code は `AGENTS.md` も読めます。ただし、同じディレクトリか親に `CLAUDE.md` があると、そちらが優先されます。両方を読ませる設定もありますが、既定はどちらか一方です。複数の製品で同じ指示を共有したいときは、`CLAUDE.md` の先頭で `@AGENTS.md` として読み込む形が案内されています。

`@path/to/file` の形で別のファイルを取り込めます。入れ子の深さは 4 段までで、パスに空白があるときはエスケープします。`CLAUDE.md` 自体が 4 MiB を超えると読み込みが飛ばされるので、巨大なファイルを置かないようにします。

[[prompt]] として見れば、指示ファイルは毎回効くが弱い指示、Skill は必要なときだけ効く詳しい指示、Hook は指示ではない強制、と整理できます。「[[harness]] の設定が効かない」と感じたときは、この三段のどこに書いたつもりだったかを確かめると原因が見えます。

## 外から持ち込む拡張は、中身を読んでから入れる

Plugin はSkill・エージェント・Hook・MCP サーバーをまとめたディレクトリです。`.claude-plugin/plugin.json` に名前と、任意で版や説明を書きます。配布はマーケットプレイスという形で、`.claude-plugin/marketplace.json` を持つリポジトリやディレクトリが目録になります。

公式ページは、これを「ホストされた店ではなく目録」と表現しています。`/plugin` を開くと Discover のタブに並び、`名前@マーケットプレイス` の形で入れます。

有効にしたプラグインはすべてのセッションに組み込まれます。公式ページは、呼び出せる Skill・エージェント・コマンドの名前と説明が毎ターン文脈に載り、本文は使うときに読み込まれると説明しています。つまり、入れる数が増えるほど、使わなくても文脈を少しずつ消費します。

そして公式ページの一文が導入判断の中心になります。プラグインが実行するものは、自分の権限で実行される、という趣旨の記述です。Hook もシェルコマンドも、あなたのアカウントで動きます。中身を読まずに入れるのは、読まずにスクリプトを実行するのと同じです。

確認する順は決めておくと迷いません。まず manifest を見て、何が入っているかを把握します。次に Hook と MCP サーバーの定義を読み、外部へ何を送るか、何を実行するかを見ます。そのうえで、開発中なら `--plugin-dir` でディレクトリから読み込み、試します。不要になったら `claude plugin disable` で切り、残すか消すかを決めます。

[[sandbox]] の内側で試すのも有効です。ネットワークを切った状態で起動し、外部への通信が要るかどうかを先に確かめられます。

## 置き場所に迷ったら、この表に戻る

やりたいことから、置く場所を引けます。

| やりたいこと | 置く層 | そう決める理由 |
| --- | --- | --- |
| 毎回同じ前提を読ませたい | 指示ファイル（`CLAUDE.md` / `AGENTS.md`） | セッション開始時に読まれる。ただし強制力はない |
| たまに使う手順を、必要なときだけ読ませたい | Skill | 本文は使うときだけ読み込まれ、文脈を消費しにくい |
| 必ず実行させたい | Hook | 終了コードで止められる。指示ではない強制 |
| 外部のサービスやデータにつなぎたい | MCP | ツールの供給元を外に開く規格 |
| チームにまとめて配りたい | Plugin | 複数の部品を1つの箱にして配れる |
| モデルに新しい操作を1つ足したい | Tool（ハーネス側の定義） | ツールはハーネスか MCP から供給される |

この表は、この記事の内容を一枚にまとめたものです。製品ごとの設定ファイルの書式は変わるので、実際に書くときは公式ページで確かめてください。

## 演習：名前を、層に分けて書く

手を動かす前に、自分の作業を層に分けます。新しいものを入れる必要はありません。

1. 直近一週間で、同じ指示を三回以上貼った作業を一つ思い出します。これは Skill の候補です。
2. 毎回ではなく、危ない操作のときだけ必要な確認を一つ挙げます。これは Hook の候補です。
3. 手元のファイルではなく、外部のサービスを調べたい作業を一つ挙げます。これは MCP の候補です。
4. どの製品でも同じ指示を渡したいなら、`AGENTS.md` に書く内容を切り出します。Claude Code だけで効かせたいなら `CLAUDE.md` に残します。
5. 3 で挙げた外部サービスについて、公式の MCP サーバーがあるかを調べます。無ければ、この段階では作らずに「未確認」と書きます。
6. 六つの欄（Tool・MCP・Hook・Skill・Plugin・指示ファイル）を紙かテキストに書き、1〜5 の候補を入れます。入らないものは、入れずに理由を書きます。

期待する結果は、候補が三つ以上、どの層に入るかが決まっている状態です。全部の欄が埋まる必要はありません。むしろ、Tool と Plugin の欄が空のほうが普通です。Tool はハーネスが用意するもので、Plugin は配る相手がいるときに作るものです。

うまく分けられないときは、次の質問で切ります。それは「モデルに読ませたい指示か」。「はい」なら指示ファイルか Skill です。「いいえ、必ず実行したい」なら Hook です。「外部の何かに接続したい」なら MCP です。「複数の人に配りたい」なら Plugin です。

## 評価

五つの観点で点検します。概念名と製品名を分けて書いたか。Hook と指示ファイルの違いを、強制力で説明できるか。MCP のスコープと優先順位を、自分の言葉で言えるか。Plugin を入れる前に読む場所を挙げられるか。そして、確認していない製品や数値を、確認したように書いていないか。

書き直しが要るのは、次の状態です。「MCP を入れるとモデルが賢くなる」と書いた。Plugin と Skill を同じものとして扱った。`AGENTS.md` と `CLAUDE.md` の読み込み方が同じだと書いた。どれも、層を取り違えた説明です。

## できあがるもの

手元に残るのは、自分の作業を六つの層に割り付けた一枚のメモです。このメモがあると、次に「これを自動化したい」と思ったときに、どこへ置くかを考えずに済みます。

次の記事では、この層のうち Skill を一つ作ります。記事の文体と HTML の意味づけを検査する Skill を、読み取り専用の道具だけで組み立て、入れる前と後で指摘がどう変わるかを比べます。

比較の材料として、製品ごとの対応状況は[AI図鑑](/zukan/)で並べられます。図鑑の値も確認日つきなので、この記事の記述と食い違ったときは、新しいほうを採ってください。実践編のほかの記事は[実践編の入口](/practice/)からたどれます。
