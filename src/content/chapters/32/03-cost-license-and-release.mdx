前の記事で、判定の順番とテストがそろいました。質問を投げれば、答える・人に回す・答えないのどれかが返り、理由も付きます。動くものは、もう手元にあります。

動くものと、公開できるもののあいだには、三つの書き出しが挟まります。この製品はいくらかかるのか。使っている素材の権利はどうなっているのか。そして、どこまで確かめて、どこから先は確かめていないのか。どれも、コードを読んでも分かりません。作った人が、別の場所に書いておくしかありません。

この記事の目標はその三つを、公開の前に書き出せるようになることです。前提は、前の二つの記事の成果物があること。無くても読めますが、自分の製品に当てはめる演習は、成果物があるほうが具体的になります。

## 単価が無いなら、費用は「未設定」と書く

費用の話でいちばん多い間違いは計算そのものではありません。単価が分からないときに、0 と書いてしまうことです。0 円と表示された画面は「無料」と読まれます。実際には単価が決まっていないだけで、使えば請求が来るかもしれません。分からないことを 0 で埋めると、分からないという事実が消えます。

演習アプリはこの間違いを構造で防いでいます。単価は `config.json` に置き、初期値は `null`。費用を出す関数は、入力と出力の両方の単価が数値のときだけ計算し、そうでなければ `null` を返します。

```js
// lib/cost.mjs から、計算するかどうかを決める部分
const inputTokens = estimateTokens(inputText, charsPerToken);
const outputTokens = estimateTokens(outputText, charsPerToken);

const priced = typeof inPrice === 'number' && typeof outPrice === 'number';
const cost = priced ? (inputTokens * inPrice + outputTokens * outPrice) / 1_000_000 : null;

return { inputTokens, outputTokens, cost, priced, priceSource, priceCheckedAt };
```

`null` を受け取った画面と端末は、どちらも「未設定」と書き、計算しなかった理由を添えます。

```text
（画面）トークン推定 入力 4 / 出力 26。推定費用 未設定（config.json に単価が入っていないため計算しません）
（端末）推定費用: 未設定（config.json の単価が空のため計算しない）
```

理由まで書くのは、読み手が「壊れている」と受け取らないようにするためです。「未設定」の四文字だけだと、表示の不具合と区別が付きません。単価が入っていないから計算していない、と分かれば、設定を入れれば出るのだと分かります。

片方だけ単価が入っている場合も、計算しません。入力の単価だけ分かって出力が分からないなら、出せるのは費用の一部だけです。一部の額を「費用」として出すと、実際より安く見えます。安く見積もる誤りは、高く見積もる誤りより気づかれにくいので、こちらを避ける形にしました。

この違いはテストで固定してあります。「単価が空なら費用は null で、0円とは言わない」「片方だけ単価が入っていても計算しない」の二件が、それです。表示の文字列ではなく、返り値の `null` を見ています。画面の文言を変えても、0 を出さないという約束は残ります。

## 単位を先に確かめる。違う単位は足せない

単価を写すとき、数字だけを写してはいけません。単位も一緒に写します。料金ページの単位は、製品によって違います。あるページでは 100万トークンあたり、別の場所では 1回あたり、席あたりの月額、時間あたり。

Anthropic の料金ページを 2026-10-28 に見ると、[[api|API]] のモデル料金は「/ MTok」、つまり 100万トークンあたりの表記で、入力と出力が別の行に分かれていました。同じページには、セッション時間あたり、検索 1,000 回あたり、コンテナの時間あたりという、別の単位の料金も並んでいます。同じページの中で単位が混ざっているので、数字を写すだけでは足りません。

定額の契約と、使った分だけ払う料金も、別のものとして扱います。月額と席あたり月額は、使う人の数で総額が変わります。100万トークンあたりの単価は、使う量で変わります。この二つを一つの表に入れると、どちらが増えると総額が増えるのかが読めなくなります。

だから `config.json` には、単価と並べて `price_source` と `price_checked_at` を置いています。数字を更新する人が、どこを見て、いつ確認した数字なのかを辿れるようにするためです。この演習では、この二つも `null` のままです。単価を入れていないので、出典も確認日も書くことがありません。

単位を確かめずに計算すると、桁が変わります。100万トークンあたりの単価を 1,000トークンあたりの単価として扱えば、千倍の費用が出ます。逆も同じです。計算式を疑う前に、単位を疑ってください。式はたいてい合っていて、入力の意味がずれています。

## 一回の額ではなく、千回で見る

一回あたりの費用は多くの場合、表示できる桁より小さくなります。0.00002 のような額を見せられても、高いのか安いのか判断できません。千回に直してから見ます。

前の記事で使った質問の、実際のトークン推定です。

```text
$ node cli.mjs "会議室の鍵"
トークン推定: 入力 4 / 出力 26
推定費用: 未設定（config.json の単価が空のため計算しない）
```

同じ質問を千回したとすると、入力は 4,000 [[token]]、出力は 26,000 トークンです。どちらも 100 万には届きません。100万トークンあたりの単価に対して、入力は 0.4%、出力は 2.6% を占める計算になります。千回分の費用は、単価のおよそ 3% です。

単価が決まる前にこの二つの数字を出しておくと、あとで掛け算だけで費用の見当が付きます。単価が変わったときも、掛け直すだけで済みます。質問の種類を増やしたいときは、代表的な質問を十件ほど選んで同じように数え、一件あたりの平均を出してください。

この 4 と 26 には、二つの但し書きが付きます。

一つは、実際のモデルのトークナイザで数えた値ではないこと。文字数を1トークンあたり1.5文字として割り、切り上げた概算です（文字数5の質問が4トークンになる計算）。これは「日本語はおよそ1文字1トークン」という目安より少なめに見積もる係数で、この値がどれくらい合うかは確かめていません（未確認）。[[tokenization]] で扱ったとおり、トークンの区切りはモデルごとに違います。この係数がどれくらい合うかは、確かめていません（未確認）。実際のトークナイザで数えた値と比べるまでは、目安として扱ってください。

もう一つはこのアプリがモデルを呼ばないこと。26 という出力トークンは、自分で組み立てた返事の長さです。実際のモデルにつないだ場合、返事の長さは毎回変わり、費用も変わります。この記事は、モデルにつないだ状態の費用を実測していません（未確認）。[[inference]] の費用を実際に測るには、鍵を用意して課金のある API を呼ぶことになります。この連載では、そこまで行っていません。

## 権利は、素材ごとに一行ずつ残す

費用の次は権利です。製品には、自分で書いたものと、そうでないものが混ざります。混ざった状態のまま公開すると、どこまでが自分のものか、あとから分からなくなります。

演習アプリの FAQ 十二件と評価用の質問十四件は、この演習のために書いた架空の社内規程です。実在の組織の規程ではなく、第三者の文章・画像・音声を含みません。この事実を、`data/faq.json` の冒頭と `CHECKLIST.md` の両方に書きました。データを見ただけでは分からないことなので、書いておく場所を決める必要があります。

外部の素材を使うときは、何を、どこから、どの[[license|ライセンス]]で、いつ取得したかを一行にします。ライセンスの名前は、SPDX の一覧にある短い識別子を使うと伝わりやすい。SPDX の一覧には、識別子・正式名称・ライセンス本文・恒久的な URL がそろっていて、同じ名前の別ライセンスを取り違えにくくなっています。

| 素材 | 出所 | 権利 | 確認日 |
| --- | --- | --- | --- |
| FAQ 12件 | この演習のために自作 | 自作。第三者の文章を含まない | 2026-10-28 |
| 評価用の質問14件 | この演習のために自作 | 自作 | 2026-10-28 |
| 外部の素材 | 使っていない | — | — |

識別子だけでは足りません。同じ MIT でも、同梱するファイルの場所や著作権表示の書き方が決まっています。識別子で検索して、条件を読んでください。読んだうえで、同梱ファイルを置き、表示を書きます。

音声や画像を扱うときは、さらに厳しくします。第31章でも書きましたが、利用権が明確な素材だけを使い、第三者の声・肖像・著作物を無許諾で組み込みません。自分の声を録って使う、自分で描いた図を使う、提供元が利用条件を明記している素材だけを使う。この三つのどれかに寄せるのが安全です。

使わなかったことも記録です。表の三行目は、外部の素材を使っていないことを示すために置きました。あとから素材を足したときに、この行が差分として見えます。空欄のままにすると、足したのか元から無かったのかが分かりません。

## 済みと未確認を、同じ表に分けて書く

最後は確かめたことと確かめていないことの一覧です。`CHECKLIST.md` に、この演習アプリ自身を当てはめた結果を置きました。

| 項目 | 状態 | 根拠 |
| --- | --- | --- |
| 代表的な質問で動きを確かめた | 済み | 四つの行き先を、端末と画面の両方で実行 |
| 自動テスト | 済み | 39件すべて通過 |
| 画面の確認 | 済み（Chromium のみ） | 1280×900 と 390×844。横スクロールなし、コンソールエラー 0件 |
| 外部への通信が無いこと | 済み | 呼び出しの文字列を検索。外部のホスト名 0件 |
| 秘密情報を扱っていないこと | 済み | 鍵・トークン・環境変数の読み出しが無い |
| 費用の表示 | 済み。ただし単価を入れた状態は未確認 | `cost: null` をテストで固定 |
| データとライセンス | 済み | 自作であることをデータとチェックリストに明記 |

費用の行がこの表の書き方をよく表しています。済みと未確認が一行の中に同居しています。単価が空のときに未設定と出ることは確かめた。単価を入れたときに正しく計算されることは、実課金を伴うので確かめていない。この二つを「済み」の一言でまとめると、後半の但し書きが消えます。

未確認として残したのは、五つです。

- **Chromium 以外のブラウザ。** Firefox と Safari では開いていません。`<details>` と `fetch` は広く使われている機能ですが、確認したとは書けません。
- **スクリーンリーダーでの読み上げ。** `aria-live` は付けたものの、実際に読み上げさせて確かめていません。
- **HTTPS での配信。** 手元の HTTP サーバーでしか開いていません。
- **実際のモデルにつないだ場合の費用と文面。** このアプリはモデルを呼びません。
- **長期の運用。** ログの保存、更新の手順、問い合わせの一次受けは、この演習の範囲外です。

この二つを分けて書くことが、公開前チェックの本体です。済みだけを並べたチェックリストは、読み手に「全部確かめた」と受け取られます。そこに一項目でも未確認が混ざっていれば、読み手は「この範囲までは確かめたのだな」と読めます。

未確認と書くのは、手を抜いた告白ではありません。次に誰が何を確かめればよいかの指示になります。「Firefox で開いていない」と書いてあれば、次に触る人がまずそこを開きます。書いていなければ、同じ穴がまた残ります。

公開前チェックは公開を止めるための道具ではありません。公開してよい範囲を決めるための道具です。五つの未確認のうち、業務で使うなら HTTPS と長期運用は必須になるでしょう。社内の試験利用なら、Chromium だけで始める判断もあります。決めるのは作り手ですが、材料はこの表にそろえます。

## うまくいかないときの見方

費用が 0 と出るときは、まず `null` と `0` の取り違えを疑ってください。設定ファイルに `0` が入っていれば、計算は行われ、0 が返ります。空にするときは `null` にします。空文字や `0` で代用すると、意味が変わります。

費用が想定より千倍大きいときは、単位を疑います。100万トークンあたりの単価を、1,000トークンあたりとして扱っていないか。逆に千分の一になるなら、その反対です。計算式を書き直す前に、入れた数字の単位を読み返してください。

費用が想定より小さいときは、出力を数えているかを見ます。入力だけを計算している実装はよくあります。この演習では、返事の本文も入力と同じ関数に通しています。

ライセンスが分からない素材が出てきたら、使わない選択をしてください。分からないまま使うと、公開後に条件を満たすために作り直すことになります。代わりの素材を探すか、自分で作るかのほうが、たいてい安く済みます。

未確認の項目が多いと感じたら、公開する範囲を狭めます。全部を確かめてから出すのではなく、確かめた範囲だけを出し、残りは次のバージョンに回す。チェックリストは、その線を引くためにあります。

## 演習：自分の製品の、公開前チェックを書く

この章の最初の記事で書いた条件の表を、もう一度開きます。その表と、この記事の三つの書き出しを突き合わせます。

1. 条件のうち、費用に関わるものを抜き出す。「1回あたり何円まで」でも「月いくらまで」でも構いません。
2. 費用の見積りを、千回分のトークン数で書く。単価が決まっていなければ、単価の欄を空のまま残し、「未設定」と書く。
3. 使っている素材を全部リストにする。自作、外部、不明の三つに分ける。
4. 「不明」が一つでもあれば、その素材を外すか、権利を確かめる。確かめるまでは公開しない。
5. 公開前チェックの表を作り、各行に状態と根拠を書く。根拠が書けない行は「未確認」にする。
6. 未確認の項目を読み、公開する範囲を決める。狭めるのか、確かめてから出すのかを一行で書く。

期待する結果は、費用・権利・未確認の三枚がそろうことです。三枚そろっていれば、公開の可否を自分で判断できます。そろっていない状態で「たぶん大丈夫」と言うのは、判断ではなく願いです。

**この記事で実際に確認した対象は、演習アプリです。** 自分の製品での実施は、この記事の執筆時点では行っていません（未実機確認）。手順と、表の書き方だけを持ち帰ってください。

## 評価

五つの観点で点検します。単価が無いときに 0 と書いていないか。単価に単位・出典・確認日が付いているか。費用を千回分に直して見たか。素材ごとに権利の行があるか。そして、未確認の項目が表に残っているか。

書き直しが要るのは、次の状態です。費用の欄を空文字や 0 で埋めた。単価だけを写して、単位と確認日を落とした。一回分の額だけを見て「安い」と判断した。素材の一覧を作らず、口頭で「たぶん使える」と確認した。チェックリストを済みだけで埋めた。どれも、あとから同じ判断ができない記録です。

## できあがるもの

手元に残るのは、三枚です。千回分のトークン数と単価の欄がある費用の見積り。素材ごとの権利の一覧。済みと未確認を分けた公開前チェック。この三枚と、前の二つの記事で作った条件の表とテストがあれば、第32章の成果物は一通りそろいます。

第23章から数えると、製品の全体像、モデルの選び方、料金の読み方、端末と CLI、ハーネスの違い、[[skill|Skills]] と MCP、計画と分担、音声と画像。部品はそれぞれ別の章で扱いましたが、この章でそれらが一つの製品の形にまとまりました。大事だったのは、部品を覚えることより、条件を先に書き、確かめた範囲を記録し、確かめていないことを残すという順番のほうです。

自分の題材で作るときは、この順番をそのまま使ってください。条件、実装、テスト、費用、権利、未確認。どれかを飛ばすと、飛ばした場所が公開後に見つかります。

[実践編の入口](/practice/)から、公開済みの章をたどれます。使うモデルやハーネスを名前で比べたいときは [AI図鑑](/zukan/) が使えます。この章の最初の記事は [受け入れ条件を決める](/chapters/32/01-requirements-and-acceptance/)、その次は [判定の順番を決める](/chapters/32/02-build-and-test/) です。
