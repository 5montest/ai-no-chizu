画像をモデルに渡すとき、費用は「枚数」では決まりません。同じ1枚でも、200×200 のサムネイルと 4K の写真では、数十倍の差が出ます。理由は、画像がピクセルのまま処理されるのではなく、小さなブロックに区切って数えられるからです。

この記事の目的は、画像を読ませる [[vlm]] を使う前に、費用と限界を見積もれるようになることです。数え方、解像度の段、1回あたりの上限、そして「読み取れないもの」の一覧を順に扱います。最後に、生成とは別に置く判定モデルの話をします。

前提は、第25章で決めた費用の数え方です。画像を一枚用意してください。文字の入った写真や、グラフの入った図が使いやすい素材です。第三者の顔写真や著作物は使わないでください。

## 画像は、パッチの数で値段が決まる

公式の説明では、Claude は画像をピクセルではなくパッチで処理します。1パッチは 28×28 ピクセルのブロックで、これが visual [[token]] と呼ばれます。トークン数は、縦と横のパッチ数の積です。

```text
トークン数 = ceil(幅 / 28) × ceil(高さ / 28)
```

切り上げなので、28の倍数でない端数も1パッチとして数えます。1000×1000 なら36×36で1,296トークン、1092×1092 なら39×39で1,521トークンです。同じ「だいたい千ピクセル四方」でも、28で割り切れるかどうかで数十トークン変わります。

手元で数えるなら、この計算だけで足ります。

```python
# image_tokens.py — 画像の縦横からパッチ数を数える
import sys


def ceil_div(a, b):
    return -(-a // b)


width, height = int(sys.argv[1]), int(sys.argv[2])
w_patches = ceil_div(width, 28)
h_patches = ceil_div(height, 28)
tokens = w_patches * h_patches

print(f'{width}x{height} -> {w_patches}x{h_patches} パッチ = {tokens:,} トークン')
print(f'1000枚あたり {tokens * 1000:,} トークン')
```

ただし、これは「縮小されなかった場合」の数です。次の節の上限を超える画像は、送る前に縮められます。縮められたあとの寸法で数え直してください。

## 解像度には、二つの段がある

上限は一つではなく、モデルの世代で二つの段に分かれています。

| 段 | 対象 | 長辺の上限 | トークンの上限 |
| --- | --- | --- | --- |
| 高解像度 | Claude 4.7 以降 | 2,576px | 4,784 |
| 標準 | それ以外のモデル | 1,568px | 1,568 |

上限を超えた画像は、段の範囲に収まるよう縮小されます。だから 4K の写真を送っても、高解像度の段で4,784トークン、標準の段で1,560トークンに収まります。元の画素数がいくら大きくても、青天井にはなりません。

代わりに、縮小で情報が落ちます。小さい文字が入った書類の写真を標準の段で送ると、文字が潰れて読めないことがあります。読めなかったのか、書いていなかったのかは、結果からは区別できません。文字を読ませたいときは、高解像度の段のモデルを使うか、画像を分割して送ります。

公式ページには、モデルの料金と組み合わせた例が載っています。Haiku 4.5（入力100万トークンあたり1ドル）で 1000×1000 の画像を標準の段で送ると、1000枚あたり約1.30ドル。Opus 5.5（同4ドル）で高解像度の段を使うと約5.18ドル、4K の画像なら約19.14ドルという例です。同じ1枚でも、モデルと段の選び方で10倍以上変わります。

## 送る前の上限を、四つ確かめる

画像を送るときに見る数字は四つあります。

| 項目 | 上限 |
| --- | --- |
| 1リクエストあたりの枚数 | 20枚（claude.ai）、100枚（コンテキスト20万のモデル）、600枚（それ以外） |
| 画像の寸法 | 8000×8000px |
| 1枚あたりの大きさ | 10MB（API・Google Cloud）、5MB（Amazon Bedrock）、10MB（claude.ai） |
| リクエスト全体の大きさ | 32MB（標準のエンドポイント） |

枚数の上限を超えると、もう一つ条件が増えます。20枚を超えるリクエストでは、1枚あたりの寸法に厳しい制限がかかります。公式には、どちらかの辺が2000pxを超えないように縮小するか、画像と文書のブロックを20以下に抑えるか、と書かれています。大量の画像を一度に送るときは、この二択を先に決めてください。

形式は JPEG、PNG、GIF、WebP です。GIF は最初のフレームだけが使われ、動きは見られません。アニメーションの内容を説明させたいなら、フレームを静止画として切り出して送ります。

渡し方は三つあります。base64 で埋め込む、URL を渡す、Files API で上げた `file_id` を渡す。ただし Amazon Bedrock と Google Cloud では、base64 だけが使えると書かれています。環境を移す予定があるなら、最初から base64 にしておくと手戻りが少なく済みます。

並べ方にも指定があります。[[multimodal]] のモデルでは、画像とテキストを同じリクエストに置きます。画像を先に、テキストを後に置くほうが良いとされています。指示を先に長く書いてから画像を置くと、指示と画像の対応が取りにくくなります。

## 文書は、ページの束として渡す

PDF も、画像と同じ枠組みで扱えます。公式には、テキスト、図、表、グラフを読めると書かれています。スキャンしただけの文書でも、ページを画像として見るので読めます。

| 項目 | 上限 |
| --- | --- |
| リクエストの大きさ | 32MB |
| 1リクエストあたりのページ数 | 600ページ（コンテキストが100万トークン未満なら100ページ） |
| 形式 | 標準のPDF。パスワード付きと暗号化は不可 |

ページ数の上限が、コンテキストの大きさで変わる点に注意してください。長い契約書を丸ごと渡すときは、使うモデルのコンテキストを先に確かめます。100ページを超える文書は、章ごとに分けて送り、結果を統合する形にします。

PDF はページごとに画像として処理されるので、[[inference]] の費用はページ数と解像度に比例します。同じ100ページでも、図版の多い資料と文字だけの資料では、かかるトークンが違います。送る前に、ページ数と、1ページあたりの文字量を見ておくと見積もりが立てやすくなります。

文字がきれいに入っている PDF なら、PDF を渡すより先にテキストを抜き出したほうが安く済むことがあります。判定の基準は単純です。埋め込みテキストが取れるなら、テキストで渡す。取れない、あるいは表や図の配置そのものが要るなら、PDF のまま渡す。

## 判定は、生成とは別のモデルに置く

文章を書かせるモデルに「この内容は不適切か」と聞く形は、安定しません。同じ入力でも言い方が変わり、基準も毎回違います。判定には、判定用に作られたモデルを使います。

OpenAI の Moderation は `POST /v1/moderations` で、モデルは `omni-moderation-latest` です。テキストと画像を受け付け、音声は分類しないと明記されています。画像は20MBまでです。

返ってくるのは、`flagged`（有害と判断されたか）、`categories`（項目ごとの該当）、`category_scores`（0から1の確信度）です。項目は入力の種類で分かれ、嫌がらせ・憎悪・違法行為の系統はテキストに、自傷・性的・暴力の系統はテキストと画像の両方に適用されます。

スコアの扱いには、公式から二つの注意が出ています。一つは、スコアはアプリケーションの方針を決めるための信号であって、自動の遮断判断として使うものではないこと。もう一つは、下のモデルは継続的に更新される予定なので、`category_scores` に依存した独自の方針は、時間とともに再調整が要ることです。

つまり、しきい値を決めて終わりにできません。しきい値を決めた日付と、そのときの判定の記録を残し、定期的に見直します。第28章の実験ログと同じ扱いです。

このエンドポイントは無料で使えると書かれています。ただし、無料であることと、送ってよい内容であることは別です。公式には、既知の、あるいは疑わしい児童の性的虐待素材を送らないこと、このAPIはその検出や取り扱いのために作られていないことが明記されています。無料だからとりあえず通す、という使い方をしてはいけません。

## 読み取れないものを、読み取ったことにしない

画像を読むモデルには、はっきりした苦手があります。公式ページに列挙されているものを、そのまま押さえてください。

**人は特定できない。** 画像に写った人物の名前を答えることはせず、求められれば断ります。

**小さい画像と、傾いた画像に弱い。** 200ピクセルを下回るような小さい画像、低品質の画像、回転した画像では、存在しない内容を作り出すことがあると書かれています。

**位置の出力は概算。** 物体の座標や位置を答えさせると、おおよその値になります。

**数を数えるのは苦手。** 小さい物体が多数ある画像では、数え上げが概算になります。

**AI生成画像かどうかは判定できない。** これは特に誤解が多い点です。見た目で判断しているわけではありません。

ほかに、不適切な画像や露骨な画像は扱わないこと、CT や MRI の診断目的には使わないこと、画像のメタデータは読まないこと、アップロードした画像は処理後に削除され学習には使われないこと、そして画像を生成・編集する機能は無いことが書かれています。

この一覧は、機能の紹介ではなく、責任の範囲を決める材料です。人物の特定、医療の判断、生成画像の検出。どれも「たぶんできるだろう」で設計すると、あとで取り返しがつきません。

## 演習：同じ画像を二つの大きさで数える

API は呼びません。数と費用の計算だけを練習します。課金も、外部への送信もしません。

1. 手元の画像を一枚選ぶ。縦横のピクセル数を調べる。
2. `image_tokens.py` にその寸法を渡し、パッチ数とトークン数を出す。
3. 同じ画像を、長辺が1,568pxになるよう縮小した場合の寸法を計算し、もう一度数を出す。
4. 二つの差を、百分率で出す。どれだけ削られるかが分かる。
5. 第25章の表から使うモデルの入力単価を引き、1000枚あたりの費用を計算する。単価には確認日を添える。
6. 表にまとめる。寸法、パッチ数、トークン数、1000枚あたりの費用、そして「この解像度で読めそうか」の判断。

三つ目の手順が要点です。縮小の影響を、送る前に数字で見ます。小さい文字が入った書類なら、1,568px に縮めた時点で読めなくなるかもしれません。読めない画像を1000枚送るより、読める大きさで100枚送るほうが安く、正確です。

余力があれば、文字の入った画像を二つの大きさで実際に読ませて、抽出できた文字数を比べます。この場合はAPIを呼ぶので、費用と送信先を自分で確かめてから実行してください。**この記事の執筆時点で、私はこの比較を実行していません（未実機確認）。**

## うまくいかないときの見方

文字が抜けるなら、まず解像度を疑います。標準の段に縮められて、文字が潰れています。高解像度の段のモデルにするか、画像を分割します。

表の列がずれるなら、表を画像のまま読ませるのをやめて、テキストとして渡す形に変えます。表の構造は、テキストにしたほうが保てます。

同じ画像で毎回違う答えが返るなら、質問が広すぎます。「この画像について説明してください」ではなく「左上の表の、三行目の数値を読み取ってください」のように範囲を絞ります。位置の出力は概算なので、座標を指定する質問は避けます。

20枚を超えて送ると寸法の制限が厳しくなる、という点も見落としやすいところです。大量に送るときは、枚数を20以下に抑えるか、1枚ずつ小さくするかを先に決めます。

判定モデルのスコアが、自分の感覚と合わないなら、しきい値ではなく入力の種類を疑います。テキストだけを渡しているのに、画像の項目を見ている。逆も同じです。どの項目がどの入力に適用されるかを、一覧で確かめてください。

## 評価

五つの観点で点検します。送る前にトークン数を計算したか。解像度の段を意識してモデルを選んだか。枚数と容量の上限を確かめたか。読み取れないものの一覧を、設計に反映したか。そして、判定のしきい値に日付を付けたか。

書き直しが要るのは、次の状態です。画像の枚数だけで費用を見積もった。文字が抜けた原因を、モデルの能力のせいにして解像度を疑わなかった。判定モデルのスコアを、そのまま遮断の条件にした。どれも、条件を変えたときに同じ判断ができない設計です。

## できあがるもの

手元に残るのは、寸法とトークン数の対応表、1000枚あたりの費用の見積もり、そして読み取れないことの一覧です。この三つがあれば、新しい画像を送る前に、いくらかかって、どこまで読めるかを言えます。

次の記事では、ここまでの部品をつないで、音声を文字にして、応答を読み上げる最小構成を作ります。区間ごとの待ち時間を測る表と、費用を区間ごとに数える表を持ち帰ってください。[次の記事](/chapters/31/03-voice-pipeline/)に進みます。

製品の料金や上限は [AI図鑑](/zukan/) と [料金の章](/chapters/25/) で確かめられます。図鑑の値には確認日があるので、この記事の日付と見比べてください。
