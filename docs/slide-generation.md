# スライド生成の設計（段階的実装方針）

「AIの地図」（Astro + MDX の技術解説書）の本文を、Web 版とスライド版の両方で再利用するための設計方針。この文書は設計のみを扱い、コードを含まない。既存の構造、すなわち `src/content/chapters/` 配下の MDX を正本とする content collection、`src/components/` 配下のコンポーネント、`src/data/diagrams.ts` で管理する Mermaid 図を壊さない段階的移行を目的とする。

前提となる現状の事実を先に確認しておく。

- 本文は `src/content/chapters/{章番号}/{slug}.mdx` に MDX で書かれ、`src/content.config.ts` の `chapters` コレクション（glob loader）で読み込まれる。
- 本文から import されている Astro コンポーネントは現時点で `Diagram`、`Callout`、`DeepDive`、`ModelTable`、`ProbabilityChart`、`PriceCompareChart` の6種である。前の3つは本文の内容をそのまま受け取るのに対し、`ModelTable` と2つのグラフは `src/data/` 配下のデータから描く。`Quiz` は MDX 内には現れず、frontmatter の `quiz` フィールドにデータがあり、`src/pages/chapters/[chapter]/[slug].astro` が `<Quiz questions={data.quiz} />` として本文の外側で描画している。
- 図は `src/data/diagrams.ts` に `name` → `{ number, title, caption, code }` の形で登録され、`src/components/Diagram.astro` が `<pre class="mermaid">{diagram.code}</pre>` を出力する。Mermaid 本体は `src/layouts/BaseLayout.astro` のクライアント側スクリプトが動的に `import('mermaid')` して `run()` で描画する。つまり図は現状、閲覧時のブラウザ内でしか存在しない。
- 章の構造は `src/data/curriculum.json` が持ち、章ごとに `outcome`（到達目標）・`core`（章の芯の主張）など章レベルのメタデータを持つ。ページレベルの frontmatter には `summary`（ちょうど3行）・`quiz`・`sources` がある。

## 1. MDX 本文を Web とスライドで再利用する方法

**結論: MDX 本文と frontmatter は1本に保つ。スライドの区切りは既存の `##` 見出し単位を基本とし、どうしても必要になったときだけ補助的なコメント記法を後から足す。** スライド用に本文を複製したソースファイル群は作らない。Web は `src/pages/chapters/[chapter]/[slug].astro` がこの1本を描画し、スライドは変換スクリプトが同じ1本を読む。これが正本の一元化であり、この文書の他の節もすべてこの前提に立つ。

Web 専用の「見た目」が本文テキストではなくコンポーネント側に寄せられている点が、再利用を現実的にする根拠である。たとえば `Callout` は `<Callout type="myth">本文</Callout>` のように書かれ、注意の種類は属性が持ち、装飾は `src/components/Callout.astro` 側の CSS が担う。スライド側でこの要素を「ラベル付きの引用」として意味的に置き換えれば、本文テキストはそのまま使える。`Diagram` も `name` 属性だけを本文に書く形のため、本文は図の実体から独立している。

スライドの区切り表現の比較は次のとおり。

- **見出し単位**（推奨）: 既存の `##` 見出し 1つをスライド1枚に対応させる。追加記法が不要で、本文を書くだけでスライド構成が定まる。`src/pages/chapters/[chapter]/[slug].astro` が `render()` の戻り値から取得している `headings` と同じ粒度を扱えるため、Web の目次とスライドの構成が自然に一致する。区切りの漏れや二重定義が起きにくい。
- **`---` 区切り**: Marp 風に水平線で区切る方式。ファイル冒頭の frontmatter 終端 `---` と見た目が重なり、本文の流れの途中に誤って打つとスライドが意図せず分断される。markdown としては単なる水平線なので、エディタ上で「区切りとしての `---`」と普通の水平線を見分ける手がかりがない。細粒度の制御力は高いが、Web 版本文の読みやすさと引き換えになる。
- **専用コメント記法**: `<!-- slide -->` のような HTML コメントを区切りとして特別扱いする方式。本文の見た目に影響を与えずに区切りを制御できる利点がある一方、`src/plugins/remark-guide-links.mjs` が `html` 型ノードを変換対象から除外している (`SKIP`) ように、コメントは既存パイプライン上では不透明なノードで、解析の実装負担が見出し単位より重い。

見出し単位を推奨する理由を補足する。スライドの粒度を読み物の見出しに従わせると、Web 版の文章構成がスライドの都合で歪む危険がある。ただしサイト本体は「短いページの積み重ね」という構成方針であり（`src/pages/chapters/[chapter]/[slug].astro` が「ページ中何番目」を表示する設計）、1ページ内の `##` 見出しは各節が数段落程度の短い区切りとして書かれている。そのため見出し＝スライド1枚の対応はまず成立すると見込める。実測して長すぎる見出しブロックが出てきた段階で、そのとき初めてコメント記法による強制分割の文法を設計すればよい。この文書の時点ではその文法を確定しない。

スライドに含まない要素はすでに構造的に分離されている。`Quiz`・`SourceList`・`RelatedTerms`・`PageNav` は `src/pages/chapters/[chapter]/[slug].astro` が MDX 本文（`.prose` 内の `<Content />`）の外側で描画している。そのため本文 MDX だけで「スライドに載せるべき部分」が自然に切り出せる。`Quiz` のデータは frontmatter にあるため、スライド末尾の「理解チェック」の1〜2枚への流用も frontmatter 参照だけで済む。

## 2. 学習目標・要点・出典などの共通メタデータ

**結論: 既存の zod スキーマに Optional なフィールドを追加するだけで、Web 版の表示に影響を与えずに拡張できる。** `src/content.config.ts` の `chapters` スキーマは zod で宣言されており、追加した項目を既存の描画（`src/pages/chapters/[chapter]/[slug].astro`）が参照しない限り、Web 側は何も変わらない。後方互換のため、追加フィールドはすべて `.default([])` を付けるか、完全に Optional にする。

追加する項目の案:

- `objectives: string[]` — そのページの学習目標。スライド冒頭の「本日のゴール」の1枚に使う。章レベルの到達目標は既に `src/data/curriculum.json` の `outcome` があるため、ここではページレベルの粒度に限定する。
- `slides?: { include?: boolean; note?: string }` — このページをスライドに含めるか、およびスライド特有の補足（口頭説明に任せる旨など）。既定では含める。講義の範囲から外したいページだけ例外として `false` を書く。Web 版の描画はこれを一切参照しない。

既存の `summary`（ちょうど3行）と `quiz`（1〜5問）はスライドへの再利用価値が高い。`summary` はスライドの目次的な1枚に対応し、`quiz` は「理解チェック」の1〜2枚に対応する。重要なのは、これらの値を Web とスライドで共有し、差分を許さないことである。スライド専用の別の文章を用意する発想はしない。重複管理が発生するためである。

`sources`（既存の配列）はそのままスライドの出典表記に使える。スライド側の実装では、`url` や `publisher` がない出典（schema 上 Optional）も考慮して、欠けている要素を無視して空表示にする。zod の型検証により項目の構造は保証されるが、表示側は空配列・省略要素を前提に組む。

## 3. Mermaid 図解を SVG として再利用する仕組み

**結論: `src/data/diagrams.ts` を唯一のソースに保ち、図はビルド時に SVG 化して、Web とスライドの両方から同じ SVG を参照できる状態にする。** 現状はブラウザ内での描画のため、スライドや PDF に静的に埋め込めない。スライド側では Mermaid 本体を持ち込まず、事前に SVG 化しておく。

構成イメージ（実装はフェーズ2以降）:

1. `scripts/render-diagrams.mjs`（仮称）を作り、`src/data/diagrams.ts` から全図の `code` と `caption` を取り出す。
2. Mermaid の Node からの直接呼び出しは DOM 前提のため動かない。実現方式は2つあり、(a) `mermaid-cli`（puppeteer 依存）を devDependency に加える方法と、(b) headless Chromium を1回だけ起動して `mermaid.run()` を実行して SVG を吐く方式である。この環境では headless Chromium 方式で足りる見込みが高い。`CLAUDE.md` が定める「ブラウザ検証では同時起動1インスタンス・`flock` による直列化」の制約に合致する。
3. 出力は `public/diagrams/{name}.svg` のような配置で、Web とスライドの両方から参照する。SVG は自動生成物であり、`src/data/diagrams.ts` を変更したときだけ再生成する。再生成の判定は `code` と `caption` から算出したハッシュで行う。
4. 失敗時のフォールバックは2段に分ける。SVG がまだ存在しない間は `src/components/Diagram.astro` が現状どおり `<pre class="mermaid">` を出す（クライアント側描画がそのままフォールバックとして残る）。SVG 変換自体に失敗した場合も Web 版の表示は壊さない。一方で、Web はクライアント描画・スライドは SVG のまま不揃いになった図があると、Web とスライドで図の見た目がずれる。これは6節の差分検出の対象になるため、失敗した図は「スライドに SVG が用意できていない」として明示的に扱う。

キャプションは `src/data/diagrams.ts` の `caption` に一元しており、`src/components/Diagram.astro` が `<figcaption>` に表示している。本文側から明示された場合だけ上書きを許す現行の挙動に倣い、スライド変換時も同じ `caption` 参照・同じ上書きルールに従う。Web とスライドで注記の文面がずれるのを防ぐためである。

検証が必要な点として、mermaid 12 系での SVG 出力の見た目（フォント・日本語幅・テーマ色）がブラウザ描画と一致するかは実測前には確定しない。フェーズ2で試験的に1〜2枚出力して確認してから全体に広げる。

## 4. MDX の Astro コンポーネント依存を扱う方法

**結論: `src/components/` 側を変更せず、スライド変換スクリプト側にマッピング表を置いてコンポーネントごとにスライド表現へ対応づける。** 対象は6種で、どれも入出力が小さいので、マッピング表1つで足りる。

変換の思想は既存の `src/plugins/remark-guide-links.mjs` と同じで、mdast（markdown AST）を走査して書き換える remark プラグインと同型の実装である。MDX 内の JSX は mdast 上で `mdxJsxFlowElement` / `mdxJsxTextElement` として現れるため、変換スクリプトはこのノード型を処理する。

対応づけの方式としては、他に「コンポーネントの薄いラッパーに差し替える」方法も考えられる。各コンポーネントの内側に Web 用とスライド用の描画を分岐させ、共通の入口を保つ方式である。しかし実装箇所が `src/components/` 全体に及ぶため、Web 版へのリスクが変換スクリプト方式より大きい。また、Astro コンポーネントはビルド時に HTML へ展開されるため、スライド変換のタイミングで Node から Astro コンポーネントを呼ぶには Astro の実行機構に依存する必要があり、スライドのパイプラインが Astro から独立できなくなる。この2点からマッピング表方式を採る。

マッピング表の案:

- `<Diagram name="llm-pipeline" />` — `src/data/diagrams.ts` から `code`・`caption`・`number` を引いて SVG として埋め込む。スライドでは「図番号＋タイトル＋キャプション」のかたまりとして出す。既存の id（`fig-{name}`）の付け方は Web 固有のため、スライド側では単純化する。
- `<Callout type="note|myth|tip|warn">本文</Callout>` — `src/components/Callout.astro` が持つ `labels` マップと同じ対応で、「補足」「よくある誤解」等のラベル付き blockquote に変換する。色やレイアウトはスライド側の CSS に寄せ、本文テキストは書き換えない。
- `<DeepDive title="…">本文</DeepDive>` — 折りたたみ要素（`<details>`）はスライドに存在しない。「深掘り: {title}」の見出しとともに1枚にするか、講義では割愛するかを変換段階で選べるようにする。基本は1枚として出す。割愛は明示的な指示があったページだけに限る。
- `<ModelTable />` — データ駆動コンポーネント（`src/data/model-comparison.json` を読む）。スライドの1枚に全モデル・全列を入れることはできないため、出力する行・列を選ぶ簡略化ルールを別途決める。全表を出さず、要点に絞った縮小表に落とす。
- `<ProbabilityChart />`（`src/data/next-token-example.ts`）と `<PriceCompareChart />`（`src/data/model-comparison.json`） — どちらもビルド時に HTML とインライン style で値と位置を焼き込む実装で、実行時 JavaScript も外部のチャートライブラリも使っていない（比率の計算は `src/lib/chart-scale.ts`）。スライドも同じデータと同じ計算関数から作れば、Web と数値・比率がずれない。スライド上は1枚の図として扱い、Web のビルド結果を画像化して載せるのを最小の実装とする。`caption` 属性による上書きは `Diagram` と同じ規則で扱う。

非対応コンポーネントの扱いは、**マッピング表に存在しない JSX が出たら変換を停止する** 方式にする。`src/plugins/remark-guide-links.mjs` が未登録の用語・章・ページに対して `throw new Error` でビルドを止めるのと同じ哲学である。黙って何もしないで捨てると事故に気づけないため、新しいコンポーネントを MDX で使い始めたら、マッピング表への追加が必要ということにする。

将来の安全性について補足すると、変換の対象はあくまで「本文の Markdown 相当」であり、MDX を HTML へ置き換えることではない。この2層構造（本文 Markdown 抽出層、その上のスライド出力層）にしておくと、スライド形式を Marp から Slidev 等へ切り替える場合も、下層をそのままに上層の変換器を差し替えられる。

## 5. Slidev / Marp などへの変換方針

**結論: 第一候補は Marp。アニメーションやコード段階提示のような見せ場は当面の要求に入れない。** 技術解説としての章構造・図・重点が正しく出ることを優先し、変換の出口に置くものをシンプルに保つ。

理由:

- Marp は純粋な Markdown に `---` 区切りとディレクティブを足した形式で、Markdown からスライドを出す入口がシンプルである。PDF 出力は `marp-cli` 一本で済み、CI に載せやすい。
- Slidev は Vue ベースの SFC を想定する。MDX → Vue コンポーネントへの変換という手間が増えるうえ、このガイドの本文には JavaScript 表現を置く必要性が低く、コード段階提示やクリックアニメーションといった付加価値を当面は使わないと判断する。

変換の手順（見取り図を示すもので、この文書でコードを確定するものではない）:

1. `scripts/render-slides.mjs`（仮称）を作る。`src/content/chapters/{章}/{page}.mdx` を読み、マッピング表に従って mdast を走査して、スライド用の Markdown を1章分（あるいは1ページ分）生成する。
2. Marp 用の frontmatter（`marp: true`, `theme: …`, `paginate: …`）を変換側で付与する。本文 MDX には書かない。
3. `marp-cli` で HTML と PDF を出力する。出力先の配置は **フェーズ4 を迎えた時点で改めて決める**。この文書の時点では固定しない。
4. Astro 側の依存（`src/components/`・`src/layouts/`・`src/data/` 配下のデータは除く）をスライド側に引きずり込まない。スライド変換パイプラインは Markdown と SVG、および frontmatter・`curriculum.json` のメタデータにのみ依存する self-contained な状態にする。

変換時のメタデータの参照源を決めておく。ページレベルのもの（frontmatter + 2節で追加するフィールド）は MDX から、章レベルのもの（`shortTitle`、`part`、`outcome`）は `src/data/curriculum.json` から取り、表示名を統一する。スライドの表紙や節扉はこの2つの参照だけで構成できる。

## 6. Web 版とスライド版で内容の不整合を生まない設計

**結論: MDX を唯一の事実とし、スライドと PDF は生成物として扱う。生成物をリポジトリで管理せず、CI で生成と検査を行う。**

- MDX・frontmatter・`src/data/diagrams.ts` に手を入れたコミットでは、スライド変換が動く。未知の JSX・未登録の用語・リンク切れは `src/plugins/remark-guide-links.mjs` と同型の「変換を止める」保護で検出する。そのため、本文の加筆が漏れなく Web とスライドの両方に反映される。
- スライドの PDF や SVG をリポジトリに commit しない。理由は (1) 生成された PDF のバイナリ差分は diff レビューに向かない、(2) 生成物の commit が増える、(3) 検査は CI 上での生成結果の比較の方が確実であるため。`git` 管理の対象は「本文 MDX」「変換スクリプト」「スライド用テーマ」に限定する。
- CI での検査は、次を最低限にする。(a) 変換に失敗しないこと（未知の JSX・未登録の用語・未登録の章）。(b) 1章あたりのスライド枚数が見出し数と整合すること（厳密な一致チェックにするか、しきい値にするかは実装時に決める）。(c) SVG 化済みの図が `src/data/diagrams.ts` の `name` と対応していること。(d) 出典の `url` のスキームが妥当であること（`https`・`http` のみを許し、`data:` 等は拒否する）。
- レビュー手順として、章の加筆を入れた PR では、生成された PDF へのリンクを CI が job summary に掲載する。レビュー者は「本文をどう変えたか」を MDX の diff で確認し、「スライド上の見た目」を CI が生成した PDF で確認する。目視はこの2点に集約できる。「本文を変えたのにスライドが古い」という不整合は、正本が一元化されている以上、変換スクリプト自体が壊れている場合にしか起こり得ないため、変換スクリプトの変更と本文の変更は同じ PR に混ぜない運用を合わせて敷く。

生成物の差分検出として、中間生成物である「スライド用 Markdown」だけはテキストであるため、これを CI 上で再生成して前回の実行結果と比較する。MDX の変更がスライド出力のどの部分に影響したかをマシン側で検出し、意図しない文言の増減をレビュー前に気づける。スライド PDF（バイナリ）の比較は行わず、Markdown（テキスト）の比較で代用する。中間 Markdown をリポジトリに commit するかは実装時に決める（commit すればローカル diff が増え、commit しなければ CI だけが差分を把握する。どちらが主流でも設計の前提は変わらない）。

## 7. インタラクティブ図・スナップショット・出典の扱い

**結論: Web 版で操作できる図も、スライドと PDF では「JavaScript を動かさない既定の状態」を1枚の図として出す。数値の出所は本文と同じデータファイルに固定し、スライド側で値を書き写さない。**

### 7-1. インタラクティブな図

`ProbabilityChart` と `PriceCompareChart` は、ビルド時に HTML とインライン style で値を焼き込む静的実装である（4節）。この性質はスライド再利用の前提でもあるため、操作を足す場合も次の制約を守る。

- 実行時 JavaScript を足すのは、静的状態だけでは伝わらない1つの操作に限る。いまの想定は、`src/data/next-token-example.ts` のロジットから温度を変えて softmax の結果を見る操作である。温度の計算式をコンポーネント側に複製せず、データと同じ計算関数を共有する。
- JavaScript がない状態、および初期表示では、**温度を1としたときの棒グラフをそのまま出す**。本文の表・キャプションと数値が一致する状態を既定にする。操作を加えても、JS 無効時に空の枠や「読み込み中」だけが残る実装にはしない。
- スライド変換では、操作部分を落として既定状態の図だけを採用する。スライドのマッピング表（4節）には「静的状態を出力する」と明記し、操作 UI の HTML をスライド Markdown に流し込まない。
- 値の整合は変換時ではなくビルド時に検査する。確率の合計が1であること、ラベルと数値が対応していることは、既存の `ProbabilityChart` の検証と同じく、ビルドを止める条件にする。スライド側でも同じデータと同じ関数を使うため、Web とスライドで数値がずれる余地を残さない。
- 操作 UI はキーボードで動かせ、値の変化が読み上げでも追えるようにする（`input` の label、現在値のテキスト出力）。動きを伴う演出は入れない。`prefers-reduced-motion` への分岐が必要になるようなアニメーションは、この用途では使わない。

### 7-2. スナップショット

モデルの料金・コンテキスト長のような、外部の都合で変わる値は、能力の評価と混ぜずに別ファイルへ置く（`src/data/model-comparison.json` の価格・文脈長と、能力の記述を分ける方針）。スライドもこの分離をそのまま引き継ぐ。

- スナップショットには、取得日・出典・条件（ベンチマーク名、指標、モデルの版）を添える。日付のない数値は、スライドに載せない。
- 有効期限を過ぎた値や、出典を確認できない値は、図表から外す。推測で埋めない。埋められない場合は、その図をスライドから落とす判断をする。
- スライドの PDF は生成時点のスナップショットを写したものになる。配布した PDF の数値が古くなったときのために、PDF の奥付か最終ページに、データの取得日と MDX の更新日を出す。

### 7-3. 出典の保全

- 出典は MDX の frontmatter `sources` を唯一の正とし、スライドの参考文献ページもここから生成する。スライド用に別の出典リストを作らない。
- URL は変換時にそのまま引き継ぐ。リンクの到達確認は CI では行わない（ネットワークに依存させない）。代わりに、URL の形式（`https`・`http` のみ）と、`title` が空でないことを検査する。
- 到達できなかった出典は、値を創作して埋めず、URL を外して書誌情報だけを残す。外した理由は、本文の更新履歴か PR の説明に残す。

## 実装順序

段階を分け、各フェーズで「何をしたら次に進めるか」を明示する。Web 版に対する破壊的な変更はどのフェーズにも含めない。

### フェーズ1: 変換パイプラインのプロトタイプ（コードを書かない段階を含む）

- 1つの章（例: `src/content/chapters/04/01-pipeline.mdx`）を選び、その MDX が mdast 上でどのノード型に展開されるかを、remark 単体（`remark-parse` + `remark-mdx`）のサンプル実装によって一覧化する。特に `Diagram`, `Callout`, `DeepDive` が `mdxJsxFlowElement` にどう現れるかを確認する。`ModelTable` と2つのグラフは子要素を持たない自己終了の要素なので、その形もあわせて見る。
- 「MDX → スライド Markdown」のマッピング表（4節参照）をこの章で検証する。MDX の実態と表の内容が一致するかを見る。
- 完了条件（次に進める条件）: 選んだ1章について、「見出し単位に切ったスライド Markdown が問題なく生成できるか」の見立てが得られ、表に記載したマップの実装目途が立つこと。もし JSX の構造化が意外に困難だった場合、その事実をこの設計文書に反映してから次のフェーズへ進む。

### フェーズ2: 図の SVG 化とキャプション一元化

- `scripts/render-diagrams.mjs`（仮称）を実装し、SVG 出力が静的に作れるかを `llm-pipeline` を含む1〜2枚で試す。ブラウザ描画との見た目の差（フォント・色）を確認する。
- SVG 化に成功したら、SVG 出力の配置（例: `public/diagrams/`）と変換時の再生成判定の仕組みを確定する。失敗した場合もクライアント側描画がフォールバックとして残り続けるため、この段階で `src/components/Diagram.astro` を変更する必要はない。
- 完了条件: 1〜2枚の Mermaid 図が SVG で再現でき、スライドの Markdown に埋め込めることが確認できること。

### フェーズ3: メタデータ拡張と変換辞書の確定

- `src/content.config.ts` に `objectives`・`slides` を追加する。Optional の追加であるため、既存の MDX の frontmatter への一括修正は必要なく、随時書き足すだけでよい。zod の default で既存の MDX も検証を通ることを確認する。
- 4節のマッピング表を実装する。マッピング表に存在しない JSX の場合にビルドを停止する保護も実装する。
- 完了条件: 全章に対象を広げてそれぞれのページでスライド Markdown に変換できること。どこかの章で「変換しきれない JSX が見つかった」場合、マッピングの設計を見直してから次のフェーズへ進む。

### フェーズ4: Marp によるスライド出力と CI

- Marp を導入し、変換辞書から出た Markdown に `marp: true` 等の frontmatter を付与して、`marp-cli` で PDF または HTML を出力する。
- スライド用テーマを最低限（章扉・本文・図ページ・理解チェックの1〜2種）だけ作る。メタデータ（章番号・図番号・キャプション）の表示は Web 版と同じく `src/data/diagrams.ts`・`src/data/curriculum.json` の参照に統一する。
- 完了条件: CI 上で「MDX 変更 → スライド PDF 再生成 → 検査」が走り、失敗時に CI が赤になる。

以上の各段階を踏む中で、「何をしたら次に進めるか」の条件は実態に合わせて適宜更新する。この文書は設計の方針を固定するものであり、実装を約束するものではない。着手をした後は、現実の進捗に応じてこの文書を読み直す前提で運用する。
